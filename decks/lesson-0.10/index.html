Part 5 · Networking · conceptual

The request path and the service

BalanceService.swift
import Foundation

struct BalanceResponse: Decodable {
    let balanceMinor: Int64
    let currency: String
}

struct BalanceService {
    func fetchBalance() async throws -> BalanceResponse {
        let url = URL(
            string: "https://api.npay.example/balance"
        )!

        let (data, response) =
            try await URLSession.shared.data(from: url)

        guard let http = response as? HTTPURLResponse,
              http.statusCode == 200 else {
            throw URLError(.badServerResponse)
        }

        return try JSONDecoder().decode(
            BalanceResponse.self,
            from: data
        )
    }
}

Fictional URL. Real banking code also needs authentication, authorization-aware error handling and secure token management.

SAY

Click down the path: DashboardView, BalanceViewModel, BalanceService, URLSession, HTTPS and the bank API.

SAY

The service builds the URL, awaits URLSession, checks for a 200 status and decodes BalanceResponse. The URL is fictional, and real code needs authentication, authorization-aware error handling and secure token management.

Part 8 · Design challenge

“Just put it all in UserDefaults”

A developer proposes saving the token, the balance and all transactions in UserDefaults. What is wrong?

Authentication token

Use appropriate Keychain protections, not ordinary preferences.

Account balance

The backend is authoritative; a local copy may be stale.

Transactions

A structured persistence mechanism, with data protection and retention.

Preferences

UserDefaults is right for small, non-secret settings.

Choose storage by sensitivity, size, lifecycle and consistency needs, not because an API is easy.
ASK

A developer proposes saving the authentication token, account balance and all transactions into UserDefaults. What is wrong?

EXPECT

Different data has different security, persistence and performance requirements.

SAY

Click through: the token needs Keychain protection; the balance belongs to the backend and a local copy may be stale; transactions need structured persistence with data protection and retention; only preferences belong in UserDefaults. Choose storage by sensitivity, size, lifecycle and consistency, not convenience.

Part 10 · Ownership · conceptual

A ViewModel and its closure

A stored closure that strongly captures the ViewModel creates a retain cycle. [weak self] avoids it.

TransactionViewModel.swift
class TransactionViewModel {
    var onRefresh: (() -> Void)?

    func configure() {
        onRefresh = { [weak self] in
            self?.refresh()
        }
    }

    func refresh() {
        print("Refreshing transactions")
    }

    deinit {
        print("ViewModel deinitialized")
    }
}
SAY

Click down: the view owns the ViewModel, which uses the service. If the ViewModel stores a closure that strongly captures the ViewModel, a retain cycle can form; this code uses weak capture to avoid it.

ASK

Does navigating away from a screen guarantee its ViewModel’s deinit runs immediately?

EXPECT

No. It may still be legitimately retained elsewhere. Navigation and object lifetime are related but not identical.

Survived, or terminated?

Part 11 · Return scenarios

Warm activation or cold launch

Process survived: warm activation
  1. iOS resumes execution if the process was suspended.
  2. The scene returns toward the foreground.
  3. In-memory state may still exist.
  4. The app refreshes data when appropriate.
Process terminated: cold launch
  1. iOS starts a new process.
  2. The launch runs again, as in Stage one.
  3. In-memory state is gone.
  4. The app restores persisted data and fetches fresh data.
Work correctly in both. Never assume the process stays alive, and never assume cached financial data is current.
SAY

Warm activation: iOS resumes the suspended process, the scene comes back to the foreground, in-memory state may still exist, and the app refreshes data when appropriate. Click: cold launch: a new process, the full launch again, in-memory state is gone, so the app restores what it persisted and fetches fresh data.

SAY

A robust app must work in both cases. Never assume the process stays alive, and never assume cached financial data is current.
