For modern Swift: an asynchronous task is not the same thing as a thread. Swift concurrency schedules tasks onto executors, and tasks may suspend without blocking an operating-system thread. We return to this shortly.

What is a RunLoop?

The main thread does not poll in a busy loop. It waits, handles one piece of work, and waits again.

Here is the cycle.

Part 3 · RunLoop · conceptual

The RunLoop cycle

A RunLoop lets a thread wait for and process work: input events, timers and scheduled callbacks. The main thread’s run loop takes part in app event processing.

It can only handle the next event when execution returns to it. A callback that blocks for seconds stops everything else.

Conceptual. The real Core Foundation RunLoop has modes, input sources, observers, timers and dispatch-queue integration.

SAY

A RunLoop lets a thread wait for and process sources of work: input events, timers and scheduled callbacks. Click through the cycle: the head chef waits at the order rail, takes the next ticket, cooks that one order, and returns to the rail. The RunLoop is the order rail.

SAY

Why it matters: the loop only handles the next event when execution returns to it. If a main-thread callback blocks for several seconds, other main-thread work cannot proceed normally.

The button action runs on the main actor, and Thread.sleep blocks the executing thread for three seconds. During that time other main-thread work cannot proceed normally: taps, scrolling and animations all wait.

SAY

Click: the non-blocking version. The task suspends while it waits, and the main thread stays free for UI work.

Part 5 · Non-blocking

Suspend instead of block

DashboardView.swift
Button("Refresh balance") {
    Task {
        isLoading = true
        do {
            balance = try await balanceService.fetchBalance()
        } catch {
            errorMessage = error.localizedDescription
        }
        isLoading = false
    }
}
await suspendsthe task pauses while the operation is pending
The main thread stays freeno blocking is required
async does not move CPU-heavy work off the main actor. Heavy synchronous computation still needs to run elsewhere.
SAY

Use asynchronous APIs for operations that can suspend, such as networking. await lets the task suspend while the operation is pending, without blocking the main thread.

SAY

Important nuance: async does not automatically move CPU-intensive work off the main actor. Heavy synchronous computation still needs appropriate isolation or execution elsewhere.

Part 6 · Comparison

Main thread vs MainActor

Main threadMainActor
Operating-system threadSwift concurrency global actor
Executes UI event processingSerializes access to main-actor-isolated code
Exists at runtimeEnforced through Swift’s actor isolation model
Can be blocked by synchronous workCode waiting at await lets other main-actor work run first

SAY

The main thread is an operating-system thread that executes UI event processing; it exists at runtime and can be blocked by synchronous work. MainActor is a Swift concurrency global actor that serializes access to main-actor-isolated code, enforced by Swift’s actor isolation model, and it can suspend at await points.

SAY

Mental model: MainActor is an isolation mechanism that coordinates main-thread-bound work.

SAY

Click: one consequence. While a main-actor function waits at await, the main actor is free to run other main-actor work, such as a second tap on Refresh balance. So when the function resumes, state it read before the await may have changed. That is actor reentrancy: re-check state after every await. Unit 08 covers it properly.

Part 6 · @MainActor

A main-actor ViewModel

DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    private(set) var balanceText = "—"

    func show(_ balance: Balance) {
        balanceText = (Decimal(balance.balanceMinor) / 100)
            .formatted(.currency(code: "INR"))
    }
}

The annotation helps ensure the ViewModel’s mutable state is accessed consistently through the main actor.

@MainActor does not make a slow calculation faster. A long synchronous calculation on the main actor can still freeze the UI.
SAY

Marking the ViewModel @MainActor means its mutable state, like balanceText, is always accessed through the main actor, which is where SwiftUI reads it. The balance arrives in paise as balanceMinor; the ViewModel formats it as rupees for the screen.

ASK

Does @MainActor make a slow calculation faster?

EXPECT

No. It provides isolation, not acceleration. A long synchronous calculation on the main actor can still freeze the interface.

Part 7 · Three kinds of work

Three things called “background”

Asynchronous I/O

Network requests that wait without occupying a thread. Most file APIs are synchronous: keep large reads and writes off the main actor.

CPU-bound parallel work

Image processing, data transformation and expensive calculations that need CPU time away from the main actor.

iOS background execution

Work allowed while the app is no longer foreground, subject to system policies and capabilities.

An async task does not mean iOS will let it continue after the app is suspended.
SAY

Asynchronous I/O: network requests that can wait without occupying a thread. Careful with files: most file APIs, such as Data(contentsOf:) and write(to:), are synchronous and block the calling thread, so large reads and writes belong off the main actor. CPU-bound parallel work: image processing, data transformation, expensive calculations that need CPU execution away from the main actor. iOS background execution: work allowed after the app leaves the foreground, subject to system policies and specific capabilities, as in Lesson 0.3.

SAY

These are different concerns. An async task does not automatically mean iOS will let it continue after the app is suspended.

The rendering pipeline and frame budget

The display refreshes many times a second: 60 Hz, or up to 120 Hz on ProMotion displays, which adapt their rate. Each refresh is a deadline.

Compare 60 Hz and 120 Hz.

Part 8 · Frame budget · illustrative

One refresh, one deadline

Your app does not get the whole interval: the system also needs time for layout, rendering and compositing. ProMotion displays adapt their rate, up to 120 Hz.

If main-thread work or rendering misses it, no new frame arrives in time: visible stutter or dropped frames.
SAY

An iPhone display updates at a rate the device and conditions support. At 60 Hz one refresh interval is about 16.67 milliseconds; click, and at 120 Hz it is about 8.33.

SAY

Back in the kitchen: a frame is a dish sent out on every tick. ProMotion displays adapt their rate, low when nothing moves and up to 120 Hz while scrolling, so the deadline changes with them.

SAY

That does not mean the app gets the whole interval for arbitrary computation; the system also needs time for layout, rendering, compositing and other work. Miss the deadline and the interface may not deliver a new frame in time, which shows as stutter or dropped frames.

Part 11 · Two kinds of slow

Waiting vs computing

Asynchronous I/O

Download the NPay balance

Mostly waiting for an external response.

CPU-bound work

Process a million transactions

Mostly executing calculations on a CPU.

BalanceService.swift
func fetchBalance() async throws -> Data {
    let url = URL(string: "https://api.npay.example/balance")!
    let (data, _) = try await URLSession.shared.data(from: url)
    return data
}

While URLSession waits for the response, the task suspends. No thread sits idle waiting.

SAY

Operation A downloads the NPay balance: mostly waiting for the bank’s server. Operation B processes a million transaction records: mostly executing calculations. Both take time, for different reasons.

SAY

For networking: when URLSession waits for the response, the calling task can suspend. The executing thread does not need to sit idle.

But what about the calculation?

Part 11 · async is not parallel

async does not mean background

Spending.swift
@MainActor
func totalSpent(_ amountsMinor: [Int64]) async -> Int64 {
    var total: Int64 = 0
    for amount in amountsMinor {   // a million transactions
        total += amount
    }
    return total
}

Declared async, but it does synchronous CPU work on the main actor with no suspension point. It can block the UI.

async enables suspension. It does not guarantee parallel execution or a different thread.
SAY

Despite being declared async, this function loops over a million NPay transactions as synchronous CPU work on the main actor. It contains no suspension point, so it can block UI responsiveness.

ASK

Does adding async automatically create a background thread?

EXPECT

No. async enables suspension; it does not guarantee parallel execution or a different thread.

Predict the print order

A Swift command-line lab: no Xcode project needed.

  1. Save the starter file as lab05.swift: this code plus a fetchBalance() that waits 0.2 s.
  2. Before running, write down the order in which A–E print.
  3. Run swiftc -swift-version 6 lab05.swift -o lab05 && ./lab05. Were you right?
  4. Replace await fetchBalance() with a blocking call (Thread.sleep inside a plain function). Predict again, run, and explain why B moves.
lab05.swift
// + fetchBalance(): waits 0.2 s, returns 25_000
@MainActor
func refreshBalance() async {
    print("A: Refresh balance tapped")
    Task { print("B: a new main-actor task runs") }
    print("C: the action continues")
    let balance = await fetchBalance()
    print("D: balance \(balance) arrived")
}

await refreshBalance()
print("E: done")
SAY

A command-line lab: predict first, then run. Expected output: A, C, B, D, E. B runs while refreshBalance waits at await. With a blocking call instead, the order becomes A, C, D, B, E: the new task cannot run until the main actor is free. LAB SCRIPT, full starter file lab05.swift: func fetchBalance() async -> Int { try? await Task.sleep(for: .milliseconds(200)); return 25_000 } followed by the code on the slide. Step 4 version: import Foundation; func blockingFetch() -> Int { Thread.sleep(forTimeInterval: 0.2); return 25_000 }; call let balance = blockingFetch(); and add try? await Task.sleep(for: .milliseconds(100)) before print("E: done") so B has time to print before the program exits. Note: Swift 6 refuses Thread.sleep directly inside an async function, which is why it sits in a plain function.
