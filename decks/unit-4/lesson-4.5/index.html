An application-facing interface to domain data

    repository.fetchBalance()
Hidden from the caller

  • A local database
  • A remote API

SAY

A repository provides an application-facing interface for accessing and modifying domain data, and hides how the data is stored or retrieved. The caller writes try await repository.fetchBalance() and does not know whether that is an in-memory dictionary, a local database or a remote API.

SAY

Click: repository versus service. The repository retrieves and stores domain data and abstracts data sources: fetchBalance, fetchTransactions, saveTransaction. A service or use case coordinates behaviour and enforces workflows: sendPayment, validate and execute a transfer, decide when to save and what to return.

SAY

Click: the distinction is architectural, not enforced by Swift, and in some apps a repository operation is itself a meaningful atomic domain operation, as ours will be.

Part 3 · An in-memory repository (section 6)

An actor: one operation at a time on its state

InMemoryAccountRepository.swift (condensed)
actor InMemoryAccountRepository: AccountRepository {
    private var balancePaise: Int
    private var transactions: [PaymentRecord] = []

    init(initialBalancePaise: Int = 2_500_000) {
        self.balancePaise = initialBalancePaise
    }

    func fetchSnapshot() async throws -> AccountSnapshot {
        AccountSnapshot(balancePaise: balancePaise, transactions: transactions)
    }

    func recordPayment(recipient: String, amountPaise: Int)
        async throws -> PaymentRecord {
        let trimmed = recipient.trimmingCharacters(
            in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty else { throw AccountRepositoryError.invalidRecipient }
        guard amountPaise > 0 else { throw AccountRepositoryError.invalidAmount }
        guard amountPaise <= balancePaise else {
            throw AccountRepositoryError.insufficientBalance }

        let payment = PaymentRecord(id: UUID(), recipient: trimmed,
            amountPaise: amountPaise, createdAt: .now)
        balancePaise -= amountPaise
        transactions.insert(payment, at: 0)
        return payment
    }
}
recordPayment
  • Check recipient, amount, balance
  • Create the record
  • Deduct, insert, return
Why an actor?
  • Protects mutable state from unsynchronized access
  • Called with await from outside
  • No await inside check-and-update
SAY

Our first repository is a Swift actor. It holds the balance, default ₹25,000, and the transactions, both private. fetchSnapshot returns them together. recordPayment trims the recipient and throws invalidRecipient if it is empty, invalidAmount if the amount is not positive, insufficientBalance if it exceeds the balance; otherwise it creates the record, deducts, inserts it first, and returns it.

SAY

Click: why an actor? It protects its mutable state from unsynchronized concurrent access; outside callers reach its methods asynchronously, with await.

SAY

Click: the detail that makes it work: there is no await inside the check-and-update sequence. Actor isolation then lets that sequence run without another actor-isolated operation interleaving. Imagine two payments arriving almost together: let’s test that.

Part 3 · Actor isolation, measured (section 7)

Concurrent payments can’t overdraw

Mac run, the text’s code (Swift 6)

two ₹1,500 payments at once, ₹2,000 balance:
 a@npay: recorded
 rejected: insufficientBalance
 balance 50000, transactions 1

1,000 concurrent ₹1 payments, ₹500 balance (ours):
 recorded 500, rejected 500; balance 0

Which request wins isn’t guaranteed; that one wins is.

Why
  • Each recordPayment runs to completion
  • The second sees ₹500, and is rejected
  • Data-race safety, not workflow atomicity
  • An await between read and write breaks it (Part 6)
SAY

The text’s scenario: ₹2,000, two ₹1,500 payments at the same moment. We ran it: one recorded, the other rejected with insufficientBalance; balance ₹500, one transaction. Which request wins depends on scheduling, as the text notes; that exactly one wins does not.

SAY

Then a heavier version of ours: a thousand concurrent ₹1 payments against ₹500. Exactly five hundred recorded, five hundred rejected, balance zero. No lost updates.

SAY

Click: why: each recordPayment runs its non-suspending check-and-update to completion before the next one touches the balance. Click: but the text’s insight: actors prevent data races on isolated state; they do not make a multi-step workflow atomic if it suspends between reading and writing. Part 6 measures that, and Unit 8 studies reentrancy.

Part 4 · Connect the repository to a payment service (sections 9, 15)

Depend on the contract; translate its errors

RepositoryPaymentService (section 15’s version)
@MainActor
final class RepositoryPaymentService: PaymentService {
    private let repository: any AccountRepository

    init(repository: any AccountRepository) {
        self.repository = repository
    }

    func send(_ request: PaymentRequest) async throws
        -> PaymentReceipt {
        do {
            let payment = try await repository.recordPayment(
                recipient: request.recipient,
                amountPaise: request.amountPaise)
            return PaymentReceipt(transactionID: payment.id,
                recipient: payment.recipient,
                amountPaise: payment.amountPaise)
        } catch AccountRepositoryError.invalidRecipient {
            throw PaymentError.invalidRecipient
        } catch AccountRepositoryError.invalidAmount {
            throw PaymentError.invalidAmount
        } catch AccountRepositoryError.insufficientBalance {
            throw PaymentError.insufficientBalance
        } catch {
            throw PaymentError.unknown
        }
    }
}
What changed
  • Before: DemoPaymentService → NPayStore
  • Now: RepositoryPaymentService → AccountRepository
Error mapping
  • Storage errors → PaymentError
  • Better than nil for every failure
  • Section 15’s version replaces section 9’s
SAY

Section 9 adds a PaymentService implementation built on the repository: it records the payment and turns the PaymentRecord into a PaymentReceipt. Section 15 improves it, and that is the version on the slide: each AccountRepositoryError is caught and rethrown as a PaymentError, with anything else becoming unknown.

SAY

Before, DemoPaymentService depended on the concrete NPayStore; now RepositoryPaymentService depends on the AccountRepository abstraction. Click: why map errors? The payment feature should not expose internal storage or networking errors directly to the UI; the service translates repository failures into payment-domain failures. Three distinct cases are better than a nil that could mean anything.

SAY

Click: the text’s warning: section 15’s version replaces section 9’s; keep only one declaration in a target, or it will not compile.

Part 7 · Repository consistency (section 14)

Read, then later write: the balance can move

Section 14: an unsafe design
let balance = try await repository.fetchBalance()

guard balance >= amount else {
    throw PaymentError.insufficientBalance
}

try await repository.saveTransaction(payment)
try await repository.updateBalance(balance - amount)
Two problems
  • The balance can change between read and update
  • Save can succeed while update fails
Mac run, the text’s code (a 20 ms await stands in for I/O)

two ₹1,500 payments at once, ₹2,000 balance
split read / save / update, on an actor (ours):
 both accepted: 2 transactions, ₹3,000
 balance ₹500 (each wrote 2,000 − 1,500)

recordPayment (one call): 1 accepted, 1 rejected

  • Validate and mutate in one actor call
  • No suspension inside
  • No durable transactions, no cross-device consistency
SAY

The unsafe design: fetch the balance, check it, then save the transaction and update the balance in two more calls. Two problems: the balance can change between reading and updating; and saving might succeed while the balance update fails, leaving inconsistent records.

SAY

Click: we built exactly that shape, on an actor, so every individual call is data-race safe, with a short await between reading and writing standing in for any I/O. Two ₹1,500 payments at once from ₹2,000: both accepted. Two transactions totalling ₹3,000, and the balance ₹500, because both computed 2,000 minus 1,500 from the same stale read. The single recordPayment call: one accepted, one rejected. Actor isolation was never the problem; the suspension in the middle of the workflow was.

SAY

Click: so our repository validates and mutates in one actor call with no suspension inside: check the request, check the balance, create, deduct, insert, return. Click: production-ready? No: that protects one actor instance’s memory. Durable database transactions, cross-device consistency and server-enforced authorization must come from the backend and persistence architecture.

Part 7 · Duplicate payment requests (section 20)

Concurrency safety ≠ idempotency

Mac run, the text’s code: the same request, twice, one after the other

transactions 2, balance 2,199,900
(₹1,500.50 taken twice)

Concurrency safetyIdempotency
Safe concurrent access to stateThe same logical request applied once
The actor provides itNeeds a request identifier
Where it’s enforced
  • The backend, with request IDs and authoritative records
  • Later: use cases (4.6) and networking (Unit 5)
  • The UI guards (isProcessing, isSubmitting) don’t reach the server
SAY

Suppose the same logical payment is submitted twice, one after the other. The actor executes both safely, and we measured it: two transactions, balance 2,199,900: ₹1,500.50 taken twice. Safely, and wrongly.

SAY

Click: concurrency safety and idempotency are different. Actor isolation prevents unsafe concurrent access to its state. Idempotency prevents the same logical request from being applied more than once, and it needs an identifier for the request.

SAY

Click: in a real payment system the backend enforces idempotency with request identifiers and authoritative transaction records; we revisit it with use cases and networking. Click: and the guards we already have, the sheet’s isProcessing and the ViewModel’s isSubmitting, only stop a double tap in this process; they never reach the server.

Lesson 4.5 · Recap

What to remember

A repository hides where data lives
one contract: fetchSnapshot, recordPayment

One atomic actor call
1 of 2 accepted; the split workflow took ₹3,000 from ₹2,000

Share it; refresh deliberately
one repository, two ViewModels, explicit refresh

SAY

Three things to remember. A repository is the application’s contract for domain data; it hides whether data comes from memory, a database or an API, and the service above it translates its errors into payment errors. Payment and balance must change together: our actor does it in one non-suspending call, so concurrent payments cannot overdraw, while the split read-save-update workflow accepted ₹3,000 from ₹2,000. And share one repository across ViewModels, but refresh their snapshots deliberately: a snapshot never updates itself, and a failed refresh is not a failed payment.
