Part 3 · PaymentViewModel with explicit UI state (section 8)

isSubmitting + errorMessage + successRecord → state

PaymentViewModel (condensed)
private(set) var state: PaymentUIState = .idle

func submit(_ command: SendPaymentCommand) async {
    guard !state.isBusy else { return }

    state = .validating
    // Command value objects were validated at creation.
    state = .submitting

    do {
        let record = try await sendPayment.execute(command)
        recipient = ""; amountText = ""
        state = .success(record)
    } catch PaymentDomainError.insufficientBalance {
        state = .failure("Insufficient balance")
    } catch PaymentDomainError.limitExceeded {
        state = .failure("Demo payment limit exceeded")
    } catch {
        state = .failure("Unable to complete payment")
    }
}

func reset() {
    guard !state.isBusy else { return }
    state = .idle
}

  • One enum replaces three properties
  • private(set): only the ViewModel moves it

SAY

The core implementation: the ViewModel keeps recipient and amountText, and a private(set) state starting at idle. submit refuses if busy, sets validating, then submitting, awaits the use case, and moves to success with the record or to failure with a message for insufficient balance, the limit, or anything else. reset returns to idle unless busy. Previously we had isSubmitting, errorMessage and a success record; now one enum.

The text predicts exactly this, and says not to insert artificial delays just to make every state visible.

Why can SwiftUI show submitting at all?

Part 3 · async/await and UI state (sections 9–10)

await is a suspension point, not a thread

While suspended
  • The main actor runs other work
  • SwiftUI can render .submitting
  • await doesn’t pick a thread
  • Actor isolation and the callee do
SAY

Click through the asynchronous lifecycle: on the main actor, state becomes submitting; await execute is a possible suspension point; the repository actor processes its isolated account state; the result, a record or a thrown error, comes back; on the main actor, state becomes success or failure; SwiftUI displays the new state.

SAY

Click: while the operation is suspended, the main actor can run other eligible work, including SwiftUI rendering the submitting state. That is why the ProgressView can appear at all.

SAY

Click: does await create a background thread? No. async/await is a concurrency abstraction, not a promise to run on a particular thread; where code runs depends on actor isolation and on the operation called. Lesson 3.11 showed the flip side: synchronous work on the main actor delivered no frames.

A safer submit contract.

Part 6 · A safer submission contract (sections 20–21)

Return the result; still publish the state

Section 20 (condensed)
enum PaymentSubmissionResult {
    case success(PaymentRecord)
    case failure(String)
    case statusUnknown
}

func submit(_ command: SendPaymentCommand)
    async -> PaymentSubmissionResult {
    guard !state.isBusy else {
        return .failure("A payment is already processing")
    }
    state = .validating
    state = .submitting
    do {
        let record = try await sendPayment.execute(command)
        state = .success(record)
        recipient = ""; amountText = ""
        return .success(record)
    } catch PaymentDomainError.insufficientBalance {
        state = .failure("Insufficient balance")
        return .failure("Insufficient balance")
    } // ... limitExceeded, then a generic failure
}
Before
  • submit() returned Void
  • The caller read shared state after the await
Now
  • The caller gets this call’s result
  • Views still render state
  • Confirm switches on the result (Part 4)
SAY

Section 20 improves the contract. The earlier submit returned nothing, so the caller had to inspect mutable state after awaiting it, and that state might already belong to something else. Now submit returns a PaymentSubmissionResult: success with the record, failure with a message, or statusUnknown, and still sets state for rendering.

SAY

Click: the caller receives the result of exactly the command it submitted; the views keep rendering the published state. Two complementary responsibilities. Click: NPay’s Confirm already switches on this result, as Part 4 showed. For the local demo the repository gives definitive answers, so no unknown outcome is invented for ordinary validation errors.

Part 7 · Why not one enormous enum? (section 23)

Separate concerns; impossible combinations within each

Elsewhere already
  • Focus: @FocusState (2.11)
  • Sheet: review; route: NPayRouter
  • Draft: the ViewModel; appearance: preferences
  • Make invalid combinations hard
  • Not the fewest variables
SAY

PaymentUIState models submission status. NPay also has text-field focus, review-sheet visibility, navigation paths, appearance preferences and the payment draft. Combine them into one enum? No: that would produce an overly complex state machine. Click: the payment feature has form state, submission state, in teal, presentation state and navigation state, each with its own owner.

SAY

Click: the goal is not to minimize state variables at all costs; it is to make invalid combinations hard to represent while keeping independent concerns separate.

The recap.

Lesson 4.7 · Recap

What to remember

One enum, one lifecycle
idle, validating, submitting, success, failure, unknown

Results belong to submissions
return the result; check the active ID

Cancelled ≠ reversed ≠ failed
cancelled after recording: the money moved

SAY

Three things to remember. Model the submission lifecycle as one enum with associated values, guard it with isBusy, and render it with an exhaustive switch; four Booleans allow sixteen states, most of them nonsense. Tie every asynchronous result to the submission that produced it: return it from submit, and ignore results whose submission is no longer active. And keep cancellation, failure and unknown apart: our cancelled task reported failure after the money had already moved, which is exactly what statusUnknown and status checks exist for.
