SAY

Three shapes, as simplified teaching diagrams. Click: MVC, Model-View-Controller, historically common in UIKit: the controller coordinates user interaction and updates between views and models.

SAY

Click: MVVM, Model-View-ViewModel: the ViewModel holds the state and behaviour a screen needs, separate from how the screen looks. It fits SwiftUI’s state-driven approach naturally. Click: Clean Architecture emphasises dependency direction and keeping business rules apart from external technologies such as networking and storage. It complements MVVM rather than replacing it.

SAY

NPay’s choice, in the title: MVVM for presentation, with domain use cases and repository abstractions introduced incrementally across Unit 4.

Part 4 · Move validation out of the View (section 5)

PaymentValidator: rules without SwiftUI

PaymentValidator.swift (import Foundation)
enum PaymentValidationError: Error {
    case emptyRecipient
    case invalidAmount
    case insufficientBalance
}

struct PaymentValidator {

    func validate(
        recipient: String,
        amountPaise: Int,
        balancePaise: Int
    ) throws {

        guard !recipient.trimmingCharacters(
            in: .whitespacesAndNewlines
        ).isEmpty else {
            throw PaymentValidationError.emptyRecipient
        }

        guard amountPaise > 0 else {
            throw PaymentValidationError.invalidAmount
        }

        guard amountPaise <= balancePaise else {
            throw PaymentValidationError.insufficientBalance
        }
    }
}
Three rules, three errors
  • Recipient not blank
  • Amount above zero
  • Amount within the balance
What changed
  • No dependency on SwiftUI
  • Callable from a ViewModel, a use case, a test
  • Toward testable architecture
SAY

Start small. Our payment form validates the amount inside the SwiftUI view. We extract a pure Swift validation component: an error enum with three cases, empty recipient, invalid amount, insufficient balance; and a PaymentValidator struct whose validate method takes the recipient, the amount in paise and the balance in paise, and throws.

SAY

The rules: the recipient, trimmed of whitespace, must not be empty; the amount must be above zero; the amount must not exceed the balance. Only Foundation is imported. Click: the rules no longer depend on SwiftUI: we can call them from a ViewModel, a use case or a unit test. Click: this is our first step toward a testable architecture.

From Unit 1
  • Protocols, async, throws
  • Dependency abstraction
SAY

Suppose NPay first uses an in-memory payment repository and later a network-backed one. We do not want to rewrite every ViewModel. So we define an abstraction: PaymentRepository, with one async throwing method, sendPayment, returning the new payment’s UUID. Different implementations conform to the same contract; DemoPaymentRepository is the simplest.

SAY

Click: we called it through the protocol type on the Mac: it returned an ID, and the balance was unchanged. Click: that is the text’s point: this implementation is only a contract demonstration; it does not update NPay’s balance or history. A real in-memory demo repository connected to account state comes in Lesson 4.5.

SAY

Click: these are Unit 1 fundamentals at work: protocol-oriented programming, async and throwing functions, and dependency abstraction.
