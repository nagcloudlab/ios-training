Part 5 · Build the payment submission method (section 9)

Coordinate: validator, store, presentation state

submitPayment() (condensed)
func submitPayment() -> UUID? {
    guard let amount = Money.parsePaise(amountText) else {
        errorMessage = "Invalid amount"
        return nil
    }
    do {
        try PaymentValidator().validate(
            recipient: recipient, amountPaise: amount,
            balancePaise: store.balancePaise)
    } catch {
        errorMessage = "Payment validation failed"
        return nil
    }
    guard let transactionID = store.recordDemoPayment(
        recipient: recipient, amountPaise: amount) else {
        errorMessage = "Unable to record payment"
        return nil
    }
    recipient = ""; amountText = ""; errorMessage = nil
    return transactionID
}
What it does
  • Validator checks the rules
  • Store records the transaction
  • ViewModel updates its state
  • Returns the ID
Navigation stays out
  • The router decides where the user goes
  • Review and confirm are separate user actions (3.4)
SAY

The text’s first submission method, condensed on the slide. Parse the amount, or set "Invalid amount". Validate with PaymentValidator against the store’s balance, or set "Payment validation failed". Ask the store to record the demo payment, or set "Unable to record payment". On success clear the form and the error, and return the transaction ID.

SAY

It coordinates the workflow: the validator checks the rules, the store records the transaction, the ViewModel updates its presentation state, and it returns the ID so the caller can coordinate navigation. Click: navigation deliberately stays outside the ViewModel; the router remains responsible for where the user goes.

SAY

Click: but remember Lesson 3.4: Review and Confirm are two different user actions. One method that validates and executes at once doesn’t match the flow.

SAY

If the ViewModel stores a closure that captures the ViewModel strongly, the ViewModel owns the closure and the closure owns the ViewModel: neither can be released. A weak capture breaks the cycle: the closure holds viewModel weakly and calls it optionally.

SAY

Click: we ran both on the Mac with an @MainActor @Observable class that prints its lifecycle. The strong version initialized, ran its action, and when the function ended, no deinit: leaked. The weak version initialized, ran, and deinitialized as soon as the function ended.

SAY

Click: this is why Unit 1 studied ARC, strong and weak references and escaping closures, Lesson 1.8. SwiftUI does not eliminate reference-cycle risks in reference-type models.
