Not automatic

SAY

Swift’s access levels: private, the enclosing declaration and its extensions in the same file; fileprivate, the source file; internal, the whole module, and the default; package, the whole Swift package; public, usable from other modules; open, which additionally allows subclassing and overriding from other modules for eligible classes.

SAY

The text’s example makes PaymentAmount and its paise property public, visible to importing modules. Click: but a public type does not make every initializer or member public; the public API must be designed deliberately. We will see the compiler insist on this.

SAY

Click through the simplified module build, conceptual: the Swift sources; the compiler parses and type-checks the whole module; it emits a module interface exposing declarations to importers; compiled code for linking; and the app links the modules it needs, with resources. Conceptual: details depend on build settings.

Part 5 · Cross-module access control (sections 11–12, 17–18)

The compiler checks the public contract

NPayDomain/AccountRepository.swift (section 17, condensed)
public struct PaymentRecord: Identifiable, Sendable {
    public let id: UUID
    public let recipient: String
    public let amountPaise: Int
    public let createdAt: Date

    public init(id: UUID, recipient: String,
                amountPaise: Int, createdAt: Date) {
        self.id = id
        self.recipient = recipient
        self.amountPaise = amountPaise
        self.createdAt = createdAt
    }
}

public protocol AccountRepository: Sendable {
    func fetchSnapshot() async throws -> AccountSnapshot
    func recordPayment(recipient: String, amountPaise: Int)
        async throws -> PaymentRecord
}
violations.sh (ours), swift build

no explicit public init on PaymentRecord:
 NPayData: 'PaymentRecord' initializer is inaccessible
 due to 'internal' protection level

PaymentRecord not public:
 NPayDomain itself: property / initializer / method
 cannot be declared public because its type uses
 an internal type

Learned
  • Memberwise inits stay internal: write public ones
  • Public API can’t expose internal types
SAY

Once the domain moves into NPayDomain, every type and requirement used across the boundary must be public, and the text adds explicit public initializers. PaymentRecord gets a public init; AccountSnapshot too; the protocol’s requirements are public through the protocol. NPayData then imports NPayDomain and declares public actor InMemoryAccountRepository with a public init and public methods.

SAY

Click: we broke it on purpose, with a script of ours. Remove PaymentRecord’s explicit public init: NPayData fails, "PaymentRecord initializer is inaccessible due to internal protection level": a public struct’s synthesized memberwise initializer is not public, the common surprise when extracting code. Remove public from PaymentRecord itself: the text expected the app to fail, but the domain module fails first, because its own public snapshot, protocol and initializer use the now-internal type.

SAY

Click: so module boundaries turn architectural intentions into compiler-checked constraints: nobody can reach an internal detail from another module by accident.

Part 6 · Dependency direction across modules (sections 16, 19–20)

Contracts in the domain; implementations depend on them

violations.sh (ours)

NPayDomain imports NPayData (no dependency declared):
 error: no such module 'NPayData'

NPayDomain depends on NPayData (a cycle):
 error: cyclic dependency declaration found:
 NPayData -> NPayDomain -> NPayData

How to avoid it
  • AccountRepository in NPayDomain
  • InMemoryAccountRepository in NPayData
  • The app composes them
Section 19: the composition root
import SwiftUI
import NPayDomain
import NPayData

@MainActor
final class NPayDependencies {
    let repository: any AccountRepository

    init() {
        repository = InMemoryAccountRepository(
            initialBalancePaise: 2_500_000)
    }
}
From NPay’s app module (simulator)

NPayDomain use case over NPayData repository:
recorded 150050; balance 2349950

SAY

App to Data to Domain is fine. A cycle, domain depending on data while data depends on domain, is not, and SwiftPM requires an acyclic target graph. We tried both of the text’s violations. Importing NPayData inside NPayDomain without declaring the dependency: "no such module NPayData". Declaring the dependency, making a cycle: "cyclic dependency declaration found: NPayData, NPayDomain, NPayData". The package refuses to build.

SAY

Click: the way out is dependency inversion across modules: the AccountRepository protocol in NPayDomain, the actor in NPayData conforming to it, and the app composing them. The domain stays independent of infrastructure. Click: Section 19’s composition root imports both modules and creates one InMemoryAccountRepository behind the protocol; later, an API-backed repository replaces it while the contract stays.

SAY

Click: we ran that composition from inside NPay’s app module: the NPayDomain use case, on an NPayData repository: 150,050 paise recorded, balance 2,349,950. NPay’s own screens still use our adapter over NPayStore, which now conforms to the imported protocol, so Home and History keep their source of truth.

Part 7 · Not 20 packages; feature vs shared modules (sections 13–14, 21)

Modularity has a cost

StageArchitecture
CurrentOne app target, feature folders
NextExtract stable domain code: NPayDomain
LaterExtract data implementations: NPayData
Larger appFeature modules where justified
Every module costs
  • Public API decisions
  • Dependency and build configuration
  • Integration overhead
Shared vs feature
  • NPayDesignSystem: NPayButton, NPayCard, NPayTheme
  • PaymentReviewSheet stays in Payments
  • Extract stable, meaningful contracts
  • Modularize to solve a real ownership, dependency or build problem
SAY

Why not twenty packages immediately? Every module brings public API decisions, dependency management, build configuration and integration overhead; for a small app, too many modules make development harder. NPay evolves in stages: one target with feature folders now; extract the stable domain; later the data implementations; feature modules only when the app is large enough to justify them. Click: we just felt that cost: one missing platform line, one missing public init.

SAY

Click: with several teams owning Payments, History and Profile, feature modules can mark ownership. Shared code goes in shared modules, carefully: a design system with NPayButton, NPayCard and NPayTheme; but a payment-specific PaymentReviewSheet stays in Payments. Don’t move code into a shared module just because two files use it.

SAY

Click: the text’s strategy chooser: a small app, one target with feature folders; growing and multi-team apps, more modules. Modularization should solve a real maintenance, ownership, dependency or build problem; more modules is not better architecture by itself.

Lesson 4.8 · Recap

What to remember

Folders organize; modules enforce
31 files, still NPay.*; package types: NPayDomain.*

public is a deliberate contract
memberwise inits stay internal; public API can’t use internal types

Acyclic and inverted
SwiftPM rejected the cycle; the domain imports nothing of ours

SAY

Three things to remember. Feature folders make NPay navigable, but every file is still in the NPay module: only a target or package creates a module. Across a module boundary, public is a deliberate contract: the compiler rejected a missing public initializer and a public API built on an internal type. And the module graph must be acyclic, with the domain at the centre: contracts in NPayDomain, implementations in NPayData depending on it, and the app composing both, which SwiftPM enforced when we tried to break it.
