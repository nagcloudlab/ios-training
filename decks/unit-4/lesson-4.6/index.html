Part 2 · PaymentAmount and PaymentRecipient (sections 3–4)

Throwing initializers guard the invariants

Domain value objects (PaymentDomainError: invalidAmount, invalidRecipient, insufficientBalance, limitExceeded)
struct PaymentAmount: Equatable, Sendable {
    let paise: Int

    init(paise: Int) throws {
        guard paise > 0 else {
            throw PaymentDomainError.invalidAmount
        }
        self.paise = paise
    }
}

struct PaymentRecipient: Equatable, Sendable {
    let identifier: String

    init(_ identifier: String) throws {
        let trimmed = identifier.trimmingCharacters(
            in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty else {
            throw PaymentDomainError.invalidRecipient
        }
        self.identifier = trimmed
    }
}
Mac run, the text’s code

PaymentAmount(paise: 150050) → 150050
PaymentAmount(paise: 0)    → throws invalidAmount
PaymentAmount(paise: -100) → throws invalidAmount
PaymentRecipient(" ravi@npay ") → "ravi@npay"
PaymentRecipient("   ")    → throws invalidRecipient

Invariant
  • A PaymentAmount is always positive
  • A PaymentRecipient is never blank
  • Positive can still exceed the balance or a limit
SAY

Until now Money was a formatting utility. PaymentAmount, named so it does not clash with Money, wraps paise, and its throwing initializer refuses anything not positive. PaymentRecipient trims the identifier and refuses an empty one. Both throw PaymentDomainError, whose four cases are invalid amount, invalid recipient, insufficient balance and limit exceeded.

SAY

Click: run on the Mac: 150,050 is accepted; zero and minus a hundred throw invalidAmount; "ravi@npay" with spaces is trimmed; blanks throw invalidRecipient. Click: these are domain invariants: if you hold a PaymentAmount, it is positive; if you hold a PaymentRecipient, it is not blank. A value object makes invalid states hard to represent.

SAY

Click: but one invariant is not every rule: a positive amount can still exceed the balance or a limit. And real UPI recipient validation needs far more, with authoritative verification; NPay stays a simulation.

Part 3 · What is a use case? Build one (sections 6–7)

SendPaymentUseCase, version 1

Section 7
struct SendPaymentUseCase {
    let repository: any AccountRepository

    func execute(_ command: SendPaymentCommand)
        async throws -> PaymentRecord {
        let snapshot = try await repository.fetchSnapshot()

        guard command.amount.paise <= snapshot.balancePaise else {
            throw PaymentDomainError.insufficientBalance
        }

        let perPaymentLimitPaise = 100_000_00
        guard command.amount.paise <= perPaymentLimitPaise else {
            throw PaymentDomainError.limitExceeded
        }

        return try await repository.recordPayment(
            recipient: command.recipient.identifier,
            amountPaise: command.amount.paise)
    }
}
A use case is
  • An operation the app supports
  • Not a screen, a table or a request
Steps
  • Snapshot; check balance
  • Check a ₹1,00,000 limit (illustrative)
  • Record; return the record
  • The balance can change before recordPayment
  • The repository must check again
SAY

A use case represents an operation the application supports: SendPayment, FetchBalance, FetchTransactionHistory. It coordinates the rules and dependencies the operation needs. It is not a screen, not a database table, not necessarily a network request; sending money stays meaningful even if SwiftUI is replaced.

SAY

Click: version one uses Lesson 4.5’s repository. It fetches a snapshot, rejects the payment if the amount exceeds the balance, applies an illustrative per-payment limit of ₹1,00,000, which is not a statement of actual UPI limits, then asks the repository to record the payment and returns the record.

SAY

Click: the text’s concurrency detail: the early balance check expresses the rule but is not the final guarantee; another operation can change the balance between fetchSnapshot and recordPayment. That is why the repository revalidates atomically. Part 6 measures exactly this.

Part 3 · Why not every rule in the repository? (section 8)

Policy in the use case; integrity at the data

RuleUse caseRepository
Amount positiveDomain value objectDefensive validation
Recipient non-emptyDomain value objectDefensive validation
Per-payment limitUse-case policyMay also need enforcement
Sufficient balancePreliminary checkAtomic final check
Record transactionRequests the operationPerforms it
Different jobs
  • Use case: application policy
  • Repository: data integrity, data operations
  • Authoritative limits and balance checks: the trusted backend
SAY

Repositories and use cases have different responsibilities: the use case represents application policy; the repository protects data integrity and performs data operations. Some rules are enforced at both boundaries for different reasons.

SAY

The text’s table: positive amount and non-empty recipient are guaranteed by the value objects, and validated defensively again by the repository. The per-payment limit is use-case policy, though authoritative enforcement may also be required. Sufficient balance: a preliminary check in the use case, the atomic final check in the repository. Recording: the use case requests it, the repository performs it.

SAY

Click: different jobs. Click: and for a real payment system, authoritative limits and balance checks belong on the trusted backend; the exact division depends on the domain and the backend contract.

Part 5 · What is the Dependency Rule? (sections 10–11)

Infrastructure depends on the domain, not the reverse

Arrows: source-code dependencies. Calls still flow out to infrastructure, through domain-owned abstractions.

Dependency inversion, in practice
  • The use case depends on the protocol
  • The actor implements it
A protocol for the use case?
  • Not now: a struct is fine
  • Add one for ViewModel tests if needed
  • Abstractions where they earn it
  • Not layers to imitate a diagram
SAY

Clean Architecture says source-code dependencies should point toward the application’s core policies. Presentation, SwiftUI and the ViewModel, depends on the application layer, SendPaymentUseCase, which depends on the domain: click: the value objects and the repository contract. The domain does not depend on SwiftUI, URLSession or a database framework.

SAY

Click: and infrastructure, InMemoryAccountRepository, points up: it implements the domain’s protocol. At runtime the use case still calls outward into the actor, but through an abstraction the domain owns. Click: that is dependency inversion in practice, Lesson 4.4’s principle.

SAY

Click: do we need a protocol for the use case too? Not yet: a concrete struct is fine; if ViewModel tests need to mock it, introduce one then. Click: use abstractions where they give meaningful testability or replaceability, not to imitate a diagram.

Part 6 · Improve our use-case design (section 18)

Static policy here; the balance at the repository

PaymentPolicy and SendPaymentUseCase (replaces version 1)
struct PaymentPolicy: Sendable {
    let maximumPerPaymentPaise: Int

    func validate(_ amount: PaymentAmount) throws {
        guard amount.paise <= maximumPerPaymentPaise else {
            throw PaymentDomainError.limitExceeded
        }
    }
}

struct SendPaymentUseCase {
    let repository: any AccountRepository
    let policy: PaymentPolicy

    func execute(_ command: SendPaymentCommand)
        async throws -> PaymentRecord {
        try policy.validate(command.amount)

        return try await repository.recordPayment(
            recipient: command.recipient.identifier,
            amountPaise: command.amount.paise)
    }
}
What changed
  • No snapshot, no early balance check
  • Policy first, then the atomic mutation
Why better
  • No stale-balance decision
  • The policy is testable alone (section 22)
Demo configuration
PaymentPolicy(maximumPerPaymentPaise: 10_000_000)
// ₹1,00,000, illustrative
SAY

Version one did an early balance check from a snapshot and then recorded, duplicating validation and assuming fresh data. Version two separates static policy from the authoritative balance check. PaymentPolicy holds a maximum per payment and validates an amount against it. SendPaymentUseCase now takes the repository and a policy: it validates the policy, then delegates the atomic account mutation.

SAY

Click: why better: the use case no longer makes a balance decision from a possibly stale snapshot, and the policy can be tested independently, as Section 22 did. Click: the demo policy is 10,000,000 paise, ₹1,00,000, purely illustrative. This replaces version one under the same name.

Part 7 · ViewModel and composition root (sections 12–13, 19–20)

The ViewModel delegates the operation

PaymentViewModel (section 20’s submission)
private let sendPayment: SendPaymentUseCase

init(sendPayment: SendPaymentUseCase) {
    self.sendPayment = sendPayment
}

func submit(_ command: SendPaymentCommand) async -> PaymentRecord? {
    guard !isSubmitting else { return nil }
    isSubmitting = true
    defer { isSubmitting = false }
    do {
        let result = try await sendPayment.execute(command)
        recipient = ""; amountText = ""; errorMessage = nil
        return result
    } catch {
        errorMessage = "Unable to complete demo payment"
        return nil
    }
}
NPayFactory (section 19)
@MainActor
enum NPayFactory {
    static func makePaymentViewModel(
        repository: any AccountRepository
    ) -> PaymentViewModel {
        let policy = PaymentPolicy(
            maximumPerPaymentPaise: 10_000_000)
        let useCase = SendPaymentUseCase(
            repository: repository, policy: policy)
        return PaymentViewModel(sendPayment: useCase)
    }
}
Section 12’s version
  • Parsed the fields itself; specific messages
  • Section 20’s: one generic message
SAY

Section 12 replaces the PaymentService dependency with the use case: the ViewModel no longer calls the repository, it delegates the operation. Its first submit parsed the form fields into a command itself and mapped insufficientBalance and limitExceeded to specific messages. Section 20 replaces that with submit taking a command, on the slide: guard against a double submit, execute the use case, clear the form, or set "Unable to complete demo payment".

SAY

Click: the composition root, Section 19: the factory creates the policy and the use case from a repository and hands the use case to the ViewModel, which constructs neither.

SAY

Click: one trade-off to notice: Section 12 gave specific messages; Section 20’s version shows one message for every failure: we measured insufficient balance and over-limit both giving "Unable to complete demo payment". Lesson 4.7 models those states properly.
