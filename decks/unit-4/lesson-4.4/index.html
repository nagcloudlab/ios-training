What exactly is it?

Part 1 · What is dependency injection? (section 2)

Supply the dependency from outside

Without injection
final class PaymentViewModel {
    private let service = DemoPaymentService()
}
Coupled
  • The ViewModel creates its dependency
  • Always DemoPaymentService
With injection
final class PaymentViewModel {
    private let service: PaymentService

    init(service: PaymentService) {
        self.service = service
    }
}
Decoupled
  • The ViewModel receives it
  • The caller chooses the implementation
SAY

A dependency is an object or capability another component needs to do its work. Dependency injection means supplying it from outside rather than constructing it inside. Without injection, the ViewModel creates a DemoPaymentService itself: it is coupled to that one class.

SAY

Click: with injection, the ViewModel stores a PaymentService and receives it in its initializer. Click: the caller decides which implementation to supply.

SAY

Nothing new in Swift: protocols, initializer parameters and reference types from Unit 1. Dependency injection is an architectural pattern, not a SwiftUI feature; Lesson 4.2’s init(store:) was already a small case of it.

The contract.

Part 2 · Our first dependency contract (section 3)

A request in, a receipt out

PaymentService.swift (import Foundation)
struct PaymentRequest {
    let recipient: String
    let amountPaise: Int
}

struct PaymentReceipt {
    let transactionID: UUID
    let recipient: String
    let amountPaise: Int
}

@MainActor
protocol PaymentService {
    func send(_ request: PaymentRequest) async throws
        -> PaymentReceipt
}
Three types
  • PaymentRequest: validated input
  • PaymentReceipt: the result
  • PaymentService: behaviour, no implementation
async throws
  • A real payment waits and can fail
  • @MainActor on the protocol, for this local lesson
  • Revisited with networking
SAY

Create PaymentService.swift. PaymentRequest represents the validated input we intend to submit: recipient and amount in paise. PaymentReceipt is the result after the operation: the transaction ID, recipient and amount. PaymentService defines the behaviour, send a request and get a receipt, without saying how.

SAY

Click: send is async throws because a future implementation will involve asynchronous work and failures, a network call for instance, even though today’s demo is immediate.

SAY

Click: the @MainActor on the protocol is a deliberate simplification for this local lesson; we revisit concurrency boundaries when networking is introduced in Unit 5.

Part 2 · The demo implementation (section 4)

It receives the shared store; it owns no balance

DemoPaymentService
enum PaymentServiceError: Error {
    case rejected
}

@MainActor
final class DemoPaymentService: PaymentService {
    private let store: NPayStore

    init(store: NPayStore) {
        self.store = store
    }

    func send(
        _ request: PaymentRequest
    ) async throws -> PaymentReceipt {
        guard let id = store.recordDemoPayment(
            recipient: request.recipient,
            amountPaise: request.amountPaise
        ) else {
            throw PaymentServiceError.rejected
        }
        return PaymentReceipt(
            transactionID: id,
            recipient: request.recipient,
            amountPaise: request.amountPaise)
    }
}
What it does
  • Calls recordDemoPayment
  • nil → throws .rejected
  • An ID → returns a receipt
Mac, NPay’s real NPayStore

send ₹1,500.50 → receipt
store: 2,349,950 paise, 4 transactions

  • The same store as Home and History
SAY

The demo implementation. A small error enum with one case, rejected. DemoPaymentService receives an NPayStore in its initializer, and send asks the store to record the demo payment: if the store returns nil, it throws rejected; otherwise it returns a receipt with the store’s transaction ID. It relies on recordDemoPayment returning an optional UUID, which ours does.

SAY

Click: we compiled the text’s code on the Mac together with NPay’s real NPayStore, Money and PaymentValidator: sending ₹1,500.50 produced a receipt and the store went to 2,349,950 paise with four transactions.

SAY

Click: what matters: DemoPaymentService does not own a new balance. It receives the same store Home and History use. A single source of truth, the lesson from 3.1 and 4.2 again.

Two terms that sound alike.

Part 3 · Injection versus inversion (section 15)

A technique and a principle

What it isSays
Dependency InjectionA techniqueSupply dependencies from outside
Dependency Inversion PrincipleA design principlePolicy and details both depend on abstractions
Injection without inversion
  • Inject a concrete class: no protocol
  • init(store: NPayStore) in 4.2
Inversion undermined
  • A protocol exists…
  • …but the consumer still constructs the concrete type
  • Often combined; neither guarantees the other
SAY

Dependency injection is a technique: supplying dependencies to a component. The dependency inversion principle is a design principle: high-level policy, here the payment ViewModel, should not depend directly on low-level details like DemoPaymentService; both should depend on an abstraction, the PaymentService protocol. In the text’s before-and-after diagram, the arrows are source-code dependencies and conformance, not the runtime call sequence.

SAY

Click: you can inject a concrete class without any protocol: Lesson 4.2’s init(store: NPayStore) was injection without inversion. Click: and you can define an abstraction yet still construct the concrete implementation inside the consumer, undermining the separation.

SAY

Click: they often work together, but neither automatically guarantees the other.

Part 4 · Refactor PaymentViewModel (section 6)

No DemoPaymentService, no NPayStore

PaymentViewModel.submit() (condensed)
private let service: any PaymentService   // init(service:)
func submit() async -> PaymentReceipt? {
    guard !isSubmitting else { return nil }
    let trimmed = recipient.trimmingCharacters(
        in: .whitespacesAndNewlines)
    guard let amount = Money.parsePaise(amountText),
          amount > 0, !trimmed.isEmpty else {
        errorMessage = "Check your payment details."
        return nil
    }
    let request = PaymentRequest(recipient: trimmed,
                                 amountPaise: amount)
    isSubmitting = true
    defer { isSubmitting = false }
    do {
        let receipt = try await service.send(request)
        recipient = ""; amountText = ""; errorMessage = nil
        return receipt
    } catch {
        errorMessage = "Payment could not be completed."
        return nil
    }
}
submit()
  • Guard, parse, check
  • Send through the service
  • Clear the form, or set an error
The balance check?
  • Not here: the service enforces it
  • Demo, ₹30,000 → “Payment could not be completed.”
  • Review is reconnected in Part 7
SAY

The ViewModel keeps the input properties and gains isSubmitting. Its only dependency is now any PaymentService, received in the initializer. submit() refuses a second submit while one is running; parses the amount and checks the recipient, setting "Check your payment details." if they fail; builds a PaymentRequest with the trimmed recipient; sets isSubmitting, with a defer to clear it; sends through the service; on success clears the form, on failure sets "Payment could not be completed."

SAY

The ViewModel no longer knows DemoPaymentService or NPayStore. Click: the service enforces the balance at execution time. On the Mac, ₹30,000 against a ₹25,000 balance came back as the generic "Payment could not be completed.": the store refused it and the demo service threw rejected. Lesson 4.7’s structured UI state can say why.

SAY

Click: the text is explicit that this is a standalone submission experiment; the review sheet and confirmation are reconnected during integration, which we did, Part 7.

SAY

PaymentService is a protocol. any PaymentService stores a value whose concrete type conforms to it: DemoPaymentService or MockPaymentService. The any keyword makes existential use explicit. Click: is a protocol required for dependency injection? No: you can inject concrete types. Protocols pay off when multiple implementations, testing or an abstraction boundary justify them; a protocol for every class adds complexity.

SAY

Click: Section 16 asks whether any PaymentService creates a new service instance. We checked on the Mac: reading the ViewModel’s stored service back with Mirror gives the very same object, identity true. SAY

Click: assigning a class instance to an existential-typed property does not construct a new service object.

Part 5 · A mock service, and one call three ways (sections 8–9)

MockPaymentService
@MainActor
final class MockPaymentService: PaymentService {

    var shouldFail = false
    private(set) var requests: [PaymentRequest] = []

    func send(
        _ request: PaymentRequest
    ) async throws -> PaymentReceipt {
        requests.append(request)
        if shouldFail {
            throw PaymentServiceError.rejected
        }
        return PaymentReceipt(
            transactionID: UUID(),
            recipient: request.recipient,
            amountPaise: request.amountPaise)
    }
}

Part 6 · The composition root (sections 10–11, 19)

One factory builds the feature

App/NPayFactory.swift
@MainActor
enum NPayFactory {

    static func makePaymentViewModel(
        store: NPayStore
    ) -> PaymentViewModel {

        let service = DemoPaymentService(store: store)

        return PaymentViewModel(service: service)
    }
}
A framework?
  • Not yet: a factory is enough
  • Containers can hide ownership
Constructor injectionEnvironment injection
Passed in the initializerSupplied through the view hierarchy
Explicit at the call siteConvenient for descendants
ViewModels, services, repositoriesShared UI context
Required dependencies are visibleNeeds deliberate setup
  • Constructor: services, repositories
  • Environment: presentation preferences (3.9)
SAY

Where are dependencies assembled? In a composition root. NPayFactory centralizes construction: makePaymentViewModel takes the shared store, builds a DemoPaymentService with it, and returns a ViewModel with that service. NPay’s root owns the store; a payment feature root owns the ViewModel in @State, so it is not recreated in body and the draft survives tab changes, Lessons 4.2 and 4.3.

SAY

Click: should NPay use a dependency injection framework? Not yet: a few shared dependencies, a simple factory. A container helps when construction rules, scopes and graphs grow complex, but introduced too early it hides the ownership and initialization we are trying to master.

SAY

Click: two injection styles. Constructor injection passes the dependency in the initializer, explicit at the call site, good for ViewModels and services, required dependencies visible. Environment injection supplies it through the view hierarchy, convenient for descendants, good for shared UI context, but it needs deliberate setup: Lesson 3.9 showed a missing environment object crashing. Click: NPay uses constructor injection for payment services and repositories, the environment for presentation preferences. Neither manages persistence or security for you.

Should everything get a protocol?

Part 7 · Useful boundaries; NPay after 4.4 (sections 20–21)

Protocols where they earn their place

Use a protocol for
  • Swapping a payment implementation
  • Isolating infrastructure
  • Testing important behaviour
Prefer a concrete type for
  • A simple, stable formatter
  • Anything with one implementation
  • A backend behind the same contract
SAY

NPay after this lesson: the root composes shared dependencies; PaymentsScreen presents; PaymentViewModel holds form state and coordinates submission; click: it depends on the PaymentService protocol; DemoPaymentService implements it with the shared store. The ViewModel is independent of the concrete demo implementation.

SAY

Click: but abstractions are not free: every protocol is a contract to maintain. Use one where it provides a meaningful boundary: replacing a payment implementation, isolating infrastructure, testing important behaviour. Click: for a simple, stable formatter with one implementation, a protocol, factory, mock and container add more complexity than value. Good architecture is about useful boundaries, not the number of protocols.

SAY

Click: in Unit 5 a backend arrives behind this same contract, without rewriting the SwiftUI payment screen.

What to remember

Receive, don’t create
the ViewModel holds any PaymentService

Mocks make tests deterministic
success and failure, no store, no network

SAY

Three things to remember. Dependency injection means a component receives what it needs instead of creating it: PaymentViewModel now holds any PaymentService and never mentions the store or the demo class, and dependency inversion is the principle that makes the abstraction worth having. Because of that, a mock can drive success and failure deterministically, on the Mac or inside NPay, without changing a line of the ViewModel. And one factory assembles the objects, with each lifetime matching its job: the store application-wide, the ViewModel per feature.
