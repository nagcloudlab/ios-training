Part 2 · Refresh after a payment (section 9, question 6)

A failed refresh is not a failed payment

Ours
// DashboardViewModel (ours)
var refreshFailed = false

func reload() async {
    do {
        try await refresh()
        refreshFailed = false
    } catch {
        refreshFailed = true      // the payment stays a success
    }
}

// PaymentsScreen, after Confirm succeeds
pendingSuccessID = record.id
self.review = nil
await onPaymentRecorded()     // { await dashboard.reload() }
NPayAppTests (ours)

✔ dashboardShowsThePaymentAfterRefresh()
 before reload: 2500000; after: 2349950
✔ failedRefreshKeepsTheLastSnapshot()
 refreshFailed true; snapshot untouched

  • Preserve the success; report the refresh separately
SAY

The text’s assessment asks what should happen after a confirmed payment when the dashboard refresh fails: preserve the success and report the refresh failure separately. Our DashboardViewModel gets a reload that does exactly that: it refreshes, and on error sets refreshFailed instead of throwing at the payment. The Payments screen, on success, stores the ID, dismisses the sheet and awaits the dashboard reload.

SAY

Click: two tests of ours. One pays through the real use case and shows the dashboard is a snapshot: still 2,500,000 until reload, then 2,349,950 with "Sent to ravi@npay" first. The other uses a repository whose snapshot always fails: reload sets refreshFailed and leaves the last snapshot untouched.

SAY

Click: the rule from Lesson 4.5, now in the app: never interpret a failed UI refresh as proof the payment failed.

Three isolation domains, one call

SAY

Left, the review sheet showing the command; right, Home after the payment, ₹23,499.50 and the new row on top. The call that did the work: let record equals try await sendPayment.execute(command).

SAY

Click: it crosses several boundaries: the ViewModel is main-actor isolated; the use case makes an asynchronous call into the repository; the repository actor protects its mutable account state; when it completes, the ViewModel resumes on the main actor and updates its state. await marks a possible suspension; it does not guarantee a new thread. Actor isolation controls access; the concurrency runtime schedules tasks.

SAY

Click: we slowed the repository by three seconds through a debug-only hook to watch it: 0.8 seconds in, "Processing demo payment...", Confirm disabled, the dashboard still on the old snapshot; then Payment Recorded and the dashboard at 2,349,950. This is the foundation for networking and concurrency in later units.

Exactly what later units address

Even with MVVM and Clean Architecture, the demo has limits.
