protocol SendPaymentExecuting: Sendable {

// PaymentViewModel

Part 6 · A controllable mock; the duplicate test (sections 18–19)

The test decides when the payment completes

Section 18
actor SuspendedPaymentUseCase: SendPaymentExecuting {
    private var continuation:
        CheckedContinuation<PaymentRecord, Error>?
    private var invocationCount = 0

    func execute(_ command: SendPaymentCommand)
        async throws -> PaymentRecord {
        invocationCount += 1
        return try await withCheckedThrowingContinuation {
            continuation = $0
        }
    }

    func calls() -> Int { invocationCount }

    func succeed() {
        continuation?.resume(returning: PaymentRecord(
            id: UUID(), recipient: "ravi@npay",
            amountPaise: 150_050, createdAt: .now))
        continuation = nil
    }
}
Section 19’s test
  • Start submit #1; wait until the mock is called
  • Submit #2: expect a failure
  • Expect calls() == 1; then succeed()
  • #1 ends in success
swift test

✔ duplicateSubmissionIsRejected() (< 1 s)

  • Resume every continuation exactly once
  • Bound every wait
SAY

To test duplicate submission we need the first payment to stay in flight. SuspendedPaymentUseCase, an actor, counts calls and, inside withCheckedThrowingContinuation, stores the continuation instead of finishing: the ViewModel stays submitting until the test calls succeed, which resumes it with a record.

SAY

Section 19’s test: start the first submit in a Task; yield until the mock has been called once; submit again and expect a failure; expect calls to still be one; then succeed and expect the first submission to end in success. Click: it passes in well under a second, with no sleeps.

SAY

Click: the text’s cautions: every checked continuation must be resumed exactly once, and the polling loop is a teaching shortcut; a robust suite bounds its waits so a regression cannot hang the run. Let’s see what that regression looks like.

SAY

We removed the isBusy guard from a copy of the ViewModel and ran Section 19’s test. It produced no result at all; we stopped it after forty seconds. With the guard it passes in under a second.

SAY

Click: why it hung: without the guard, the second submit also reached the mock; its continuation replaced the first one’s, so the first was never resumed, and the test’s await on the first task waits forever. A regression became a hang, not a failure: exactly why the text asks for bounded waits, for example a Swift Testing time-limit trait, and for resuming every continuation exactly once.

SAY

Click: Section 20’s table: an arbitrary sleep is timing-dependent, wasteful on fast machines and too short on slow ones; controlled mock completion is deterministic; expectations explicitly await an event; an injected clock suits retry and debounce tests later. Click: control completion, bound the wait, never sleep and hope. The text’s eight-stage lifecycle stepper was shared at stage one; this run is its sharpest lesson.

What to remember

Every layer, its own tests
3 XCTest + 16 Swift Testing, all passing

Mocks for isolation, real chains for contracts
the real chain checks the exact message

Deterministic async; meaningful assertions
no guard: a hang; no boundary test: a hidden bug at 92%

SAY

Three things to remember. Each layer gets tests at its own boundary: domain values and policies, the actor repository including concurrency, the use case, and the ViewModel, which we tested on the app’s own source. Mocks isolate the ViewModel, while a real-chain test checks the contract between layers, which mocks cannot. And async tests must control completion and bound their waits, and assertions must target boundaries: removing a guard turned a test into a hang, and a planted off-by-one bug survived at 92% coverage until the at-limit assertion caught it.
