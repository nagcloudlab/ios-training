Part 3 · Sandbox · conceptual

Explore application isolation

Apps can still exchange data through App Groups, extensions, document pickers and system-mediated services.

Widgets and other extensions run as separate sandboxed processes; they share data with the app through an App Group (Unit 10 · 10.9).

SAY

Each app normally has its own private data container. Click through what ShopEasy tries: its own files, allowed; NPay’s private files directly, blocked; a document the user shares through an approved system interface, allowed because the system mediates it.

SAY

The sandbox does not mean apps can never exchange data. App Groups, extensions, document pickers and system-mediated services allow controlled communication. The important word is authorized.

SAY

One more boundary to know about: a widget or other extension is not part of the app process. It runs as its own sandboxed process and shares data with the app through an App Group. Unit 10, lesson 10.9, builds one.

Entitlements

Signed declarations of capability

SAY

An entitlement is a signed declaration of a capability granted to an app, for example access to an App Group or certain Apple services.

CONNECT

Here is how it flows.

Part 4 · Entitlements · conceptual

From declaration to enforcement

An entitlement is not a boolean an app sets at runtime. It must be configured, signed and accepted by the platform.
SAY

NPay declares a capability, such as an App Group. It is part of the signed entitlements, and the system enforces it.

SAY

An entitlement is not something an app can switch on at runtime to grab any privilege. The capability must be configured, signed and accepted by the platform.

CONNECT

Entitlements are often confused with permissions. Compare them.

Part 4 · Comparison

Entitlements vs privacy permissions

Some capabilities need both: an entitlement in the signature and the user’s permission at run time.
SAY

Top lane, an entitlement: it declares an app capability, is configured at build or signing time, becomes part of the signature, and is enforced by platform services. App Groups is an example.

SAY

Bottom lane, a privacy permission: it authorizes access to a privacy-sensitive resource. The app asks, the user chooses at run time, and privacy and system APIs enforce the choice. The camera is an example.

SAY

Some capabilities need both mechanisms working together.

Part 5 · Camera authorization · conceptual

Scanning a cheque

Without NSCameraUsageDescription in Info.plist, the app is terminated when it asks for the camera. Explain why before the prompt appears.
SAY

The user taps Scan Cheque; NPay requests camera authorization; the system shows its prompt. Until the user decides, the state is not determined. Click: Allow, and NPay can use the camera. Click: Don’t Allow. The system shows its prompt only once, so NPay cannot ask again: it must offer another way to continue, such as uploading a photo, and can only direct the user to Settings to change the decision.

SAY

The app must also declare a privacy usage description, NSCameraUsageDescription, in Info.plist. If it is missing, iOS terminates the app the moment it asks for the camera. The user should understand why access is requested before the system prompt appears. Later, the privacy manifest declares what data the app collects; Unit 11, lesson 11.8, covers it.

ASK

Can NPay secretly activate the camera, as we asked at the start?

EXPECT

No. Camera access goes through the system’s privacy authorization, with the user’s choice.

Part 6 · Code signing · conceptual

From build to trusted execution

A valid signature establishes code identity and integrity. It is not proof that the app’s logic is secure.
SAY

Click through: the developer builds the app; the app is signed, with a signature and metadata protecting its integrity; iOS validates execution requirements through platform policies and signing checks; and the app runs under restrictions. Signing does not bypass the sandbox or privacy controls.

ASK

Does a valid code signature guarantee the app has no security vulnerabilities?

EXPECT

No. Signing establishes identity and integrity under platform policy. It says nothing about whether the app’s logic is secure.

Compare the two common options.

Part 7 · Storage choice · conceptual

UserDefaults vs Keychain

UserDefaults is a plain preferences file: never put a token there. Keychain items also choose when they can be read, e.g. only while the device is unlocked.
ASK

After sign-in, NPay has a token. Where should it go: UserDefaults or the Keychain?

EXPECT

Most say the Keychain; ask why not UserDefaults.

SAY

Click: UserDefaults is for preferences and lightweight settings, such as the selected theme or whether onboarding is done. It is stored as a preferences file inside NPay’s container, so it is not a place for credentials.

SAY

Click: the Keychain is a database managed by iOS, outside the app’s container, that encrypts each item. It is designed for credentials and small secrets: authentication tokens and cryptographic key references.

SAY

Keychain items also carry an accessibility policy, for example an item intended to be readable only while the device is unlocked. The right policy depends on the app’s security and background-access needs; Unit 07, lesson 7.3, goes deeper.

CONNECT

Part 8 · Secure Enclave · conceptual

Isolated security operations

Keychain items are not stored in the Secure Enclave. It protects the keys that encrypt them, and can create P-256 private keys that never leave it.
SAY

Click down: NPay calls the security frameworks, such as Keychain services, CryptoKit and LocalAuthentication.

SAY

Click: the Keychain items themselves live in an encrypted database. Click: the Secure Enclave is a separate hardware subsystem. It protects the keys used to encrypt Keychain items, and it can create P-256 private keys that never leave it; the app asks the Enclave to sign or decrypt with them.

SAY

The critical distinction: Keychain items are not stored inside the Secure Enclave. It is not a general-purpose database. Unit 07, lesson 7.5, uses it from CryptoKit.

Lesson 0.7 · Recap

What to remember

Sandboxeach app in its own container; sharing must be authorized
Signingidentity and integrity, not proof of safety
Keychainsecrets, encrypted with keys the Secure Enclave protects
SAY

Least privilege at every layer. The sandbox keeps NPay in its own container, enforced by the kernel. Entitlements and permissions grant specific capabilities. Signing proves identity and integrity, not safety. Secrets go in the Keychain, whose keys the Secure Enclave protects.
