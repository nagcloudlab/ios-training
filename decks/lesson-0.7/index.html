Part 4 · Entitlements · conceptual

From declaration to enforcement

An entitlement is not a boolean an app sets at runtime. It must be configured, signed and accepted by the platform.
SAY

NPay declares a capability, such as an App Group. It is part of the signed entitlements, and the system enforces it.

SAY

An entitlement is not something an app can switch on at runtime to grab any privilege. The capability must be configured, signed and accepted by the platform.

Entitlements are often confused with permissions. Compare them.

Part 4 · Comparison

Entitlements vs privacy permissions

EntitlementPrivacy permission
Declares an app capabilityAuthorizes access to privacy-sensitive resources
Usually configured at build or signing timeOften involves user choice at runtime
Example: App GroupsExample: camera access
Enforced by platform servicesEnforced by privacy and system APIs
Some capabilities also require runtime authorization. These mechanisms can work together.
SAY

An entitlement declares a capability, is usually configured at build or signing time, and is enforced by platform services; App Groups is an example. A privacy permission authorizes access to privacy-sensitive resources, often involves a user choice at runtime, and is enforced by privacy and system APIs; camera access is an example.

Part 6 · Code signing · conceptual

From build to trusted execution

A valid signature establishes code identity and integrity. It is not proof that the app’s logic is secure.
SAY

Click through: the developer builds the app; the app is signed, with a signature and metadata protecting its integrity; iOS validates execution requirements through platform policies and signing checks; and the app runs under restrictions. Signing does not bypass the sandbox or privacy controls.

ASK

Does a valid code signature guarantee the app has no security vulnerabilities?

EXPECT

No. Signing establishes identity and integrity under platform policy. It says nothing about whether the app’s logic is secure.

Part 7 · Storage choice

UserDefaults vs Keychain

UserDefaults

Application preferences and lightweight settings.

Examples: selected theme, onboarding completed.

Keychain

Sensitive credentials and small secret values.

Examples: authentication tokens, cryptographic key references.

Keychain items control when data can be accessed. A WhenUnlocked class is intended for use while the device is unlocked. Choose by security and background-access needs.
SAY

UserDefaults is for preferences and lightweight settings like the selected theme or whether onboarding is done. Storing sensitive credentials there is generally inappropriate. The Keychain is for credentials and small secrets: authentication tokens and cryptographic key references.

SAY

Keychain items support accessibility policies. An item with a WhenUnlocked class is intended to be accessible while the device is unlocked. The right policy depends on the app’s security and background-access requirements.

iOS Security
Architecture

Least privilege, enforced at every layer.

SAY

Recap: apps get only what they are authorized to use. Security comes in layers: app security, privacy permissions, sandbox and entitlements, code signing, and kernel and hardware protection. The sandbox isolates containers; entitlements and permissions grant specific capabilities; signing proves identity and integrity, not safety; secrets go in the Keychain; and the Secure Enclave protects particular keys.
