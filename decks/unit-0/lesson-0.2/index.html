How SwiftUI differs from traditional UI

The UI is a function of its state

SAY

Traditional UIKit code changes interface properties explicitly. SwiftUI describes the result and lets the framework update it.

CONNECT

Compare the two styles.

Part 4 · Imperative vs declarative

UIKit style vs SwiftUI style

SwiftUI uses a declarative approach: the UI is a function of its state.

UIKit style
  1. Create a UILabel
  2. Set its text
  3. Update it manually when needed

Imperative: tell the interface what to change.

SwiftUI style
  1. Declare a view
  2. Connect it to state
  3. Change state

Declarative: describe the desired result.

SAY

Traditional UIKit code often changes interface properties explicitly: create a label, set its text, and remember to update it whenever the data changes. SwiftUI flips this: declare the view, connect it to state, and just change the state.

ASK

What goes wrong in the UIKit style if you forget one manual update?

EXPECT

The screen shows stale data. In SwiftUI the view is derived from state, so it cannot drift out of sync the same way.

Part 5 · MVVM

Model–View–ViewModel, for a balance screen

For a bank balance screen:

Balance.swift
struct Balance {
    let accountID: String
    // paise: exact money
    let balanceMinor: Int64
}
DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    var balanceText = "—"

    func show(_ b: Balance) {
        let rupees = Decimal(b.balanceMinor) / 100
        balanceText = rupees.formatted(
            .currency(code: "INR"))
    }
}
DashboardView.swift
struct DashboardView: View {
    @State private var model =
        DashboardViewModel()

    var body: some View {
        Text(model.balanceText)
    }
}

Simplified teaching examples, to read rather than write. Coming in Unit 04: MVVM responsibilities in depth (4.2) and dependency injection (4.5).

LIVE DEMO

Open a prepared Xcode project with these three files already in place; students watch, they do not code in this lesson. Call show(_:) with a different balanceMinor in the preview and show the text updating.

SAY

MVVM stands for Model, View, ViewModel. Click through: the model is what the data means, a balance for an account. The ViewModel is what the screen needs, here ready-to-show balance text; it is marked @MainActor because it feeds the UI, and final because nothing subclasses it. The view is what the user sees: it owns its ViewModel with @State and shows a Text.

SAY

The balance is stored as whole paise in an Int64, so amounts are exact; never binary floating point for money. Turning paise into rupees with a currency symbol is presentation, so the ViewModel does it, not the server and not the view. These are simplified teaching examples; Unit 04 adds dependency injection, loading and error states.
