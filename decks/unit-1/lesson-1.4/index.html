Part 2 · Vocabulary (section 3)

Parameter versus argument

Greet.swift
func greet(name: String) {
    print("Hello, \(name)")
}

greet(name: "Ravi")
Parameter
  • In the declaration: name: String
  • What kind of input is accepted
Argument
  • In the call: "Ravi"
  • The actual value supplied
SAY

name in the function declaration is a parameter: it describes what kind of input the function accepts.

SAY

Click: "Ravi", passed when we call the function, is an argument: the actual value supplied. Think of a machine: the parameter is the slot’s shape, the argument is the item you put in.

Swift gives each parameter up to two names.

Part 2 · Argument labels (section 4)

Outside name, inside name

Transfer.swift
func transfer(from source: String,
              to destination: String,
              amountMinor: Int64) {
    print("\(source) → \(destination): \(amountMinor)")
}

transfer(from: "NP1001", to: "NP2002", amountMinor: 50_000)
External label (caller)Internal name (body)
fromsource
todestination
amountMinoramountMinor
Without labels

transfer("NP1001", "NP2002", 50_000)

ERROR missing argument labels ‘from:to:amountMinor:’ in call
SAY

A distinctive Swift feature: a parameter can have an external argument label, used by the caller, and an internal name, used in the body. from and to are labels; source and destination are names. amountMinor uses one name for both.

SAY

The call reads like a sentence: transfer from NP1001 to NP2002, amount 50,000 paise. Labels make calls readable; internal names make the implementation understandable.

SAY

Click: leave the labels out and Swift refuses: missing argument labels from, to, amountMinor in call. The labels are part of the function’s name, so intent stays visible at every call site.

CONNECT

Sometimes a label adds nothing.

Part 2 · Omitting labels (section 5)

The underscore removes the label

Square.swift
func square(_ number: Int) -> Int {
    number * number
}

print(square(5))           // 25
print(square(number: 5))   // error

ERROR extraneous argument label ‘number:’ in call

_ number
  • Callers write no label: square(5)
  • Inside, the name is still number
Use it when
  • The function name already says it
  • Like print(x), square(5)
SAY

The underscore means callers do not write an external label for that parameter: square(5) reads naturally. Inside the function the parameter is still called number.

SAY

Click: and now the label is not allowed: square(number: 5) fails with extraneous argument label number. Without the underscore, it is the other way round: the label is required.

Part 3 · Tuples and defaults (sections 6–7)

Several results, optional arguments

Summary.swift
func accountSummary() -> (balanceMinor: Int64,
                          isActive: Bool) {
    (balanceMinor: 2_500_000, isActive: true)
}

let result = accountSummary()
print(result.balanceMinor)   // 2500000
print(result.isActive)       // true
Tuple return
  • Good for small grouped results
  • Stable model with behavior: a struct
DefaultRate.swift
func calculateFee(amountMinor: Int64,
                  percent: Int64 = 2) -> Int64 {
    amountMinor * percent / 100
}

print(calculateFee(amountMinor: 100_000))
// 2000
print(calculateFee(amountMinor: 100_000, percent: 3))
// 3000
Default value
  • Callers may omit percent
  • Override when needed: percent: 3
SAY

A function can return a tuple: here a balance and an active flag together, read back as result.balanceMinor and result.isActive. Useful for small grouped results; for a stable domain model with behavior, a struct is better, as in Lesson 1.2.

SAY

Click: default parameter values. percent defaults to 2, so most callers write calculateFee(amountMinor:) and get 2,000; a caller that needs 3% passes percent: 3 and gets 3,000. Fewer repeated arguments, still customizable.

Create it now, run it later

FirstClosure.swift
let greet = {
    print("Hello from a closure")

Functions are closures too
  • A function is a named closure
  • A closure expression is written inline
SAY

A closure is a self-contained block of functionality that can be passed around and executed later. Click through its life: create a block of logic; store it in a constant or pass it as an argument; execute it when needed.

SAY

The first closure: we assign a block to greet, and later call greet() like a function. It prints Hello from a closure.

SAY

Functions are also closures in Swift’s broad sense; closure expressions are the inline form, and that is what we write most often.

Part 4 · Syntax (section 9)

Reading a closure

Add.swift
let add: (Int, Int) -> Int = { a, b in
    return a + b
}

print(add(10, 20))   // 30
Function
  • Named, reusable
  • func add(…)
Closure
  • Inline value
  • { a, b in … }
PieceMeaning
(Int, Int) -> Intthe closure’s type
{ … }the closure expression
a, bits parameters
inseparates parameters from the body
return a + bthe result
SAY

A closure that adds two numbers. Read it piece by piece: (Int, Int) -> Int is the closure’s type; the braces contain the closure expression; a and b are its parameters; the keyword in separates the parameters from the body; return a + b produces the result. add(10, 20) is 30.

SAY

Click: a function is named reusable behavior; a closure expression is an inline executable value. Same idea, two forms.

Part 5 · Passing closures (sections 11–12)

Pass behavior in; trail it outside

Operation.swift
func performOperation(a: Int, b: Int,
                      operation: (Int, Int) -> Int) -> Int {
    operation(a, b)
}

performOperation(a: 10, b: 5,
                 operation: { x, y in x + y })   // 15
Trailing.swift
performOperation(a: 10, b: 5) { x, y in
    x + y
}                                    // 15

Button("Transfer") {                 // SwiftUI
    print("Transfer tapped")
}
Why it is powerful
  • Same function, any operation
  • operation: * gives 50
Trailing closure
  • Last argument a closure? Write it after ( )
  • Everywhere in SwiftUI
SAY

performOperation takes two numbers and an operation, itself a function-like value of type (Int, Int) -> Int. Pass an addition closure and you get 15. Pass the multiplication operator and you get 50, without changing performOperation at all. Behavior is supplied by the caller.

SAY

Click: when the last argument is a closure, Swift lets you write it after the parentheses. That is trailing closure syntax, and it is exactly what Button("Transfer") { … } uses.

Part 6 · Capture (section 13)

The closure outlives the function

Counter.swift
func makeCounter() -> () -> Int {
    var count = 0
    return {
        count += 1
        return count
    }
}

let counter = makeCounter()
print(counter(), counter(), counter())   // 1 2 3
let other = makeCounter()
print(other())                           // 1
  • Captured state outlives the call that created it
  • Capturing a class instance strongly can keep it alive (Part 7)
SAY

makeCounter creates a local var count, then returns a closure that adds one and returns it. When makeCounter returns, its local variables would normally be gone.

SAY

Click: call counter(): 1. Click: 2. Click: 3. The closure still remembers count, because it captured it. That is capturing values.

SAY

Click: a second makeCounter() call creates a new closure with its own count, so other() starts again at 1.

SAY

Click: captured state can outlive the function call that created it. That is also why closures can create memory ownership problems when they strongly capture class instances.

Part 7 · @escaping (section 14)

Runs now, or escapes for later

Now.swift
func executeNow(action: () -> Void) {
    action()                // runs during the call
}
Non-escaping (default)
  • Cannot outlive the call
  • Safe to capture anything
Later.swift
final class TaskManager {
    var savedAction: (() -> Void)?

    func register(action: @escaping () -> Void) {
        savedAction = action    // kept for later
    }
}
@escaping
  • May run after the function returns
  • Without it:

ERROR assigning non-escaping parameter ‘action’ to an ‘@escaping’ closure

SAY

A non-escaping closure is guaranteed not to outlive the call it is passed to. executeNow runs its action during the call, and that is Swift’s default for closure parameters.

SAY

An escaping closure may be stored or executed after the function returns. TaskManager stores the action in a property for later, so the parameter must be marked @escaping.

SAY

Click: leave @escaping out and the compiler refuses: assigning non-escaping parameter action to an @escaping closure. The marker is a warning sign to readers: this closure lives on, and so does everything it captures. That is where strong reference cycles can occur.

Here is that cycle in NPay.

Part 7 · Closures and ARC (section 15)

A closure that owns its owner

DashboardViewModel.swift
@MainActor
final class DashboardViewModel {
    var onRefresh: (() -> Void)?

    func configure() {
        onRefresh = { self.refresh() }        // cycle
        // fix: { [weak self] in self?.refresh() }
    }

    func refresh() { print("Refreshing") }
    deinit { print("DashboardViewModel deinit") }
}

Set the ViewModel to nil and run:

CaptureResult
strong selfnothing prints: leaked
[weak self]“deinit” prints: freed
  • [weak self] only for escaping closures that self keeps
SAY

This connects to Lesson 0.6. The ViewModel strongly owns its onRefresh closure, and the closure strongly captures self, the ViewModel. Each keeps the other alive: a retain cycle.

SAY

Click: the evidence. We created the ViewModel, configured it and set it to nil. With the strong capture, nothing prints: deinit never runs, the ViewModel leaked. With [weak self], DashboardViewModel deinit prints: it was freed.

SAY

Click: weak capture is right when you need to break an unwanted ownership relationship, typically an escaping closure stored by the object it captures. Not every closure needs [weak self]: a non-escaping closure, or a map or filter, cannot create this cycle. Lesson 1.8 goes deeper.

Part 8 · Higher-order functions (section 16)

Transform, select, combine

Transactions.swift
let transactions = [500, 1200, 300, 2500]

let doubled = transactions.map { $0 * 2 }        // [1000, 2400, 600, 5000]
let large = transactions.filter { $0 > 1000 }    // [1200, 2500]
let total = transactions.reduce(0) { result, value in
    result + value
}                                                // 4500
SAY

Four transaction amounts. Each of these functions takes a closure; $0 is the shorthand name for the closure’s first argument.

SAY

Click: map transforms each element: doubling gives 1000, 2400, 600, 5000. Click: filter selects the elements that match: above 1000 keeps 1200 and 2500. Click: reduce combines everything into one value, starting from 0 and adding each element: 4500.

SAY

They chain: transactions.filter { $0 > 1000 }.reduce(0, +) is 3700. And these closures are non-escaping: they run during the call, so no [weak self] needed. Collections and performance come back in later lessons.

Lesson 1.4 · Recap

What to remember

Functions name logic
labels make calls read well

Closures are values
stored, passed, run later

Captures keep things alive
@escaping + self: think weak

SAY

Three things to remember. Functions give logic a name, and argument labels, underscores and defaults make the call site read clearly. Closures are logic as a value: SwiftUI stores your button’s closure and runs it on a tap, and trailing closure syntax keeps that readable. And closures capture what they use: an escaping closure kept by the object it captures strongly is a retain cycle, which [weak self] breaks.
