Part 1 · The story (section 1)

Open and close the screen three times

TransactionViewModel.swift
@MainActor
final class TransactionViewModel {
    static var live = 0                    // instances alive now
    var onRefresh: (() -> Void)?

    init() {
        Self.live += 1
        onRefresh = { self.load() }        // strong capture
    }
    func load() {}
    deinit { MainActor.assumeIsolated { Self.live -= 1 } }
}
  • Each ViewModel owns a closure that owns the ViewModel
  • Nothing outside holds it, yet it never goes away
SAY

Every visit to the transaction-history screen creates a TransactionViewModel. When the user leaves, we expect it to be released. The code counts live instances: init adds one, deinit subtracts one. Notice the closure captures self.

SAY

Click: we simulated three visits in a real program and read the count. With the strong capture: 3. Every visit leaves a ViewModel behind. Click: change the capture to weak self and the count is 0.

SAY

Click: each ViewModel owns a closure, and the closure owns the ViewModel. Nothing outside holds them, yet ARC never frees them. To see why, revisit ARC.

What ARC actually does.

Part 1 · ARC (section 2)

Automatic Reference Counting

Automatic
  • The compiler inserts and optimizes retain/release
  • For class instances (and closures, actors)
  • You design ownership: which references keep things alive
SAY

ARC, Automatic Reference Counting, manages the lifetimes of class instances, and also closures and actors. Click through: an instance is created; strong references keep it alive; when the last strong reference is released, it is deinitialized.

SAY

The compiler inserts and optimizes the reference-management operations for you. Do not picture a fixed sequence of literal increments: the optimizer removes many of them.

SAY

Click: automatic does not mean you can ignore ownership. The language decides when to retain and release; you decide which references own something. That is the rest of this lesson.

Part 2 · Lifetimes (sections 3–4)

deinit runs when the last owner lets go

Lifetime.swift
final class Customer {
    let name: String
    init(name: String) {
        self.name = name; print("\(name) created")
    }
    deinit { print("\(name) destroyed") }
}
func testCustomer() {
    let customer = Customer(name: "Ravi")
    print(customer.name)
}
testCustomer()
Prints

Ravi created
Ravi
Ravi destroyed

Strong.swift
var customerA: Customer? = Customer(name: "Meena")
var customerB = customerA

customerA = nil;  print("a = nil")
customerB = nil;  print("b = nil")
Prints

Meena created
a = nil
Meena destroyed
b = nil

SAY

Left: Customer prints when it is created and destroyed. Inside testCustomer it lives only while the function needs it; real output: created, Ravi, destroyed. Nothing escaped, so it is freed at the end of its use. The optimizer may even end lifetimes earlier than the closing brace.

SAY

Right: two variables refer to one Customer. Click: customerA = nil releases one reference, and nothing is destroyed; customerB still owns it. Click: customerB = nil releases the last one, and only now does it print Meena destroyed.

SAY

The takeaway: setting a variable to nil releases that reference; it does not necessarily destroy the object.

Part 3 · Cycles and weak (sections 5–6)

A cycle, and the one-word fix

Cycle.swift
final class Customer {
    var account: Account?
    deinit { print("Customer destroyed") }
}
final class Account {
    var owner: Customer?            // strong: cycle
    deinit { print("Account destroyed") }
}

var customer: Customer? = Customer()
var account: Account? = Account()
customer?.account = account
account?.owner = customer
customer = nil;  account = nil      // prints nothing
WeakOwner.swift
final class Account {
    weak var owner: Customer?       // does not own
}
// customer = nil  →  "Customer destroyed"
// account.owner   →  nil
  • ARC does not detect cycles
  • You decide who owns whom
SAY

A customer owns an account; the account also strongly references its owner. Set both variables to nil and nothing prints: neither deinit runs. Each instance still holds the other. That is a strong-reference cycle.

SAY

Click: the customer owns the account, but the account only needs to know who owns it. Make the back-reference weak.

SAY

Click: we ran it. Now setting customer to nil prints Customer destroyed, and the account’s owner is automatically nil. A weak reference never keeps its target alive.

SAY

Click: ARC does not detect and break arbitrary cycles. Designing the ownership is your job.

Part 4 · weak vs unowned (section 7)

nil, or a crash

weakunowned
Keeps target aliveNoNo
TypeOptional (var)Usually non-optional
Target destroyedBecomes nilStays; access traps
Use whenTarget may go firstTarget always outlives the reference
CreditCard.swift
final class CreditCard {
    unowned let customer: Customer
    init(customer: Customer) { self.customer = customer }
}
Read it after the customer is gone

Fatal error: Attempted to read an unowned
reference but object 0x… was already destroyed

  • No check at all: undefined behaviour. Avoid in app code.
SAY

Neither weak nor unowned keeps its target alive. weak is an optional var that automatically becomes nil when the target goes. unowned is usually non-optional and does not become nil.

SAY

A CreditCard cannot exist without its customer, so it holds the customer unowned. Click: if the customer is destroyed first and the card reads it anyway, the app traps. Real message: attempted to read an unowned reference but the object was already destroyed.

SAY

So use unowned only when the lifetime relationship guarantees the target outlives every access; otherwise use weak. Click: and unowned(unsafe) removes even that check: reading it after deallocation is undefined behaviour. Avoid it in app code. This answers the question left open in Lesson 0.6.

Part 4 · Ownership for values (authored)

Non-copyable types: one owner, by law

ExportToken.swift
struct ExportToken: ~Copyable {
    let id: Int
    deinit { print("token \(id) released") }
}
func upload(_ token: consuming ExportToken) {
    print("uploading with token \(token.id)")
}

let token = ExportToken(id: 1)
upload(token)          // ownership moves in
// upload(token)       // error: consumed more than once
Prints

uploading with token 1
token 1 released

~Copyable
  • A struct that cannot be copied
  • Can have a deinit (Lesson 1.5)
  • consuming: ownership moves
Use it twice

ERROR ‘token’ consumed more than once

SAY

This slide is beyond the lesson text; Lesson 1.5 promised it. Swift 5.9 added non-copyable types. ExportToken is a struct marked tilde Copyable: it cannot be copied, so it always has exactly one owner, and it can have a deinit.

SAY

upload takes the token as consuming: ownership moves into the function. Real output: uploading with token 1, then token 1 released, when upload finishes with it.

SAY

Click: that is the point: a value with exactly one owner, enforced by the compiler. Click: use it a second time and the build fails: token consumed more than once. Good for one-time resources like an export token or a file handle. You will see it rarely in app code, but it shows where Swift ownership is heading.

Part 5 · Closures (section 8)

Ask three questions

DashboardViewModel.swift
@MainActor
final class DashboardViewModel {
    var onRefresh: (() -> Void)?

    func configure() {
        onRefresh = { [weak self] in   // the fix
            self?.refresh()
        }
    }
    func refresh() { print("Refreshing dashboard") }
}
The cycle (Lesson 1.4)
  • The ViewModel owns onRefresh
  • onRefresh captured self strongly
  • Who owns the closure?
  • How long does it live?
  • What does it capture?
No cycle
  • Non-escaping closures run now: map, filter
  • Owned by something that ends soon
SAY

The cycle from Lesson 1.4: the ViewModel owns onRefresh, and the closure captured self strongly. The fix: capture self weakly, so the closure no longer retains the ViewModel.

SAY

Click: but weak capture is not required for every closure. Before adding it, ask three questions: who owns the closure, how long does it live, and what does it capture?

SAY

Click: a non-escaping closure that runs immediately, like map or filter, cannot form this cycle, and neither can a closure owned by something short-lived. Reflexive [weak self] everywhere adds noise and can hide real design problems.

Timers are a classic long-lived owner.

Part 5 · Timers (section 9)

Weak capture and invalidate: two different jobs

DashboardController.swift
@MainActor
final class DashboardController {
    var timer: Timer?

    func start() {
        timer = Timer.scheduledTimer(
            withTimeInterval: 1, repeats: true
        ) { [weak self] _ in
            self?.refresh()
        }
    }
    func refresh() { print("Refresh") }
    func stop() { timer?.invalidate(); timer = nil }
}
[weak self]
  • Callback doesn’t keep the controller alive
invalidate()
  • Stops the timer; the run loop lets go
SAY

A repeating timer owns its callback closure, and the run loop keeps a scheduled timer alive, as Lesson 0.6 showed. If the callback captured the controller strongly, the controller would live as long as the timer.

SAY

This version does two things. Click: weak self, so the callback does not keep the controller alive. And invalidate in stop, so the timer actually stops and the run loop releases it.

SAY

They address different concerns. Weak capture alone leaves a timer firing every second into a nil self; invalidate alone, with a strong capture, depends on stop being called. Do both.

Part 6 · ARC vs GC (section 10)

Prompt and predictable, but cycles stay

ARCTracing garbage collection
HowCounts ownership; frees when it endsTraces what is reachable
WhenPromptly, when ownership endsWhen the collector runs
Strong cyclesStay aliveUsually reclaimed if unreachable
Used bySwift class instancesJava and many runtimes

Simplified; real systems add many optimizations.

  • Yes: strong cycles and unintended long-lived references
SAY

ARC manages lifetimes through ownership and can free an object promptly, the moment ownership ends. A tracing collector, as in Java, periodically finds what is still reachable, and its timing depends on the collector. The big practical difference: a strong cycle stays alive under ARC, while many tracing collectors reclaim unreachable cycles. ARC is used for Swift class instances.

SAY

This is simplified; both kinds of system use many optimizations.

SAY

Click: so, can a Swift app leak memory? Yes: strong-reference cycles and unintended long-lived references, like our screen that refused to die.

How do you find one?

Part 6 · Investigating (section 11)

Seven steps from suspicion to proof

  1. Reproduce the suspected leak
  2. Navigate away from the screen
  3. Check whether expected objects deinitialize
  4. Inspect the Memory Graph (Xcode)
  5. Find unexpected strong-reference chains
  6. Correct the ownership
  7. Repeat and verify
Tools
  • Memory Graph Debugger: who holds this object?
  • Instruments: Allocations, Leaks over time
  • A missing deinit is not proof of a leak
  • Something may legitimately still own it
SAY

A reliable process. Reproduce the suspected leak. Navigate away from the screen. Check whether the objects you expect to disappear actually deinitialize, our deinit prints and live counter. Inspect Xcode’s Memory Graph to see who still holds them. Find the unexpected strong-reference chain. Correct the ownership. Then repeat the experiment and verify.

SAY

The Memory Graph Debugger answers who holds this object; Instruments shows allocations and leaks over time. Lesson 8.9 goes deep on Instruments.

SAY

Click: a missing deinit message alone does not prove a leak. The object may still be legitimately retained, by a cache, a navigation stack, or a task that has not finished, which is our last part.

Part 7 · Tasks (section 12)

guard let self keeps it alive until the work ends

StatementViewModel.swift
@MainActor
final class StatementViewModel {
    func startExport() {
        Task { [weak self] in
            guard let self else { return }           // strong from here on
            try? await Task.sleep(for: .seconds(2))  // long work
            self.finish()
        }
    }
    func finish() { print("export finished") }
    deinit { print("StatementViewModel deinit") }
}
Real output

screen closed, vm = nil
export finished
StatementViewModel deinit

The real fix is cancellation and lifecycle design: Lesson 1.9.
SAY

A statement export runs as a long task. It captures self weakly, which looks safe, then immediately promotes it: guard let self. From that line on, the task holds a strong reference for the whole long operation.

SAY

Click: the user closes the screen and the view model variable is set to nil. Click: but the task still holds self, so nothing is freed. Click: we ran it: export finished prints after the screen closed, and only then does deinit run.

SAY

So weak self alone does not always solve the lifetime problem. Click: the real fix is cancelling the task when the screen goes away, and designing the lifecycle; Lesson 1.9 covers tasks and cancellation, and Lesson 8.3 goes deeper.

What to remember

Owners keep things alive
nil releases a reference, not the object

weak or unowned
nil safely, or trap

Prove it
deinit, Memory Graph, verify the fix

SAY

Three things to remember. Strong references own: setting one to nil releases that reference, not necessarily the object, and ARC never breaks a cycle for you. weak becomes nil safely; unowned traps if its target is gone; ask who owns a closure before adding weak self, and remember a promoted self in a task lives until the task ends. And prove it: reproduce, check deinit, inspect the Memory Graph, fix ownership, verify.
