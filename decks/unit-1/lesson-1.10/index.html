SAY

Money is a struct, because an amount is a value; it stores whole paise in an Int64, exact, with no binary fractions, as Lesson 1.2 argued. It is Equatable so amounts compare with ==, and Sendable because this immutable value will cross into the ledger actor. rupees converts to Decimal for display.

SAY

enum TransactionType

BankingError.swift
enum BankingError: Error {
    case accountNotFound
    case accountInactive
    case invalidAmount
    case insufficientFunds
    case sameAccountTransfer
    case arithmeticOverflow
}
enum BankingError
  • Says why it failed (1.7)
  • Better than returning false
SAY

Every deposit, withdrawal or transfer should produce a record. The type is an enum because valid types form a known set; that is safer than strings like Deposit, deposit and DEPOSIT, which a typo silently breaks.

SAY

Failures get their own enum, as in Lesson 1.7: account not found, inactive, invalid amount, insufficient funds, a transfer to the same account, arithmetic overflow. A good error model says why an operation failed; a Boolean false loses that information.

Part 3 · Contract (section 7)

One protocol, several implementations

BankingService.swift
protocol BankingService: Sendable {
    func balance(for accountId: String) async throws -> Money
    func deposit(_ amount: Money, into accountId: String) async throws
    func withdraw(_ amount: Money, from accountId: String) async throws
    func transfer(_ amount: Money,
                  from sourceId: String,
                  to destinationId: String) async throws
}
Why
  • async throws: any implementation may wait or fail
  • Sendable: safe to share (1.6, 1.9)
  • The ViewModel depends on this (4.5)
SAY

BankingService says what the engine can do: read a balance, deposit, withdraw, transfer. Every requirement is async throws, because some implementation may need to wait, for the network for example, and any of them can fail. It is Sendable, as Lesson 1.9 explained, because it will be shared across isolation boundaries.

SAY

It says nothing about how. Today’s in-memory BankLedger actor implements it; a mock can implement it for tests and previews; later a network-backed service can implement it.

SAY

Click: the ViewModel depends on this protocol, not on a concrete type: dependency injection from Lesson 1.6, built properly in Lesson 4.5.

Part 4 · The actor (sections 8–9)

The ledger owns the accounts

BankLedger.swift
actor BankLedger: BankingService {
    private var accounts: [String: BankAccount]

    init(accounts: [BankAccount]) {
        self.accounts = Dictionary(uniqueKeysWithValues: accounts.map { ($0.id, $0) })
    }

    func balance(for accountId: String) throws -> Money {
        guard let account = accounts[accountId] else { throw BankingError.accountNotFound }
        return account.balance
    }
}
private var accounts
  • Only the actor touches it
No async needed
  • Methods without await inside stay sync
  • Callers outside still await
Not a database
  • One door, in memory
  • No durability, no ACID
SAY

Without synchronization, two tasks could both read the same balance and both approve a withdrawal, the lost update from Lesson 1.9. So the account dictionary lives inside an actor, private, and only the actor touches it.

SAY

Click: balance(for:) is not marked async: it contains no suspension point. Yet it satisfies the protocol’s async throws requirement, and code outside the actor still awaits it, because it may have to wait its turn. We compiled this under Swift 6.

SAY

Click: an actor serializes access to its own state; it is not a database transaction system. And actor methods are reentrant at suspension points, so for our transfer we deliberately keep validation and mutation free of await. Remember that for Part 7.

Part 4 · Deposit and withdraw (sections 9–10)

Every guard before any change

BankLedger+Withdraw.swift
func withdraw(_ amount: Money, from accountId: String) throws {
    guard amount.paise > 0 else { throw BankingError.invalidAmount }
    guard var account = accounts[accountId] else { throw BankingError.accountNotFound }
    guard account.isActive else { throw BankingError.accountInactive }
    guard account.balance.paise >= amount.paise else {
        throw BankingError.insufficientFunds
    }
    account.balance = Money(paise: account.balance.paise - amount.paise)
    accounts[accountId] = account
}
Validation order
  • Amount, account exists, active, enough funds
  • Only then change the balance
deposit
  • Same guards, plus addingReportingOverflow (1.2)
  • Overflow throws .arithmeticOverflow
SAY

withdraw checks, in order: a positive amount, the account exists, it is active, and it has enough money. Only after every guard passes does it change the balance and write the account back into the dictionary. A failed withdrawal changes nothing.

SAY

With a non-negative balance and a positive amount no larger than it, the subtraction cannot overflow Int64.

SAY

Click: deposit uses the same guards, and addingReportingOverflow from Lesson 1.2, throwing arithmeticOverflow instead of crashing.

Part 5 · Transfer (section 11)

All the checks, then both writes, no await

BankLedger+Transfer.swift
func transfer(_ amount: Money, from sourceId: String, to destinationId: String) throws {
    guard sourceId != destinationId else { throw BankingError.sameAccountTransfer }
    guard amount.paise > 0 else { throw BankingError.invalidAmount }
    guard var source = accounts[sourceId],
          var destination = accounts[destinationId] else { throw BankingError.accountNotFound }
    guard source.isActive, destination.isActive else { throw BankingError.accountInactive }
    guard source.balance.paise >= amount.paise else { throw BankingError.insufficientFunds }
    let (newDest, overflow) = destination.balance.paise.addingReportingOverflow(amount.paise)
    guard !overflow else { throw BankingError.arithmeticOverflow }
    source.balance = Money(paise: source.balance.paise - amount.paise)
    destination.balance = Money(paise: newDest)
    accounts[sourceId] = source
    accounts[destinationId] = destination          // no await anywhere above
}
Safe here because
  • The actor owns both accounts
  • No await between check and change
SAY

A transfer changes two accounts: the source goes down, the destination goes up, as one logical operation. The method checks everything first: not the same account, a positive amount, both accounts exist and are active, enough funds, and no overflow at the destination. Only then does it write both accounts.

SAY

Click: Ravi ₹25,000 sends ₹5,000 to Meena ₹10,000. Afterwards ₹20,000 and ₹15,000; the total stays ₹35,000 in this zero-fee example.

SAY

Click: why is this safe? The actor owns both accounts, and there is no await between validation and mutation, so no other call on the ledger can interleave with this critical section. It is still an in-memory simulation: no durable transactions, no distributed consistency, nothing survives the process ending.

@Test and #expect

TransferTests.swift
import Testing
@testable import NPayCore

@Test func transferMovesMoney() async throws {
    let ledger = makeLedger(2_500_000, 1_000_000)  // Ravi, Meena
    try await ledger.transfer(Money(paise: 500_000),
                              from: "A", to: "B")

    #expect(try await ledger.balance(for: "B").paise == 1_500_000)
}
@Test, #expect
  • @Test marks a test
  • #expect fails the test if false
FailureTests.swift
@Test func insufficientFundsChangesNothing() async throws {
    let ledger = makeLedger(100_000, 50_000)
    await #expect(throws: BankingError.insufficientFunds) {
        try await ledger.transfer(Money(paise: 200_000),
                                  from: "A", to: "B")
    }
    #expect(try await ledger.balance(for: "A").paise == 100_000)
    #expect(try await ledger.balance(for: "B").paise == 50_000)
}
Precise failure test
  • The exact error, not just “some error”
  • And nothing changed
SAY

Because the domain is separate from SwiftUI, we test it without launching an iPhone interface. transferMovesMoney builds a ledger, transfers ₹5,000, reads both balances with await, and checks them with #expect. @Test marks a test; #expect reports a failure if its condition is false. makeLedger is a small helper that creates Ravi and Meena.

SAY

Click: good engineers test failures too. The lesson text’s version checks that some BankingError is thrown. We tightened it, as the text suggests: the exact error, insufficientFunds, and that neither balance changed.

SAY

A passing test shows correctness for that scenario; it does not prove the whole system correct. That is why we write many.

Part 7 · Reentrancy (sections 16–17)

Check, await, change: the check goes stale

AccountStore.swift
actor AccountStore {
    var balancePaise: Int64 = 1_000_000            // ₹10,000

    func withdraw(_ amountPaise: Int64) async throws {
        guard balancePaise >= amountPaise else {
            throw BankingError.insufficientFunds
        }
        await performExternalCheck()     // others may run
        balancePaise -= amountPaise
    }
}
Real runs

check, await, change → both ok, ₹−3,000
await, then check + change → one rejected, ₹4,000

  • Actor isolation does not make a multi-step async operation atomic
SAY

An actor lets one task in at a time, but it is reentrant: at an await, the actor is free to run other calls. This AccountStore checks the balance, then awaits an external check, then subtracts.

SAY

Click through: A checks ₹10,000 against ₹7,000: fine. A awaits the external check, and the actor is free. B checks ₹10,000 against ₹6,000: fine, but stale, because A has not paid yet. A pays, then B pays. Click: −₹3,000.

SAY

Click: we ran both versions. Check, await, change: both withdrawals succeeded and the balance went to minus ₹3,000. Await first, then check and change together with no suspension in between: one was rejected and ₹4,000 remained. That is why our BankLedger’s transfer has no await inside it, and why its concurrency test passed.

SAY

The rule: never assume actor isolation makes a multi-step asynchronous business operation atomic. Keep validation and mutation together without suspension, or re-validate after the await. In a real bank this is a database and business-consistency problem; Lesson 8.4 goes deeper.
