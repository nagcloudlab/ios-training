Two words to get right first: concurrency and parallelism.

Part 1 · Two words (section 2)

Taking turns, or truly at once

Concurrency
  • Tasks make progress in overlapping periods
  • They may take turns on one resource
Parallelism
  • Computations run at the same instant
  • Needs several cores
  • Organizes concurrent work; parallel or not depends on scheduling, isolation and cores
SAY

Concurrency means several tasks make progress during overlapping periods; they may take turns. Parallelism means computations really run at the same instant, on different cores. Back to our restaurant kitchen: one chef alternating between two dishes while one simmers is concurrency; two chefs each cooking a dish is parallelism.

SAY

Click: Swift Concurrency is a way to organize concurrent work safely. Whether any of it actually runs in parallel depends on scheduling, isolation and the cores available.

Prove it.

Part 2 · Tasks vs threads (section 3)

A task is work; a thread is a worker

Thread
  • An OS execution resource with its own stack
  • Expensive; few of them
Task
  • A language unit of async work
  • Suspends; resumes on an appropriate executor
Measured on this Mac (18 cores)

10,000 tasks, each waiting 1 s
→ all finished in 1.08 s

  • Not 10,000 threads: waiting tasks free their thread
  • Task {} ≠ a new thread
SAY

A thread is an operating-system execution resource with its own stack, scheduled by the OS; threads are expensive and there are few. A Swift task is a language-level unit of asynchronous work that can suspend and resume on an appropriate executor. It is not tied to one thread.

SAY

Click through: task A runs; it reaches an await and suspends; the thread is free to run other work; later task A resumes, possibly on a different thread.

SAY

Click: we measured it. Ten thousand tasks, each waiting one second with Task.sleep, all finished in 1.08 seconds on this 18-core Mac. That is impossible with one thread per task: waiting tasks give their thread back. So never teach Task {} as creating a new thread.

That is what async and await are for.

Part 2 · async/await (section 4)

Wait without holding the thread

FetchBalance.swift
func fetchBalance() async throws -> Int64 {
    try await Task.sleep(for: .seconds(2))   // stands in for the network
    return 2_500_000
}
KeywordMeans
asyncthe function can suspend
awaita possible suspension point
throwsthe function can fail
tryacknowledges a possible error
Why it exists
  • A network call is mostly waiting
  • Blocking wastes a thread; suspending frees it
  • Marks where code may suspend, not that it will
SAY

A network request is mostly waiting for the server; the CPU has nothing to do for it. Synchronous code would block a thread for that whole time. An async function lets the calling task suspend instead. Task.sleep stands in for the network here; the balance is paise, as always.

SAY

async: the function can suspend. await: a possible suspension point. throws and try: it can fail, as in Lesson 1.7.

SAY

Click: await does not mean a delay or a network call is happening. It marks a call that may suspend; it might complete immediately.

Suspending frees the thread; blocking holds it

RefreshButton.swift
Button("Refresh balance") {

While it waits
  • The task suspends at await
  • The main thread keeps handling taps and frames (0.5)
Measured: 40 tasks, each BLOCKING 1 s

→ 3.0 s on 18 cores

  • Blocked tasks hold pool threads: about 40 ÷ 18 rounds
Swift 6 even refuses it

SAY

The Refresh balance button creates a task, and the task awaits fetchBalance. While it waits, the task is suspended, and the main thread is free to handle taps and draw frames, exactly the run loop behaviour from Lesson 0.5.

SAY

Click: compare blocking. We ran 40 tasks that each block their thread for one second with Thread.sleep: 3.0 seconds on 18 cores, because blocked tasks hold the pool’s threads. Ten thousand suspending tasks took one second.

SAY

Click: Swift 6 actually refuses Thread.sleep directly inside async code: class method sleep is unavailable from asynchronous contexts. We had to hide it inside a synchronous helper to measure it.

SAY

Click: async does not make CPU-heavy work safe. A long synchronous loop inside an async function still blocks whatever thread it runs on; if that is the main actor, the UI freezes. Lesson 8.7 covers hangs.

Two versions.

Part 4 · async let (section 6)

Three awaits, or three child tasks

Sequential.swift
let balance      = try await fetchBalance()
let transactions = try await fetchTransactions()
let profile      = try await fetchProfile()
// measured: 6.2 s
Sequential
  • Each call starts after the previous one finishes
  • Total ≈ sum: 2 + 3 + 1
Concurrent.swift
async let balance      = fetchBalance()
async let transactions = fetchTransactions()
async let profile      = fetchProfile()

let dashboard = try await (balance, transactions, profile)
// measured: 3.2 s
async let
  • Each starts a child task immediately
  • Total ≈ the slowest: 3 s
SAY

Sequential awaits: the transactions call starts only after the balance arrives, and the profile only after that. Measured 6.2 seconds.

SAY

Click: async let starts each call as a child task immediately and keeps going. The single try await on the tuple waits for all three. Measured 3.2 seconds: the slowest request, because they overlap. Only do this when the requests are independent.

CONNECT

Those child tasks have a parent. That is structured concurrency.

Part 4 · Structured concurrency (section 7)

Children belong to a parent scope

Lifetime
  • No child is abandoned
Errors
  • A child’s error reaches the parent
Cancellation
  • Cancel the parent: children are cancelled
SAY

Structured concurrency: child tasks belong to a defined parent scope. The dashboard task owns the balance, transactions and profile children, and its scope cannot end until all three have finished.

SAY

Click: that structure gives three guarantees. Lifetime: a parent cannot abandon unfinished children when it leaves the scope. Errors: a child’s thrown error propagates to the parent. Cancellation: cancelling the parent cancels its children.

SAY

Compare a loose Task {} with no owner, like the export task in Lesson 1.8: nobody waits for it, nobody cancels it. Prefer structure; Lesson 8.2 goes deeper.

Part 5 · Task groups (section 8)

One child per account, results as they finish

FetchAllBalances.swift
func fetchAllBalances(accountIds: [String]) async throws -> [(String, Int64)] {
    try await withThrowingTaskGroup(of: (String, Int64).self) { group in
        for id in accountIds {
            group.addTask { (id, try await fetchBalance(for: id)) }
        }
        var results: [(String, Int64)] = []
        for try await result in group { results.append(result) }
        return results
    }
}

Real run:

AddedNP1001, NP1002, NP1003
Took3 s, 1 s, 2 s
ReturnedNP1002, NP1003, NP1001
Completion order
  • Results come back as tasks finish
  • Need order? Return the id with each result
  • No: limits, rate limits, back-pressure (8.6)
SAY

async let suits a fixed number of operations. For a dynamic list, like every account a customer holds, use a task group: one child task per account id, then collect results with for try await. Each result carries its account id.

SAY

Click: we ran it with three accounts that take 3, 1 and 2 seconds. Added in order NP1001, NP1002, NP1003; returned NP1002, NP1003, NP1001.

SAY

Click: task-group results arrive in completion order, not the order you added them. If order matters, return an identifier with each result, as we did, and rebuild the order.

SAY

Click: should we launch thousands of requests at once? No: real systems need concurrency limits, server rate limits, resource management and back-pressure. Lesson 8.6 covers that.

Part 6 · Cancellation (section 9)

Cancellation is cooperative

LoadTransactions.swift
func loadTransactions() async throws {
    try Task.checkCancellation()
    let transactions = try await fetchTransactions()
    try Task.checkCancellation()
    print(transactions)
}

let task = Task { try await loadTransactions() }
task.cancel()       // 0.2 s later, in the real run
Real run

stopped: CancellationError

cancel()
  • Sets a flag on the task
  • Does not stop it by force
Who responds
  • Task.checkCancellation() throws
  • Task.sleep, URLSession throw on cancel
  • Your loops check Task.isCancelled
  • Synchronous code keeps running until it checks
SAY

Swift tasks support cooperative cancellation. loadTransactions checks before and after the network call; Task.checkCancellation throws CancellationError if the task has been cancelled.

SAY

Click: real run: we cancelled the task 0.2 seconds in, while it was waiting; it stopped with CancellationError.

SAY

Click: cancel only sets a flag. Things that respond: checkCancellation, and asynchronous APIs like Task.sleep and URLSession, which throw when cancelled. Your own long loops must check Task.isCancelled.

SAY

Click: requesting cancellation never forcibly stops arbitrary synchronous code. This is the fix for Lesson 1.8’s export task: keep the task, cancel it when the screen closes.

Work that lives and dies with the view

Why prefer it
  • SwiftUI owns the task’s lifetime
  • No loose, long-lived Task {}
  • Your code and its APIs must respond to cancellation
SAY

SwiftUI’s .task modifier starts async work tied to the view. Click: the view appears. Click: the task starts. Click: when the view disappears, SwiftUI cancels the task.

SAY

Click: that is usually better than creating a long-lived unstructured task with no clear owner. But cancellation is still cooperative: your code and the APIs it calls must respond. Unit 03 uses .task throughout.

Part 7 · Data race (section 11)

The lost update

Measured: 1,000 concurrent ₹1 deposits, no protection

expected ₹26,000 · got ₹25,598, then ₹25,578 (one run was right)

SAY

Two tasks update the same balance at the same time. Click: both read ₹25,000. Task A will add ₹5,000; task B will subtract ₹3,000.

SAY

Click: task A writes ₹30,000. Click: then task B writes ₹22,000, computed from the old value. The stored balance should be ₹27,000; task A’s deposit is simply lost. That is a lost update, one kind of data race.

SAY

Click: it really happens. We ran 1,000 concurrent one-rupee deposits on unprotected state. Expected ₹26,000; we got ₹25,598 and ₹25,578 on two runs, and the right answer once. Correct sometimes is the worst kind of bug.

Swift 6 has two answers: the compiler, and actors.

Part 7 · Actors (authored)

An actor lets one task in at a time

Account.swift
actor Account {
    private(set) var balanceMinor: Int64 = 2_500_000

    func deposit(_ amountMinor: Int64) {
        balanceMinor += amountMinor          // one caller at a time
    }
}

let account = Account()
await withTaskGroup(of: Void.self) { group in
    for _ in 0..<1000 { group.addTask { await account.deposit(100) } }
}
print(await account.balanceMinor)            // 2600000, every run
Swift 6 catches the unsafe version

ERROR passing closure as a ‘sending’ parameter risks causing data races…

actor
  • Protects its own state: one task at a time
  • Outside callers must await
  • Same 1,000 deposits: ₹26,000 every run
  • At an await inside an actor, other calls may run (8.4)
SAY

Beyond the lesson text, which stopped here, as you asked for actors. First, Swift 6 refuses to compile the unsafe version: share a plain class balance between two child tasks and you get passing closure as a sending parameter risks causing data races. A global var gets a similar error. We had to opt out deliberately to measure the race.

SAY

Click: the fix is an actor. An actor protects its own mutable state by letting one task in at a time. Code outside must await to call it, because it may have to wait its turn. The same thousand deposits: ₹26,000 on every run.

SAY

Click: one subtlety, from Lesson 0.5: actors are reentrant. If an actor method awaits, other calls can run in between, so state may change across the await. Lesson 8.4 covers reentrancy; Lesson 1.10 builds NPay’s ledger as an actor.

Part 8 · MainActor (authored)

The main actor owns the UI

DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    var balanceText = "—"

    func refresh() async {
        do {
            let minor = try await fetchBalance()  // elsewhere
            balanceText = "₹\(minor / 100)"        // main actor
        } catch {
            balanceText = "Balance unavailable"
        }
    }
}
@MainActor
  • A global actor: the main thread (0.5)
  • All of the ViewModel runs there
  • Safe to update what SwiftUI shows
From outside, without await

ERROR main actor-isolated property ‘balanceText’ can not be mutated from a nonisolated context

SAY

The main actor is a global actor for the main thread from Lesson 0.5. Marking the ViewModel @MainActor, the course canon since Unit 00, puts all of it there, so updating what SwiftUI shows is always safe.

SAY

refresh awaits fetchBalance, which may run elsewhere; when it returns, the code is back on the main actor and sets balanceText. The compiler handles the hop.

SAY

Click: try to set balanceText from a nonisolated function without awaiting and the compiler refuses: main actor-isolated property balanceText can not be mutated from a nonisolated context. UI updates from the wrong thread become a build error, not a crash.

Last: what is allowed to cross between actors and tasks.

Part 8 · Sendable (authored)

Sendable: safe to share across tasks

KindExampleWhy
Value types of Sendable partsstruct Balance { let balanceMinor: Int64 }copies can’t race
Actorsactor Accountprotect their own state
Immutable final classesfinal class with only let Sendable propertiesnothing to race on
Not Sendablea class with var statethe compiler stops it crossing
Lesson 1.6, explained
  • The ViewModel is on the main actor
  • fetchBalance() ran off it
  • So the service had to be Sendable
The rule
  • Values that cross an isolation boundary must be Sendable
  • Swift 6 checks it at compile time (8.5)
SAY

Sendable marks types that are safe to share between concurrency domains, between tasks and actors. Value types made of Sendable parts, like our Balance struct, are Sendable: every task gets its own copy. Actors are Sendable because they protect their own state. Immutable final classes can be. A class with mutable var state is not, and the compiler will not let it cross.

SAY

Click: this explains Lesson 1.6. The DashboardViewModel lives on the main actor; its service’s async method ran off the main actor; so the service crossed a boundary and had to be Sendable. The rule: anything that crosses an isolation boundary must be Sendable, and Swift 6 checks it when you build. Lesson 8.5 goes deeper into strict concurrency checking.

Lesson 1.9 · Recap

What to remember

Tasks suspend; threads don’t
await frees the thread

Structure your work
async let, groups, cancellation

Isolate shared state
actors, @MainActor, Sendable

SAY

Three things to remember. A task is not a thread: at an await it suspends and frees its thread, which is how ten thousand waits finished in a second, while blocking work holds threads hostage. Structure your work: async let and task groups make child tasks with a parent, errors and cancellation flow through that structure, and cancellation is cooperative. And isolate shared state: actors prevent lost updates, the main actor owns the UI, and Sendable decides what may cross between them, all checked by the Swift 6 compiler.
