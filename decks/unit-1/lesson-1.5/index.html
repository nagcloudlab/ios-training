Part 1 · The problem (section 1)

Change the transfer screen. What does the dashboard show?

Value semantics
  • Independent logical values
  • Change one, the other stays
Reference semantics
  • Shared object identity
  • Change it once, everyone sees it
SAY

NPay shows the account in two places: the dashboard and the transfer screen. Both start at ₹25,000. The transfer screen changes its balance to ₹20,000. Should the dashboard change too?

SAY

Click: with a struct, each screen holds its own value, so only the transfer screen shows ₹20,000. With a class, both screens refer to one Account instance, so both now show ₹20,000. This is a conceptual picture, not real SwiftUI synchronization or a banking transaction.

SAY

Click: two fundamental ideas. Value semantics: independent logical values. Reference semantics: shared object identity.

Part 2 · Struct and class (sections 2–3)

A copy, or a second name

StructAccount.swift
struct Account {
    var balanceMinor: Int64       // paise
}

var accountA = Account(balanceMinor: 2_500_000)
var accountB = accountA
accountB.balanceMinor = 2_000_000
print(accountA.balanceMinor)      // 2500000
print(accountB.balanceMinor)      // 2000000

Two values. Changing B left A alone.

ClassAccount.swift
final class Account {
    var balanceMinor: Int64
    init(balanceMinor: Int64) {
        self.balanceMinor = balanceMinor
    }
}
let accountA = Account(balanceMinor: 2_500_000)
let accountB = accountA
accountB.balanceMinor = 2_000_000
print(accountA.balanceMinor)      // 2000000

One instance. Both names see ₹20,000.

SAY

Both start at ₹25,000, 2,500,000 paise. accountB is assigned from accountA and changed to ₹20,000.

ASK

Before the clicks: what does accountA print in each version?

SAY

Click: the struct. Assignment produced an independent logical value: accountA still prints 2,500,000. Value semantics does not mean Swift duplicates every byte immediately; it can share storage and copy only when needed, as we will see in Part 6. The guarantee is that changing one value never changes another.

SAY

Click: the class. accountA and accountB are two references to the same object, so accountA prints 2,000,000. And notice accountB is a let: let stops you pointing it at a different object, not changing the object, exactly as in Lesson 1.2.

Part 3 · Comparison (section 4)

Eight differences

FeatureStructClass
SemanticsValueReference
IdentityNo object identityObject identity (===)
InheritanceNo class inheritanceSupports inheritance
ARCNot ARC-managed as an instanceInstances managed by ARC
DeinitializerNo deinit*Supports deinit
Mutating methodsNeed mutatingNo mutating keyword
Memberwise initSynthesizedWrite init yourself
Typical useData models and valuesShared identity, services

* Non-copyable structs (~Copyable) can have a deinit; Lesson 1.8.

“Struct = stack, class = heap” is not the rule. The distinction is semantics.
SAY

Row by row. Structs have value semantics, classes reference semantics. Classes have object identity, checked with three equals signs. Only classes support inheritance. ARC manages class instances; a struct is not ARC-managed as an instance, though any class references inside it are. Classes support deinit. A struct method that changes stored properties needs mutating; classes have no such keyword. Structs get a synthesized memberwise initializer; classes need you to write init. And typically: structs for data models and values, classes for shared identity and reference-based services.

SAY

One refinement: since Swift 5.9, non-copyable structs, marked tilde Copyable, can have a deinit. Ordinary structs cannot. Lesson 1.8 covers ownership.

SAY

Click: do not teach struct equals stack and class equals heap as a rule. Where values are stored is an implementation detail; the language guarantee is about semantics.

Part 4 · mutating and init (sections 5–6)

Say when you change it; say how it starts

Deposit.swift
struct Account {
    var balanceMinor: Int64

    mutating func deposit(_ amountMinor: Int64) {
        balanceMinor += amountMinor
    }
}

var account = Account(balanceMinor: 2_500_000)
account.deposit(500_000)
print(account.balanceMinor)       // 3000000
Without mutating

ERROR left side of mutating operator isn’t mutable: ‘self’ is immutable

Init.swift
struct Customer {                 // memberwise init: free
    let id: String
    var name: String
}
let customer = Customer(id: "C1001", name: "Ravi")

class CustomerRecord {            // no init written
    let id: String
    var name: String
}
Class without init

ERROR class ‘CustomerRecord’ has no initializers

SAY

deposit changes the struct’s stored balance, so it is marked mutating. Depositing ₹5,000 to ₹25,000 gives 3,000,000 paise. The method is changing the value represented by the instance, and mutating makes that intent explicit.

SAY

Click: remove mutating and the compiler says: left side of mutating operator isn’t mutable, self is immutable.

SAY

Right side: a struct gets a synthesized memberwise initializer for free, so Customer(id:name:) just works. A class with stored properties that have no default values must write its own init. Click: without it, class CustomerRecord has no initializers. Designated and convenience initializers and two-phase class initialization come in a later lesson.

Part 5 · === and == (section 7)

Same object versus same value

Identity.swift
final class Customer {
    let name: String
    init(name: String) { self.name = name }
}

let a = Customer(name: "Ravi")
let b = Customer(name: "Ravi")
let c = a

print(a === b)   // false
print(a === c)   // true
Equality.swift
struct CustomerValue: Equatable {
    let name: String
}

print(CustomerValue(name: "Ravi") ==
      CustomerValue(name: "Ravi"))   // true
===
  • Same instance? Classes only
  • Ignores the data
==
  • Same value? Needs Equatable
  • Compares the data
SAY

a and b are two Customer objects that both hold Ravi. c is just another name for a. Three equals signs asks: do these two references identify the same instance? a === b is false: same data, different objects. a === c is true. The picture shows it: a and c point to instance 1, b to instance 2.

SAY

Click: for equality of values, types conform to Equatable. Two CustomerValue structs with the same name are equal, ==, true. Structs have no identity to compare; they are their data.

Measure it.

Part 6 · Copy-on-write (section 8)

Share until someone writes

CopyOnWrite.swift
var a = [10, 20, 30]
var b = a          // shares a's buffer

b.append(40)       // b gets its own buffer

print(a)   // [10, 20, 30]
print(b)   // [10, 20, 30, 40]

Measured: do a and b use the same buffer address?

Before b.append(40)true: one shared buffer
Afterfalse: separate buffers
Why it matters
  • Value semantics, without copying on every assignment
  • One reason Swift favours structs for models
  • Built into Array, Dictionary, Set, String
SAY

a and b are arrays, so they have value semantics: after b.append(40), a is still [10, 20, 30]. But Swift does not copy the elements on var b = a. Both arrays start out sharing one underlying buffer.

SAY

Click: when b is mutated and the buffer is shared, b first gets its own copy. That is copy-on-write: copy only when someone writes.

SAY

Click: we measured it, using withUnsafeBufferPointer to read each array’s buffer address. Before the append: the same address, true. After: different, false. Exact storage behaviour is an implementation detail; the semantics are the guarantee.

SAY

Click: copy-on-write gives you the simplicity of value semantics with efficient storage reuse. It is built into the standard collections, Array, Dictionary, Set and String; your own structs get it only if you implement it. That is one reason Swift encourages value types for data models.

Part 7 · ARC and SwiftUI (sections 9–10)

Classes live and die; views describe

Lifetime.swift
final class Customer {
    let name: String
    init(name: String) {
        self.name = name; print("Created")
    }
    deinit { print("Destroyed") }
}
var customer: Customer? = Customer(name: "Ravi")
customer = nil
Prints

Created
Destroyed

  • Last strong reference gone: deinit
  • A cycle prevents it (0.6, 1.4)
BalanceView.swift
import SwiftUI

struct BalanceView: View {
    let balanceText: String   // from the ViewModel

    var body: some View {
        Text(balanceText)
    }
}
SwiftUI views are structs
  • A description of the UI, recreated often
  • Lasting state is kept by SwiftUI (Unit 03)
SAY

Classes introduce reference ownership. Create a Customer and it prints Created; set the only reference to nil and ARC deinitializes it: Destroyed. Strong reference cycles would prevent that, as in Lesson 0.6 and the closure cycle in Lesson 1.4. Now you can see why cycles are a reference-type problem.

SAY

Click: SwiftUI views are usually structs. BalanceView takes ready-formatted text from the ViewModel, as in Lesson 0.2, and describes a Text. That does not mean SwiftUI redraws the whole screen whenever a struct changes: view values are descriptions of the desired interface, and SwiftUI manages identity, state and rendering itself.

SAY

A view struct can be recreated very often, so lasting view state is kept separately by SwiftUI. That is why view identity and property wrappers matter so much in Unit 03.

Part 8 · Decision (section 11)

Struct or class?

NPay typeChooseBecause
Transaction recordstructa value representing data
Currency amountstructa value; equal amounts are interchangeable
SwiftUI screen descriptionstructa cheap description SwiftUI recreates
Observable ViewModelclassone shared, observed instance (@Observable is for classes)
Shared session managerclassidentity and shared mutable session state
  • Start with a struct for independent values
  • Choose a class when identity or shared ownership is part of the design
  • A guideline, not a law
ASK

Before the table: struct or class for each of the five?

SAY

A transaction record is naturally a value representing data: struct. A currency amount: struct; two equal amounts are interchangeable. A SwiftUI screen description: struct, recreated cheaply. An observable ViewModel: class; the screen observes one shared instance, and the @Observable macro works on classes. A shared session manager: class, because identity and shared mutable session state are the point.

SAY

Click: start with a struct when you need independent values; choose a class when reference identity or shared ownership is genuinely part of the design. A guideline, not an absolute law.

Part 8 · NPay model (section 12)

Values for data, a class for the session

Model.swift
struct Money: Equatable {
    let amountMinor: Int64       // paise
    let currency: String         // "INR"
}

struct Transaction: Equatable {
    let id: String
    let amount: Money
    let description: String
}

final class SessionManager {
    private(set) var isLoggedIn = false
    func login() { isLoggedIn = true }
    func logout() { isLoggedIn = false }
}
Money, Transaction
  • Domain values: structs
  • Equatable: compare by value
SessionManager
  • A service with identity
  • Shared, mutable session state
  • final: no subclassing
  • Stronger validation, secure sessions (Unit 07)
SAY

Money and Transaction are domain values, so they are structs, and Equatable so they compare by value. Money stores whole paise in Int64 plus a currency code, as in Lesson 1.2; Lesson 1.10 makes it a richer type.

SAY

Click: SessionManager is a service with identity and shared mutable state, so it is a class, final because nothing should subclass it. private(set) lets everyone read isLoggedIn but only the manager change it.

SAY

Click: a real banking implementation needs stronger domain validation and secure session handling; Unit 07 covers that.
