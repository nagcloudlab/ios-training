Part 1 · The problem (section A1)

Same logic, written once

Copies.swift
func firstTransaction(_ values: [Int]) -> Int? {
    values.first
}
func firstCustomer(_ values: [String]) -> String? {
    values.first
}

Identical logic; only the type changes.

Generic.swift
func firstElement<T>(_ values: [T]) -> T? {
    values.first
}
Called withT becomesReturns
[10, 20, 30]IntOptional(10)
["Ravi", "Meena"]StringOptional("Ravi")
[true, false]BoolOptional(true)
T is a type parameter. The compiler picks the real type at each call, and keeps it.
SAY

NPay needs the first element of an array: once for transaction ids, once for customer names. Two functions, identical logic, only the type differs.

SAY

Click: one generic function. The angle brackets declare T, a generic type parameter. Called with an array of Int, T becomes Int and it returns Optional(10). With strings, T becomes String. With Bools, Bool. Those are the real outputs.

SAY

Click: the compiler determines the concrete type at each call, and keeps it: the result of firstElement(["Ravi"]) is typed Optional of String, not something vaguer.

Why not just use Any?

Part 1 · Not Any (section A2)

Any forgets the type; generics keep it

AnyValue.swift
func addOne(_ value: Any) -> Any {
    value + 1                  // error
}
Any
  • Holds any value, but the compiler forgets what it was
  • Type-specific work needs casts (as?)

ERROR cannot convert value of type ‘Any’ to expected argument type ‘Int’

Identity.swift
func identity<T>(_ value: T) -> T {
    value
}

let amount: Int = identity(100)
let name: String = identity("Ravi")
Generic
  • Return type matches the input type
  • No casts; checked at compile time
Any erases the type. Generics preserve the relationship between types.
SAY

Any can hold any value. But then the compiler knows less about it: adding one to an Any is rejected, cannot convert value of type Any to expected argument type Int. You would need runtime casts with as?.

SAY

Click: the generic identity function returns exactly the type it received. identity(100) is an Int; identity("Ravi") is a String. No casts, all checked at compile time.

SAY

Click: Any provides type erasure; generics preserve type relationships.

Part 2 · Types and constraints (sections A3–A4)

One wrapper; a constraint that unlocks ==

APIResponse.swift
struct APIResponse<T> {
    let data: T
    let statusCode: Int
}

struct Customer { let name: String }
struct Account { let balanceMinor: Int64 }

let a = APIResponse(data: Customer(name: "Ravi"),
                    statusCode: 200)     // APIResponse<Customer>
let b = APIResponse(data: Account(balanceMinor: 2_500_000),
                    statusCode: 200)     // APIResponse<Account>
Generic type
  • One definition: APIResponse<T>
  • Many concrete types: <Customer>, <Account>
AreEqual.swift
func areEqual<T: Equatable>(_ a: T, _ b: T) -> Bool {
    a == b
}

print(areEqual(5, 5))             // true
print(areEqual("Ravi", "Meena"))  // false
T: Equatable
  • Not every type supports ==
  • The constraint promises it

Without it: ERROR binary operator ‘==’ cannot be applied to two ‘T’ operands

SAY

Generic types: APIResponse of T wraps any model with a status code. One definition; the concrete types are APIResponse of Customer and APIResponse of Account. Account holds paise in Int64, as before.

SAY

Click: constraints. areEqual compares two values, but Swift cannot assume every type supports equality. Without a constraint the compiler says: binary operator == cannot be applied to two T operands. T: Equatable requires T to conform to the Equatable protocol, and that makes == available.

SAY

This is where protocols and generics meet: protocols describe capabilities; constraints say which capabilities a type must have.

associatedtype.

Part 3 · Associated types (section A5)

Each conformer decides the type

Repository.swift
protocol Repository {
    associatedtype Item
    func fetchAll() async throws -> [Item]
}

struct CustomerRepository: Repository {
    func fetchAll() async throws -> [Customer] {   // Item = Customer
        [Customer(name: "Ravi"), Customer(name: "Meena")]
    }
}
associatedtype
  • A placeholder inside a protocol
  • Inferred from the conformer: Item = Customer
  • Used across the standard library and SwiftUI
SAY

Different repositories return different records: customers, transactions. We want one contract. associatedtype Item declares a type placeholder that each conforming type fills in.

SAY

CustomerRepository returns an array of Customer, so Swift infers Item = Customer. A TransactionRepository would set Item = Transaction. The contract stays the same.

SAY

Click: associated types let protocols relate types without hard-coding one model. The standard library uses them everywhere, for example a collection’s Element, and so does SwiftUI.

Part 4 · Throwing (sections B6–B7)

Errors are values; throw stops the function

What can fail
  • Invalid amount
  • Insufficient funds
  • Inactive account
  • Network failure
  • Backend rejects it
TransferError.swift
enum TransferError: Error {
    case invalidAmount
    case insufficientFunds
    case accountInactive
}
Validate.swift
func validateTransfer(amountMinor: Int64,
                      balanceMinor: Int64,
                      isActive: Bool) throws {
    guard isActive else { throw TransferError.accountInactive }
    guard amountMinor > 0 else { throw TransferError.invalidAmount }
    guard amountMinor <= balanceMinor else {
        throw TransferError.insufficientFunds
    }
}
throws
  • Either completes normally, or exits by throwing
  • Client-side checks only: the server authorizes transfers
SAY

A transfer of ₹10,000 can fail in several ways: an invalid amount, insufficient funds, an inactive account, a network failure, or the backend rejecting it. Swift represents failures with types that conform to the Error protocol. An enum is a natural fit: TransferError with three cases.

SAY

Click: a function that can fail is marked throws. validateTransfer checks the account is active, the amount is positive, and the balance covers it; each failed guard throws a specific error. A throwing function either completes normally or exits by throwing. Amounts are paise, as always.

SAY

These are client-side checks for a good user experience. Real transfers are authorized and processed by the server.

Part 5 · do / try / catch (section B8)

Catch what you can handle

Handle.swift
do {
    try validateTransfer(amountMinor: amount,
                         balanceMinor: 2_500_000,
                         isActive: active)
    print("Validation successful")
} catch TransferError.invalidAmount {
    print("Invalid transfer amount")
} catch TransferError.insufficientFunds {
    print("Insufficient funds")
} catch {
    print("Unexpected error: \(error)")
}
KeywordMeaning
throws / throwcan throw / throws one
trymarks a call that may throw
do / catchscope / handles matching errors

Balance ₹25,000. Real output:

TransferPrints
₹10,000Validation successful
₹0Invalid transfer amount
₹30,000Insufficient funds
inactiveUnexpected error: accountInactive
  • No catch for accountInactive: the general catch takes it
SAY

do opens a scope for throwing calls; try marks the call that may throw; each catch handles matching errors, most specific first, and a final catch with no pattern handles the rest, with the error available as error.

SAY

Click: we ran four transfers against a ₹25,000 balance. ₹10,000 from an active account: Validation successful. ₹0: Invalid transfer amount. ₹30,000: Insufficient funds. ₹10,000 from an inactive account: Unexpected error, accountInactive, because there is no specific catch for it, so the general catch takes it.

SAY

And try is not optional decoration: call a throwing function without it and the compiler says call can throw but is not marked with try. The failure path is always visible in the code.

Two shortcuts, one useful and one dangerous.

Part 5 · try? and try! (section B9)

Three ways to call a throwing function

FormMeansOn failure
tryhandle it, or propagate it to the callerthe error reaches someone who decides
try?turn failure into nilthe reason is discarded (Lesson 1.3)
try!assert it cannot failif it does: the app traps
try! that fails, run for real

Fatal error: ‘try!’ expression unexpectedly
raised an error: TransferError.invalidAmount

  • try! only when failure is impossible by a justified invariant
  • Never to skip error handling
SAY

Three forms. Plain try: the error must be handled in a do/catch or propagated from a throwing function. try?: failure becomes nil and the error details are discarded, as we saw with decoding in Lesson 1.3. try!: you assert the call cannot fail.

SAY

Click: if a try! call does fail, the app traps. Real message: Fatal error, try! expression unexpectedly raised an error, invalidAmount. In an app, that is a crash.

SAY

Use try! only when failure is genuinely impossible under a justified invariant, never to avoid writing error-handling code.

Part 6 · Propagation and Result (sections B10–B11)

Let errors travel; or return them as values

Propagate.swift
func performTransfer() throws {
    try validateTransfer(amountMinor: 1_000_000,
                         balanceMinor: 2_500_000, isActive: true)
    print("Transfer validation completed")
}
throws, without catch
  • performTransfer passes the error up
  • Each layer handles what it understands
Result.swift
func validate(amountMinor: Int64)
    -> Result<String, TransferError> {
    guard amountMinor > 0 else {
        return .failure(.invalidAmount)
    }
    return .success("Valid transfer")
}
// 0 → failure(invalidAmount)
// 5 → success("Valid transfer")
Result<Success, Failure>
  • .success(value) or .failure(error)
  • A value: store it, return it, pass it on
SAY

performTransfer is marked throws but does not catch: if validation throws, the error simply continues to performTransfer’s caller. That is propagation.

SAY

The picture shows why it matters in NPay: the view calls the ViewModel, the ViewModel calls the service, the service throws. The networking service knows an HTTP request failed; the ViewModel decides what message the user sees. A good architecture decides which layer handles which errors.

SAY

Click: Result is the other style. validate returns Result of String and TransferError: either success with a value or failure with an error, as an ordinary value you can store and pass around. Real output: failure(invalidAmount) for 0, success for 5. throws expresses failure through control flow; Result through a value. Both are useful, depending on the API.

Part 7 · async throws (section B12)

try for failure, await for waiting

FetchBalance.swift
func fetchBalance() async throws -> Int64 {
    try await Task.sleep(for: .seconds(1))   // illustrative wait
    return 2_500_000
}

do {
    let balanceMinor = try await fetchBalance()
    print(balanceMinor)
} catch {
    print("Failed: \(error)")
}
async
  • Can suspend while it waits
  • await marks the suspension point
throws
  • Can fail
  • try acknowledges it
try await
  • Two different concerns, one call
  • Order is always try await
SAY

fetchBalance is both async, it can suspend while it waits, and throws, it can fail. The sleep stands in for a network call.

SAY

Calling it needs both keywords: try acknowledges possible failure, await marks a potential suspension point. Different concerns, one call: try await. Prints 2500000.

SAY

Click: as Lesson 0.5 showed, await does not block the thread while it waits; Lesson 1.9 explains how.

Part 7 · Generic API client (section B13)

One fetch for every model

APIClient.swift
struct APIClient {
    func fetch<T: Decodable>(_ type: T.Type, from url: URL) async throws -> T {
        let (data, response) = try await URLSession.shared.data(from: url)
        guard let http = response as? HTTPURLResponse,
              (200..<300).contains(http.statusCode) else {
            throw URLError(.badServerResponse)
        }
        return try JSONDecoder().decode(T.self, from: data)
    }
}
Callers.swift
struct Balance: Decodable { let balanceMinor: Int64 }
struct Customer: Decodable { let name: String }

let balance = try await client.fetch(Balance.self, from: balanceURL)
let customer = try await client.fetch(Customer.self, from: profileURL)
Why it works
  • T: Decodable: any model that can be decoded
  • Throws on a bad status or bad JSON
  • The pattern of real Swift networking layers
SAY

One method, generic over T, constrained to Decodable. It awaits URLSession, checks for a 2xx status, throwing badServerResponse otherwise, then decodes the data as T, which can also throw. Everything from today in nine lines: a generic function, a constraint, async, and throws. The status check uses 200..<300, as in Lesson 0.8.

SAY

Click: the same method decodes a Balance, in paise, and a Customer. Each caller gets back exactly the type it asked for.

SAY

Click: T: Decodable guarantees the type can be decoded; the function throws on a bad status or bad JSON. This is the core of real Swift networking layers; Lesson 5.4 builds the full version.

Part 8 · Design (section B14)

Report, decide, present

APIError.swift
enum APIError: Error {
    case unauthorized              // 401
    case server(status: Int)
    case decoding
}
Why separate
  • The client reports; it doesn’t navigate
  • Each layer is testable on its own
  • Token refresh and sessions: 5.5, Unit 07
SAY

The API returns 401 Unauthorized. Should the generic networking service jump straight to the login screen? Usually not.

SAY

Click: the networking layer reports a meaningful error, APIError.unauthorized, instead of a raw status code. Click: a higher-level session or app coordinator decides whether to reauthenticate, perhaps refreshing a token first. Click: only then does the UI present the login screen.

SAY

Click: the client reports, it does not navigate. That keeps each layer simple and testable on its own. Lesson 5.5 covers token refresh; Unit 07 covers sessions; Lesson 4.8 maps errors across layers.

Lesson 1.7 · Recap

What to remember

Generics keep the type
<T>, constraints, associated types

Errors are typed values
throw, try, catch; try? drops the reason

Layers own their errors
report low, decide high, show at the top

SAY

Three things to remember. Generics write logic once and keep the concrete type, unlike Any; constraints like T: Equatable say what T must be able to do, and associated types give protocols their own placeholders. Errors are typed values: throw them, mark calls with try, catch what you can handle; try? throws away the reason and try! crashes on failure. And layers own their errors: the client reports, a coordinator decides, the UI shows.
