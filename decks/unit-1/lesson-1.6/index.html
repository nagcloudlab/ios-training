Part 1 · The problem (sections 1–2)

Three payment methods, one contract

PaymentMethod.swift
protocol PaymentMethod {
    func pay(amountMinor: Int64)
}
A protocol
  • States what a conforming type must provide
  • Says nothing about how
  • Each type supplies its own implementation
SAY

NPay supports UPI, card and bank transfer. Each behaves differently, but all must support one operation: making a payment. The challenge is a common contract without forcing every payment method into one class hierarchy.

SAY

Click: a protocol defines requirements that conforming types must satisfy, a contract. PaymentMethod says any conforming type must provide pay(amountMinor:). It says nothing about how payment works; that belongs to each type. Amounts are in paise, as in earlier lessons.

Part 2 · Conformance (sections 3–4)

Same contract, different behavior

Payments.swift
struct UPIPayment: PaymentMethod {
    func pay(amountMinor: Int64) {
        print("UPI payment: ₹\(amountMinor / 100)")
    }
}

struct CardPayment: PaymentMethod {
    func pay(amountMinor: Int64) {
        print("Card payment: ₹\(amountMinor / 100)")
    }
}
Conformance
  • Two structs, one protocol
  • No class inheritance involved
Process.swift
func processPayment(using method: any PaymentMethod,
                    amountMinor: Int64) {
    method.pay(amountMinor: amountMinor)
}

processPayment(using: UPIPayment(),
               amountMinor: 100_000)
processPayment(using: CardPayment(),
               amountMinor: 200_000)
Prints

UPI payment: ₹1000
Card payment: ₹2000

  • Polymorphism: the caller depends on the contract
SAY

UPIPayment and CardPayment both conform to PaymentMethod: each provides pay(amountMinor:), in its own way. Both are structs. Protocol conformance does not imply class inheritance.

SAY

Click: processPayment takes any value that conforms to PaymentMethod and calls pay. Pass a UPI payment and a card payment and each prints its own message: UPI payment ₹1000, Card payment ₹2000. That is polymorphism: different implementations through one interface.

SAY

The caller depends on a contract, not a concrete payment type. Adding BankTransferPayment needs no change to processPayment, and in tests you can pass a fake. Less coupling, easier to extend and test.

Part 3 · Properties (section 5)

Readable, or readable and writable

BankAccount.swift
protocol BankAccount {
    var accountNumber: String { get }
    var balanceMinor: Int64 { get set }
}

struct SavingsAccount: BankAccount {
    let accountNumber: String   // { get }
    var balanceMinor: Int64     // { get set }
}
{ get }
  • Must be readable
  • A let or a var satisfies it
{ get set }
  • Must be readable and writable
  • A let does not satisfy it
balanceMinor as a let

ERROR type ‘SavingsAccount’ does not conform to protocol ‘BankAccount’

SAY

BankAccount requires two properties. { get } means the property must be readable; { get set } means readable and writable. SavingsAccount satisfies both: a let accountNumber is readable, a var balanceMinor is readable and writable.

SAY

A read-only requirement can be satisfied by something that is also writable, but not the other way round.

SAY

Click: make balanceMinor a let and SavingsAccount no longer conforms: type SavingsAccount does not conform to protocol BankAccount.

Part 4 · Comparison (section 6)

One parent, or many capabilities

FeatureProtocolClass inheritance
Structs can take partYesNo
Classes can take partYesYes

SAY

Two design approaches. Class inheritance shares behavior and implementation through a hierarchy, and a class has exactly one superclass. Protocol conformance defines a shared capability, and a type, struct or class, can conform to many protocols.

SAY

The table: structs can take part in protocols but not inheritance; classes can do both; many protocols versus one superclass; protocols share implementation through extensions, which is the next part; and the main purpose differs: abstraction and capabilities versus shared identity and specialization.

Two uses, one surprise.

Part 5 · Extensions and defaults (sections 7–8)

Write it once, every type gets it

PaymentMethod.swift
protocol PaymentMethod {
    func pay(amountMinor: Int64)
    func validate(amountMinor: Int64) -> Bool    // requirement
}

extension PaymentMethod {
    func validate(amountMinor: Int64) -> Bool {   // default
        amountMinor > 0
    }
    func logPayment(amountMinor: Int64) {        // shared helper
        print("Payment initiated: ₹\(amountMinor / 100)")
    }
}
Shared behavior
  • logPayment: every payment method can call it
Default implementation
  • validate is a requirement
  • Types may use the default, or provide their own
Result
  • Composition without a deep class hierarchy
SAY

A protocol extension adds code to every conforming type. logPayment is a shared helper: any payment method can call it instead of re-implementing logging.

SAY

Click: an extension can also provide a default implementation of a requirement. validate is declared in the protocol, and the extension gives it a default: amount greater than zero. A type with no validate of its own satisfies the requirement through the default; a type that needs stricter rules provides its own.

SAY

Click: protocols define capabilities; extensions provide shared behavior. That is composition without a deep class hierarchy.

Now the surprise the lesson text warned about. Watch closely.

Part 5 · Dispatch (section 8)

Same object, two different answers

Dispatch.swift
protocol PaymentMethod {
    func validate(amountMinor: Int64) -> Bool   // requirement
}
extension PaymentMethod {
    func validate(amountMinor: Int64) -> Bool { amountMinor > 0 }
    func label() -> String { "payment" }        // extension only
}
struct CardPayment: PaymentMethod {
    func validate(amountMinor: Int64) -> Bool { amountMinor >= 10_000 }
    func label() -> String { "card" }
}
let card = CardPayment()
let method: any PaymentMethod = card
Callon cardon methodWhy
validate(amountMinor: 5_000)falsefalserequirement: the card’s version both times
label()"card""payment"extension only: chosen by the static type
SAY

One CardPayment value, seen two ways: as card, its concrete type, and as method, typed any PaymentMethod. validate is a requirement; label exists only in the extension. CardPayment provides its own version of both.

ASK

Before the click: what does each call return?

SAY

Click: we ran it. validate is a requirement, so the call goes through the protocol’s witness table to the card’s own version both times: false, because the card needs at least ₹100. But label is only in the extension: through method, Swift calls the extension’s version and returns "payment", even though the object is a card. Methods only in an extension are chosen by the static type.

SAY

This surprises developers from Java, where every method is virtual. The rule: if conforming types should be able to customize a method, declare it in the protocol.

Part 6 · Extensions (section 9)

Extend Int64 with a rupee helper

Int64+Rupees.swift
extension Int64 {
    var rupeesText: String {   // computed
        "₹\(self / 100)"
    }
}

let amountMinor: Int64 = 50_000
print(amountMinor.rupeesText)       // ₹500
Can add
  • Computed properties, methods
  • Initializers, protocol conformances, more
Even for types you don’t own
  • Int64, String, Apple’s types
  • Subject to access rules
Cannot add stored properties

ERROR extensions must not contain stored properties

SAY

An extension adds functionality to an existing type. Here we add a rupeesText computed property to Int64, turning paise into a simple rupee string: 50,000 paise is ₹500. We do not own Int64; it is in the standard library. Extensions work on accessible types you did not write, subject to access rules.

SAY

Extensions can add computed properties, methods, initializers in supported contexts, protocol conformances and more.

SAY

Click: they cannot add stored properties: extensions must not contain stored properties. The type’s memory layout is already fixed.

SAY

Click: this helper is a teaching example. Real display formatting, with grouping like ₹25,000 and the user’s locale, belongs in the ViewModel, as in Lesson 0.2.

Part 7 · Composition (section 10)

Require two capabilities with &

CompletePayment.swift
protocol PaymentProcessing {
    func process(amountMinor: Int64)
}
protocol ReceiptGenerating {
    func generateReceipt() -> String
}
func completePayment(
    using service: any PaymentProcessing & ReceiptGenerating,
    amountMinor: Int64
) {
    service.process(amountMinor: amountMinor)
    print(service.generateReceipt())
}
Callers.swift
completePayment(using: UPIService(), amountMinor: 50_000)
completePayment(using: CashCounter(), amountMinor: 50_000)
SAY

Two small protocols: PaymentProcessing can take a payment, ReceiptGenerating can produce a receipt. completePayment needs a service that can do both, so its parameter type is any PaymentProcessing & ReceiptGenerating. The ampersand means: must conform to both.

SAY

Two NPay services. UPIService conforms to both protocols. CashCounter only takes payments; it cannot issue receipts.

SAY

Click: pass the UPI service and it is accepted. Real output: UPI: ₹500 paid, then Receipt NP-R1.

SAY

Click: pass the cash counter and the build fails before the app ever runs. The real message: argument type CashCounter does not conform to expected type ReceiptGenerating.

SAY

Notice we did not need a combined superclass, such as a PaymentAndReceiptBase, just to say both. Keep protocols small and combine them with the ampersand where a function needs more.

Part 7 · any (section 11)

any: different types in one place

Mixed.swift
let methods: [any PaymentMethod] = [
    UPIPayment(), CardPayment()
]

for m in methods {
    m.pay(amountMinor: 50_000)
}
Same array with some

[some PaymentMethod]

ERROR conflicting arguments to generic parameter (‘UPIPayment’ vs. ‘CardPayment’)
any: the type can be different for each value. Use it for mixed arrays and swappable values.
SAY

any PaymentMethod and some PaymentMethod both mean: a value of a type that conforms to PaymentMethod. The difference is whether that type can vary. Start with any.

SAY

This array holds two different types: a UPIPayment and a CardPayment. That is only possible because the element type is any PaymentMethod.

SAY

Click: loop over it and each one calls its own pay. Real output: UPI ₹500, then Card ₹500. Swift works out which pay to call while the app runs.

SAY

Click: write the same array with some instead, and the compiler refuses: conflicting arguments, UPIPayment versus CardPayment. some allows only one type.

SAY

Click: so any means the type can be different for each value. Use it for mixed arrays and for stored values you may swap, like the service in a ViewModel in Part 8.

Part 7 · some (section 11)

some: one exact type you don’t have to name

DashboardView.swift
import SwiftUI

struct DashboardView: View {
    var body: some View {
        VStack {
            Text("₹25,000")
            Button("Refresh balance") { }
        }
    }
}
The real type of body (printed)

VStack<TupleView<(Text, Button<Text>)>>

  • some View hides this
  • It changes every time you edit the view
DefaultPayment.swift
func defaultPayment() -> some PaymentMethod {
    UPIPayment()   // always UPIPayment; a CardPayment
}                  // on another path won't compile
some: one exact type the compiler knows, so you don’t have to name it. any can vary; some cannot.
SAY

Now some. Here is a small NPay view: a VStack with a Text and a Button. Its body is declared as some View.

SAY

Click: we printed the real type of body. It is VStack of TupleView of Text and Button of Text. Nobody wants to write that, and it changes every time you edit the view. some View means: one exact type, the compiler knows it, you do not have to spell it.

SAY

Click: the same works for our protocol. defaultPayment returns some PaymentMethod, and it is always a UPIPayment; the caller just does not see the name. Because it must be one type, returning a card payment on another path is a compile error: the return statements do not have matching underlying types.

SAY

Click: so some means one fixed type, known to the compiler and hidden from the caller, used mostly for return types. any can vary; some cannot. Lesson 1.7 explains the generics underneath.

Part 8 · Dependency injection (section 13)

Depend on the protocol, inject the service

BalanceProviding.swift
struct Balance: Sendable { let balanceMinor: Int64 }

protocol BalanceProviding: Sendable {
    func fetchBalance() async throws -> Balance
}

struct MockBalanceService: BalanceProviding {
    func fetchBalance() async throws -> Balance {
        Balance(balanceMinor: 2_500_000)        // ₹25,000
    }
}
DashboardViewModel.swift
@MainActor
final class DashboardViewModel {
    private let service: any BalanceProviding

    init(service: any BalanceProviding) {
        self.service = service
    }

    func loadBalance() async throws -> Balance {
        try await service.fetchBalance()
    }
}
  • Without : Sendable: sending ‘self.service’ risks causing data races (why: Lesson 1.9)
SAY

NPay’s ViewModel fetches the balance. It should not be tied to one network service. So it depends on the BalanceProviding protocol and receives a service through its initializer: dependency injection. The real BalanceService talks to the bank’s API; MockBalanceService returns ₹25,000 for tests and previews. Same names as Lessons 0.8 and 1.1.

SAY

The ViewModel depends on the protocol, not the concrete implementation, so swapping the real service for a mock in a test is one line.

SAY

Click: one correction to the lesson text. Its version of this code does not compile in Swift 6: sending self.service risks causing data races. The ViewModel is on the main actor and the service’s async method runs elsewhere, so the service must be safe to share. Marking the protocol Sendable fixes it, and both our services are simple structs, so they qualify. Lesson 1.9 explains Sendable; Unit 04 builds full dependency injection.

Three things to remember. A protocol is a contract that any struct, class or enum can conform to, and a type can conform to many. SAY
