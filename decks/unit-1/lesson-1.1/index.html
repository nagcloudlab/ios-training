Part 2 · Compilation pipeline · conceptual

Six lines, six stages

main.swift
let amount = 500
let quantity = 3

let total = amount * quantity

print(total)

Building NPay sends every .swift file through the same stages before anything runs on the iPhone.

Swift source → Swift-specific compilation → LLVM-based code generation → native executable.
SAY

Six lines: amount times quantity, printed. Building a native Swift app sends this source through a compilation pipeline. Click through it.

SAY

One, the Swift source files. Two, parsing and semantic analysis: syntax, types, declarations, and the diagnostics you see as errors. Three, SIL, the Swift Intermediate Language. Four, LLVM IR, a lower-level intermediate representation. Five, machine code for the target architecture, arm64 on an iPhone. Six, the linker produces the executable with its dependencies.

SAY

The brackets show who does what: the Swift frontend, swiftc, handles stages one to three and produces the LLVM IR; LLVM optimizes it and generates machine code; the linker builds the binary. This is conceptual: real builds have more passes, modules and optimization stages.

SAY

Is Swift ever interpreted? Running swift main.swift in a terminal feels like a script, but it still compiles the code first and runs it straight away. There is no bytecode virtual machine.

What are SIL and LLVM, and can we see them?

Part 2 · SIL and LLVM

What SIL and LLVM do

SIL · Swift Intermediate Language

A representation designed for Swift. It keeps Swift’s semantics so the compiler can check and optimize them before lowering the code further.

LLVM

A compiler infrastructure project. Swift uses it to optimize and generate native machine code for each supported target.

Our six lines, compiled with swiftc -O (Swift 6.3, arm64):

StageWhat we seeMeaning
SILsmul_with_overflow_Int64Swift semantics kept: the multiply is overflow-checked
LLVM IRstore i64 1500LLVM worked out 500 × 3 at compile time
Assemblymov w20, #1500one processor instruction loads the answer
SAY

SIL stands for Swift Intermediate Language: an intermediate representation designed specifically for Swift. It lets the compiler represent Swift semantics and optimize them before lowering the code further. LLVM is a compiler infrastructure project; Swift uses it to optimize and generate native machine code for each supported target.

SAY

Click: real output from our six lines. In SIL the multiply is still there, as an overflow-checked multiply: Swift traps on integer overflow instead of silently wrapping, and SIL carries that rule. In LLVM IR the optimizer has already computed 500 times 3, so it just stores 1500. The arm64 assembly loads 1500 with a single instruction. You will reproduce this in the lab.

LIVE DEMO

In a terminal: xcrun swiftc -emit-sil -O main.swift | grep smul; xcrun swiftc -emit-ir -O main.swift | grep 1500; xcrun swiftc -S -O main.swift | grep 1500. Exact text varies with compiler version.

Part 5 · Optionals

One type, two possible states

Nickname.swift
var nickname: String? = "Ravi"

nickname = nil
Unwrap.swift
let nickname: String? = "Ravi"

if let name = nickname {
    print("Hello, \(name)")
} else {
    print("No nickname available")
}
The possibility of absence is part of the type. You unwrap before you use the value.
SAY

var nickname: String? = "Ravi". The question mark means: either a String, or no value. It starts with a value.

SAY

Right now the optional holds Some("Ravi"). Click: nickname = nil, and now it holds no value.

SAY

In many languages, null-related errors happen because code assumes a value exists. Swift puts the possibility of absence into the type system, so the compiler knows. You generally must unwrap an optional before using the value as a non-optional one. if let does that: it binds name only when there is a value, and the else branch handles absence.

SAY

Click: the takeaway. Lesson 1.3 covers optionals in much greater depth.

Values versus references

They are not.

Part 6 · Semantics

Value types and reference types

Value types
  • Structs, enums, tuples
  • Assignment makes an independent value
  • Example: a transaction amount
Reference types
  • Classes, actors
  • Many references, one shared instance
  • Example: a session manager
“Structs live on the stack, classes on the heap.” Not a guaranteed rule in Swift. The real distinction is value semantics versus reference semantics.
SAY

A transaction amount is naturally a value. A session manager may need shared identity and controlled mutable state. Swift supports both. Value types are structs, enums and tuples: assignment produces an independent logical value. Reference types are classes and actors, and closures behave the same way: several references can point to the same instance.

SAY

Click: the misconception. Struct-on-stack, class-on-heap is not a guaranteed rule; a struct inside a class or an array lives on the heap, and the optimizer may place a class instance on the stack. Lesson 0.6 showed this. Think in semantics, not storage.

Now see the difference in code, and what each version leaves in memory.

Part 6 · In code

Change the copy, check the original

StructAccount.swift
struct Account {
    var balanceMinor: Int64      // paise
}

var accountA = Account(balanceMinor: 500_000)
var accountB = accountA
accountB.balanceMinor = 900_000
print(accountA.balanceMinor)
print(accountB.balanceMinor)

Prints 500000, 900000: two values.

ClassAccount.swift
class Account {
    var balanceMinor: Int64
    init(balanceMinor: Int64) {
        self.balanceMinor = balanceMinor
    }
}
let accountA = Account(balanceMinor: 500_000)
let accountB = accountA
accountB.balanceMinor = 900_000
print(accountA.balanceMinor)

Prints 900000: one shared instance.

SAY

Two files, each with its own Account type. Amounts are whole paise in an Int64, as NPay stores money: 500,000 paise is ₹5,000. In both, accountB starts from accountA, and we change accountB to 900,000.

ASK

Before the click: what does each print?

SAY

Click: the struct. var accountB = accountA made a copy, so memory holds two Account values: changing accountB left accountA at ₹5,000. It prints 500000 then 900000. Click: the class. let accountB = accountA copied only the reference, so both names point to one instance, and the change through accountB is seen through accountA. It prints 900000.

Part 7 · ARC

Automatic Reference Counting

ARC counts strong references and frees an instance when the count reaches zero. Nothing pauses to scan memory.
Ownership becomes your design job: retain cycles keep instances alive forever.
SAY

Swift uses Automatic Reference Counting to manage the lifetime of class instances. Click through it: an instance is created; strong references keep it alive; when no strong ownership remains, ARC deinitializes it.

SAY

ARC is different from tracing garbage collection: it does not periodically scan memory to find unreachable objects. Click: the cost is that ownership becomes part of your design. Two objects that strongly own each other, a retain cycle, are never freed.

SAY

Part 8 · Protocols

Depend on what, not on who

BalanceProviding.swift
struct Balance { let balanceMinor: Int64 }   // paise

protocol BalanceProviding {
    func fetchBalance() async throws -> Balance
}

struct MockBalanceService: BalanceProviding {
    func fetchBalance() async throws -> Balance {
        Balance(balanceMinor: 2_500_000)        // ₹25,000
    }
}
Dependency injectionpass in any provider
Testinga mock, no network
Modular architectureswap implementations
SAY

Instead of forcing every provider into one class inheritance hierarchy, we define a protocol: BalanceProviding promises a fetchBalance function that returns a Balance. Any suitable type can conform, including a struct. MockBalanceService always returns ₹25,000, held as 2,500,000 paise.

SAY

The diagram: DashboardViewModel depends only on the protocol. The live BalanceService and the mock both conform, so either can be passed in.

SAY

Click: that is what makes dependency injection, testing without a network, modular architecture and interchangeable implementations possible. Lesson 1.6 covers protocols in depth; Unit 04, Lesson 4.5, builds the injection.
