Act 1 · Three entities

Installed app ≠ running process ≠ scene

App Bundle

On disk

  • Signed executable
  • Resources & metadata
  • Exists even when nothing runs
Process

In memory

  • OS-managed execution
  • Virtual address space + threads
  • Created only when needed
Scene

On screen

  • System-managed UI instance
  • Lives inside a process
  • One process can host multiple
📚

A recipe book (bundle) is not a working kitchen (process). The dining room (scene) is where the user interacts.

SAY

These three concepts are often confused. The bundle is files on disk. The process is an execution environment created by the OS. The scene is a UI instance — not the same as the process.

ASK

Can an installed app have zero running processes?

EXPECT

Yes. Installation does not create a process.

Act 4 · Execution context

A process is more than "calling a function"

The OS establishes:

  • Process identity & resources
  • Virtual address space with mapped regions
  • At least one execution thread
  • Sandbox & signing enforcement
🏢

An office building (process) with a floor plan (virtual memory) and workers (threads).

Is a process the same as a thread?
No. A process is the container; threads are workers inside it.

Mach-O is the executable format for Apple platforms.

  • Headers + load commands
  • Segments and sections
  • Metadata for loading
Is Mach-O the Swift programming language?
No. Mach-O is a binary format. Swift compiles into it.
.swift source is not interpreted on launch. It was compiled ahead of time.
SAY

Swift source goes through parsing, type checking, intermediate representation, LLVM code generation, linking, and signing. The result is a Mach-O binary in the app bundle.

Does dyld compile Swift source?
No. Compilation is build-time. dyld handles loading at runtime.
SAY

Act 7

Entering SwiftUI

@main, App, WindowGroup, and your first View

Act 7 · App entry point

The @main declaration

PocketBankApp.swift
import SwiftUI

@main
struct PocketBankApp: App {
    var body: some Scene {
        WindowGroup {
            DashboardView()
        }
    }
}
  • import SwiftUI — framework available
  • @main — app entry-point type
  • App protocol — SwiftUI application
  • WindowGroup — system-managed windows
  • DashboardView() — view description, not a drawing
App is not the OS process. WindowGroup is not a thread. DashboardView is not the window server.
SAY

This is the entire app entry point. @main tells the system which type starts the app. WindowGroup wraps your root view in a system-managed window.

ASK

Does @main create the OS process?

EXPECT

No. The process already exists. @main is a Swift abstraction within it.

Act 7 · Root view

The view is a description, not a drawing

DashboardView.swift
struct DashboardView: View {
    @State private var balanceText = "₹25,000"

    var body: some View {
        VStack(spacing: 20) {
            Text("PocketBank")
                .font(.largeTitle.bold())
            Text("Available balance")
            Text(balanceText).font(.title)
            Button("Refresh balance") {
                balanceText = "₹25,000"
            }
        }
        .padding()
    }
}
Does DashboardView() draw pixels?
No. It creates a view value. The framework renders it.
@State creates a source of truth. When balanceText changes, SwiftUI re-evaluates body — but only the parts that changed.
SAY

This is the root view. @State creates mutable state that SwiftUI manages. Body is a description, not a paint method.

Act 10 · Misconceptions

Five things that are not true

"The icon directly calls Swift."
No — system UI coordinates the action.
"An app is the same as its process."
No — bundle and process differ.
"A process is the same as a scene."
No — execution context vs UI instance.
"dyld compiles the app."
No — compilation is build time; dyld loads at runtime.
"SwiftUI body paints the screen."
No — it describes UI; frameworks render.
Correct all five and you understand the launch path.
