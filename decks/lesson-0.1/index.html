Does Swift begin executing the moment your finger touches the icon?

EXPECT

Most will say yes. The answer is no — the icon is system UI, not your app code.

Act 1 · Three entities

Installed app ≠ running process ≠ scene

App Bundle

On disk

  • Signed executable
  • Resources & metadata
  • Exists even when nothing runs
Process

In memory

  • OS-managed execution
  • Virtual address space + threads
  • Created only when needed
Scene

On screen

  • System-managed UI instance
  • Lives inside a process
  • One process can host multiple

A recipe book (bundle) is not a working kitchen (process). The dining room (scene) is where the user interacts.

SAY

These three concepts are often confused. The bundle is files on disk. The process is an execution environment created by the OS. The scene is a UI instance — not the same as the process.

ASK

Can an installed app have zero running processes?

EXPECT

Yes. Installation does not create a process.

When you tap the icon, you're interacting with SpringBoard — a system process. SpringBoard hands a launch or activation request to the system. The exact private daemons and IPC hops are undocumented and change between iOS versions, so we keep this conceptual. Your NPay code is not involved yet.

Act 3 · Launch paths · conceptual

Cold launch vs warm activation

If the process is still alive, the system reuses it. If not, it builds everything again.

Both paths end at the same place: UI becomes available.

SAY

If NPay's process is still alive, the system just foregrounds it. If not, it builds everything from scratch. The user experience looks the same.

SAY

A suspended process keeps its memory but does no ordinary work. Suspended is not the same as running, and the OS can end a suspended process at any time.

ASK

Does every icon tap create a new process (a new PID)?

EXPECT

No. An existing process may be foregrounded or activated.

Process creation

What the OS builds before your code runs

SAY

On a cold launch, the OS must build a process before any Swift code runs. What does that involve?

Act 4 · Execution context · conceptual

A process is more than "calling a function"

The OS establishes:

  • Process identity & resources
  • Virtual address space with mapped regions
  • At least one execution thread
  • Sandbox & signing enforcement
SAY

A new process is not just "calling a Swift function." The OS sets up an entire execution environment — identity, virtual memory, threads, and a security sandbox — all before your code runs.

SAY

These regions are conceptual, not a fixed physical layout. Virtual addresses are not physical RAM addresses, and mapping an executable does not mean it was all copied into RAM. Some code is shared from system caches.

ASK

Does every class live on the heap and every struct on the stack?

EXPECT

No. That is not a reliable Swift rule; the compiler decides storage. Likewise, a Swift Task is not the same thing as a thread.

ASK

Does code signing guarantee the app has no vulnerabilities? Can a sandboxed app share any data?

EXPECT

No to the first: signing proves origin and integrity, not safety. Yes to the second, but only through authorized mechanisms such as app groups or the share sheet.

SAY

Think of an office building (process) with a floor plan (virtual memory) and workers (threads). The building exists before anyone does any work in it.

What happens at build time

Act 5 · Build time

The compilation pipeline

Mach-O is the executable format for Apple platforms.

  • Headers + load commands
  • Segments and sections
  • Metadata for loading
.swift source is not interpreted on launch. It was compiled ahead of time.
SAY

Swift source goes through parsing, type checking, intermediate representation, LLVM code generation, linking, and signing. The result is a Mach-O binary in the app bundle.

CONNECT

When the user taps, the system loads this binary. That's dyld's job.

Act 6

dyld & runtime preparation

Loading the binary before your code runs

SAY

Back to launch day. The binary exists and the process exists; something has to connect them.

Act 6 · Runtime loading · conceptual

dyld: the dynamic loader

dyld prepares executable images and their dependencies at runtime.

Before a play begins, the stage crew (dyld) prepares props and sets. The crew is not the playwright (compiler).

SAY

dyld loads the Mach-O binary, resolves dependencies, binds symbols, and runs initializers. Only then does your Swift code start.

SAY

System frameworks like SwiftUI and Foundation come from the dyld shared cache, prepared ahead of time by Apple. That is why they load quickly; your own embedded frameworks do not get that benefit.

Act 7

Entering SwiftUI

@main, App, WindowGroup, and your first View

SAY

Finally, our code. Everything before this point was the system's work.

Act 7 · App entry point

The @main declaration

NPayApp.swift
import SwiftUI

@main
struct NPayApp: App {
    var body: some Scene {
        WindowGroup {
            DashboardView()
        }
    }
}
  • import SwiftUI — framework available
  • @main — app entry-point type
  • App protocol — SwiftUI application
  • body: some Scene — the app's scenes
  • WindowGroup — system-managed windows
  • DashboardView() — view description, not a drawing
App is not the OS process. WindowGroup is not a thread. DashboardView is not the window server.
SAY

This is the entire app entry point. @main tells the system which type starts the app. WindowGroup wraps your root view in a system-managed window.

ASK

Does @main create the OS process?

EXPECT

No. The process already exists. @main is a Swift abstraction within it. Also avoid saying App.init is the first machine instruction: dyld, runtime setup and initializers run before it.

Act 7 · Root view

The view is a description, not a drawing

DashboardView.swift
struct DashboardView: View {
    @State private var balanceText = "₹25,000"

    var body: some View {
        VStack(spacing: 20) {
            Text("NPay")
                .font(.largeTitle.bold())
            Text("Available balance")
            Text(balanceText).font(.title)
            Button("Refresh balance") {
                balanceText = "₹25,480"
            }
        }
        .padding()
    }
}
@State creates a source of truth. Tap Refresh and balanceText changes: SwiftUI re-evaluates body, then updates only what changed on screen.
SAY

This is the root view. @State creates mutable state that SwiftUI manages. Body is a description, not a paint method.

Act 7 · View hierarchy · conceptual

From view values to a screen

SAY

Views compose into a tree. WindowGroup holds the root view, DashboardView's body returns a VStack, and the VStack holds three Texts and a Button. Nothing here is a drawing command.

SAY

A typical iPhone app has one main scene. On iPadOS, one process can show several scenes (windows) at once, each with its own view tree.

ASK

Can one process have more than one scene?

EXPECT

Yes, on supported platforms and configurations, notably iPadOS.

Launch performance

What makes startup slow, and how to investigate

SAY

We know the path. Where can it get slow, and how do we find out?

Act 9 · Comparison

What a cold launch costs

ConcernCold launchWarm activation
New OS processTypically yesNo (if surviving)
Loading & initFull setupMay reuse state
In-memory stateMust rebuildMay survive
Scene activationYesYes
Fresh backend dataOften usefulOften useful
Startup cost sources
  • Excessive synchronous init
  • Blocking the main thread
  • Heavy work before first frame
  • Dependency loading overhead
  • Expensive initial UI work
SAY

Remember from the launch fork: process survival is never guaranteed. The OS can end any background app, so never design around "it will still be in memory".

ASK

Should we optimize dyld first when startup is slow?

EXPECT

Not without measuring. Use Instruments to find the actual bottleneck.

ASK

What happens to in-memory state when the OS ends the process?

EXPECT

It is lost. Anything that matters must be persisted and restored on the next launch.

ASK

Does using await make launch faster?

EXPECT

Not by itself. Async startup work can help keep the main thread free, but async alone does not guarantee a faster first frame.

Act 9 · Engineering method

Measure, don't guess

"dyld is always the bottleneck." Not necessarily. Every app is different. Measure first.
Hypothesis → measurement → change → remeasurement. Never optimize without data.
SAY

Performance investigation follows a strict loop. Avoid generic claims. Use Instruments, find the real bottleneck, fix it, verify.

Act 10 · End to end · conceptual

From tap to first frame

One tap crosses five ownership boundaries before the first frame appears.
SAY

The whole journey: tap, SpringBoard coordinates, process created, dyld loads binary, @main enters Swift, SwiftUI evaluates views, layout, compositing, first frame.

ASK

Which of these boxes does NPay's code own?

EXPECT

Only @main and Views. Everything else belongs to the system.

SAY

An app icon is only the visible doorway. The system receives the user's action and decides whether to activate an existing app process or start a new one. For a new launch, iOS establishes a protected process environment. The executable and its dependencies are prepared, Swift application entry executes, SwiftUI establishes a scene and root view, and the graphics pipeline eventually presents the first frame. From one tap, we have crossed the boundaries between user experience, system execution, compiled code, framework abstractions and display rendering.

Act 10 · Misconceptions

Five things that are not true

MythReality
“The icon directly calls Swift.”System UI coordinates the launch first.
“An app is the same as its process.”The bundle is on disk; a process is created on demand.
“A process is the same as a scene.”Execution context vs UI instance.
“dyld compiles the app.”Compilation is build time; dyld loads at runtime.
“SwiftUI body paints the screen.”It describes UI; the frameworks render it.
Correct all five and you understand the launch path.
SAY

These are the five most common misconceptions. If you can explain why each is wrong, you've internalized the full journey.
