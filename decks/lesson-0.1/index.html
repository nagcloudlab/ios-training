Before going further, separate three things people mix up: the installed app, the running process and the scene.

Part 1 · Three entities

Installed app ≠ running process ≠ scene

App Bundle

On disk

  • Signed executable
  • Resources & metadata
  • Exists even when nothing runs
Process

In memory

  • OS-managed execution
  • Virtual address space + threads
  • Created only when needed
Scene

A UI instance

  • System-managed UI (a window)
  • Foreground or background
  • One process can host several

A recipe book (bundle) is not a working kitchen (process). The dining room (scene) is where the user interacts.

SAY

These three concepts are often confused. The bundle is files on disk. The process is an execution environment created by the OS. The scene is a UI instance — not the same as the process. It is not simply "what is on screen": a scene can move to the background, and the system can disconnect it while the process lives on.

ASK

Can an installed app have zero running processes?

EXPECT

Yes. Installation does not create a process.

Let's zoom into step one: who actually receives the tap?

Part 2 · System UI · conceptual

SpringBoard handles the tap

A system processPart of iOS; none of NPay’s code runs here
Owns the Home ScreenDraws icons and badges; runs the app switcher
Coordinates the launchAsks the system: launch NPay or bring it forward
SAY

One: SpringBoard is a system process that starts when the iPhone boots. The Home Screen is SpringBoard's interface, not NPay's. The NPay icon is just an image from NPay's bundle that SpringBoard draws, so showing it never runs NPay's code, and nothing in our Swift code can react to the tap itself. In the hotel picture, SpringBoard is the front desk: guests ask it for their room, but it never goes inside.

SAY

Two: it owns the system interface around apps: the icon grid, folders and badges, and the app switcher. Our app can set a badge number through notification APIs, but SpringBoard draws it. Switcher cards are snapshots, so an app is not necessarily running while you see its card.

SAY

Three: on a tap it does not start NPay itself. It asks the system to open the app. If NPay's process is still alive, the system just brings it forward; if not, it creates a new process. Meanwhile the system plays the icon animation and shows the app's launch screen until the first frame is ready.

SAY

When you tap the icon, you're interacting with SpringBoard — a system process. SpringBoard hands a launch or activation request to the system. The exact private daemons and IPC hops are undocumented and change between iOS versions, so we keep this conceptual. Your NPay code is not involved yet.

Part 2 · Launch paths · conceptual

Cold launch vs warm activation

If the process is still alive, the system reuses it. If not, it builds everything again.

Both paths end at the same place: UI becomes available.

SAY

If NPay's process is still alive, the system just foregrounds it. If not, it builds everything from scratch. The user experience looks the same.

SAY

A suspended process keeps its memory but does no ordinary work. Suspended is not the same as running, and the OS can end a suspended process at any time.

Part 3 · Execution context · conceptual

A process is more than "calling a function"

On disk, an app is executable code and resources. A process is a running instance of it.

The OS establishes:

  • Process identity & resources
  • Its own virtual memory
  • At least one execution thread
  • Sandbox & signing enforcement

Lesson 0.6 opens up this memory: stack, heap and ARC.

SAY

A new process is not just "calling a Swift function." The OS sets up an entire execution environment — identity, virtual memory, threads, and a security sandbox — all before your code runs.

SAY

Virtual memory means each process sees its own private address space. Virtual addresses are not physical RAM addresses. What lives inside that space (stack, heap, how ARC frees objects) is Lesson 0.6; today we only need to know the process has its own.

ASK

Does code signing guarantee the app has no vulnerabilities? Can a sandboxed app share any data?

EXPECT

No to the first: signing proves origin and integrity, not safety. Yes to the second, but only through authorized mechanisms such as app groups or the share sheet.

Part 4 · Build time

The compilation pipeline

Mach-O is the executable format for Apple platforms.

  • Headers + load commands
  • Segments and sections
  • Metadata for loading
.swift source is not interpreted on launch. It was compiled ahead of time.
SAY

Swift source goes through parsing, type checking, intermediate representation, LLVM code generation, linking, and signing. The result is a Mach-O binary in the app bundle.

CONNECT

When the user taps, the system loads this binary. That's dyld's job.

Part 4 · Runtime loading · conceptual

dyld: the dynamic loader

dyld prepares executable images and their dependencies at runtime.

dyld loads and links code that was compiled earlier, on your Mac. It never compiles anything.
SAY

dyld loads the Mach-O binary, resolves dependencies, binds symbols, and runs initializers. Only then does your Swift code start.

SAY

System frameworks like SwiftUI and Foundation come from the dyld shared cache, prepared ahead of time by Apple. That is why they load quickly; your own embedded frameworks do not get that benefit.

Part 4 · App entry point

The @main declaration

NPayApp.swift
import SwiftUI

@main
struct NPayApp: App {
    var body: some Scene {
        WindowGroup {
            DashboardView()
        }
    }
}
1@mainIdentifies the entry-point type. Swift synthesizes the startup entry mechanism.
2struct NPayApp: AppDefines the app with SwiftUI’s App protocol. SwiftUI manages lifecycle integration.
3var body: some SceneDeclares the scenes: managed portions of the app’s interface.
4WindowGroup { DashboardView() }Windows holding the root view. iOS manages scene creation and presentation.
SAY

Read this code in four stages, one per click. @main marks the entry-point type. NPayApp conforms to App, so SwiftUI handles lifecycle integration. body declares the scenes. WindowGroup holds the root view, and iOS manages creating and presenting the scene.

SAY

Important: DashboardView() is not a command to draw pixels immediately. It creates a view value describing the interface; SwiftUI evaluates, updates and renders it. App is not the OS process, and WindowGroup is not a thread.

ASK

Does @main create the OS process?

EXPECT

No. The process already exists. @main is a Swift abstraction within it. Also avoid saying App.init is the first machine instruction: dyld, runtime setup and initializers run before it.

Part 5 · Root view

The view is a description, not a drawing

DashboardView.swift
struct DashboardView: View {
    @State private var balanceText = "₹25,000"

    var body: some View {
        VStack(spacing: 20) {
            Text("NPay")
                .font(.largeTitle.bold())
            Text("Available balance")
            Text(balanceText).font(.title)
            Button("Refresh balance") {
                balanceText = "₹25,480"
            }
        }
        .padding()
    }
}
You describe what the interface should look like for the current state. The framework manages how to update the screen.
@State creates a source of truth. Tap Refresh and balanceText changes: SwiftUI re-evaluates body, then updates only what changed on screen.
SAY

This is the root view. @State creates mutable state that SwiftUI manages. Body is a description, not a paint method.

SAY

SwiftUI is declarative. If you know React or Jetpack Compose, the idea is the same: describe the UI for the current state and let the framework work out the updates.

Part 5 · Rendering · conceptual

The first-frame journey

body may be re-evaluated without redrawing the entire screen.

First visible frame and fully interactive are not the same milestone.
SAY

The scene connects first, still in the inactive state. SwiftUI evaluates view descriptions, diffs changes, resolves layout, and composites graphics. The result is the first frame. Only after that does the scene become active and start receiving touches.

SAY

Now the main-thread lane. The first frame can be on screen while the main thread is still busy with heavy synchronous work. Until that work finishes, taps wait in line. Only then is the app fully interactive.

ASK

Should we optimize dyld first when startup is slow?

EXPECT

Not without measuring. Use Instruments to find the actual bottleneck.

ASK

EXPECT

It is lost. Anything that matters must be persisted and restored on the next launch.

ASK

Does using await make launch faster?

EXPECT

Not by itself. Async startup work can help keep the main thread free, but async alone does not guarantee a faster first frame.

Lesson 0.1 · Lab

Order the launch, read the bundle

No Xcode needed: work from cards and a file listing.

  1. Put the cards in order: tap, SpringBoard, launch request, process + sandbox, dyld, @main, scene (inactive), first frame, active.
  2. Mark each card’s owner: system, loader, your code or frameworks.
  3. Cross out the cards a warm activation can skip.
  4. Label every item in the bundle: executable, metadata, resources or signature.
NPay.app (simplified)

├── NPay
├── Info.plist
├── Assets.car

│   └── CodeResources

SAY

The lab needs no Mac. Hand out nine cards in random order. Pairs order them, mark the owner of each, then cross out what a warm activation skips. Then label the NPay bundle listing on the right.

EXPECT

Order: tap, SpringBoard, launch request, process + sandbox, dyld, @main, scene (inactive), first frame, active. Owners: tap and SpringBoard, launch request, process creation = system; dyld = loader; @main = your code; scene, first frame, active = frameworks and system together. A warm activation skips launch request to @main: the process already exists. Bundle: NPay = Mach-O executable; Info.plist = metadata; Assets.car = compiled resources (images, colours); PrivacyInfo.xcprivacy = metadata (privacy manifest); embedded.mobileprovision = signing (provisioning profile, device builds only); _CodeSignature/CodeResources = signature; Frameworks/ = embedded libraries dyld loads.

Practice · Exercises

Hands-on exercises

A: Responsibility map

Draw Home Screen system UI, the NPay process, its scene, a SwiftUI view, the kernel and hardware. Explain every boundary.

B: Cold vs warm

Draw both launch paths. Mark which stages a warm activation can reuse, and explain why survival is not guaranteed.

C: Source to binary (optional, Mac)

On a Mac, find your built app in Xcode's build products and run file and otool -l on the executable.

D: Blank screen

The app shows a blank screen at launch. Write three hypotheses and the measurement that would test each one.

Exercise C needs macOS with Xcode; the others need only paper. Use the real path from Xcode’s build products; don’t guess bundle paths.

LIVE DEMO

Before the exercises: create a new iOS SwiftUI App in Xcode, open the @main App and its WindowGroup, replace the root view with DashboardView, and run it in the Simulator. Point at each part and say whether it is Swift language, SwiftUI framework, OS-managed scene or process. If time allows, open Instruments for a first look at launch.

ASK

For exercise D: what is the first thing you would measure?

EXPECT

Time to first frame and what the main thread is doing during it. Never claim a cause before measuring.
