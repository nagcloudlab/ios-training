Part 3 · UserDefaults

Saving a preference

Settings.swift
import Foundation

// Save a preference
UserDefaults.standard.set(
    true,
    forKey: "darkModeEnabled"
)

// Read a preference
let darkMode = UserDefaults.standard.bool(
    forKey: "darkModeEnabled"
)

print(darkMode)
Good for

Selected theme, onboarding completion, preferred language, simple app settings.

Avoid for

Large structured datasets, or as a secure credential store. Tokens go in the Keychain (Lesson 0.7).

SAY

Saving and reading a boolean preference is one line each. UserDefaults suits small settings: theme, onboarding completion, preferred language, simple app settings.

SAY

Avoid it as a database for large structured data, and never as a store for credentials: as we saw in Lesson 0.7, a token belongs in the Keychain.

Part 4 · SwiftData

A persistent model

SwiftData is not an in-memory array that saves itself. Learn containers, contexts, relationships, schema evolution and save behavior.
TransactionNote.swift
import Foundation
import SwiftData

@Model
final class TransactionNote {
    var title: String
    var amountMinor: Int64   // paise

    init(title: String, amountMinor: Int64) {
        self.title = title
        self.amountMinor = amountMinor
    }
}

Money as whole paise in an Int64, like balanceMinor. @Model objects are not Sendable: use them on their context’s actor. Unit 06 · 6.2 builds this.

SAY

The SwiftUI screen works through a SwiftData ModelContext, which persists to model storage. @Model marks TransactionNote as a persistent model; SwiftData manages persistence through its model container and context. The amount is stored as whole paise in an Int64, the same convention as balanceMinor, so there are no rounding surprises.

SAY

One line for later: @Model objects are not Sendable. Use them on the actor that owns their context, which for UI work is the main actor. Unit 06, lesson 6.2, covers models, contexts and containers in depth.

SAY

SwiftData is not simply an in-memory array that automatically saves every variable. Developers still need to understand model containers, contexts, relationships, schema evolution and save behavior.

Part 5 · Sandbox directories

Where an app keeps its files

DirectoryTypical purposeBacked up
DocumentsDocuments the user creates; can be shown in FilesYes
Application SupportApp-managed data, hidden from the userYes
CachesRe-downloadable content, e.g. the statement PDFNo
TemporaryShort-lived filesNo
The system can remove cached and temporary content. Don’t treat those directories as permanent.
Statement.swift
import Foundation

// Re-downloadable: Caches
func saveStatement(_ pdf: Data) throws {
    let url = URL.cachesDirectory
        .appending(path: "statement.pdf")
    try pdf.write(to: url, options: .completeFileProtection)
}

// App-managed data: Application Support
let store = URL.applicationSupportDirectory
    .appending(path: "npay.store")

.completeFileProtection: the file stays encrypted while the device is locked. Unit 06 · 6.5 covers backups and data protection.

SAY

Apps have directories inside their sandbox. Documents is for documents the user creates; it is backed up and can be shown in the Files app, so it is not the place for app internals. Application Support holds app-managed data, backed up but hidden. Caches holds content that can be downloaded again, and Temporary holds short-lived files; the system can remove both.

SAY

NPay can download a statement again at any time, so it goes in Caches. The code uses the modern URL API, URL.cachesDirectory appending a path, and writes with complete file protection, which keeps the file encrypted while the device is locked. App data such as a store goes in Application Support.

Part 7 · Termination · conceptual

A draft that may not survive

Persist important data before the app can lose its memory. Do not depend on a final termination callback.

For drafts, save periodically or on meaningful changes, minding performance, security and consistency.

Unit 06 · 6.9 covers drafts and state restoration, including @SceneStorage.

SAY

The user types "Rent payment" as a transfer note. In the first version it exists only in memory: when iOS terminates the process and the user relaunches, it is gone. Click: in the second version the draft was saved, so it comes back.

SAY

Important data should be persisted before the app can lose its in-memory state. Do not rely on a termination callback; save periodically or when meaningful changes happen.

Part 9 · Comparison · conceptual

Four persistence technologies

New SwiftUI app

SwiftData is often a good start, when its capabilities and deployment targets fit.

Existing or advanced

Unit 06 · 6.1 compares them in practice.

SAY

SwiftData is a Swift-native framework with model-oriented APIs. Core Data is a mature object-graph and persistence framework. SQLite is an embedded relational database engine. FileManager does filesystem operations, not database object management.

SAY

Read the drawing top to bottom: SwiftData and Core Data both persist through an SQLite-backed store, which in the end is files in the sandbox; FileManager works with files directly. Their programming models are not the same as writing SQL. For a new SwiftUI app, SwiftData is often a good start; Core Data remains important for existing apps and advanced needs.

What to remember

Three things to remember. Choose storage by what the data is: preferences in UserDefaults, records in SwiftData, files in the right directory, secrets in the Keychain. @State lives with the view’s identity inside the running process. When the process ends, it is gone; data that must survive needs persistent storage.
