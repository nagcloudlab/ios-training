A text field has two jobs: read the current value to display it, and write the edited value as the user types. A plain String only gives it a value; a Binding of String gives it a read and write connection.

Part 3 · Keyboard to SwiftUI state (sections 4, 12) · conceptual

From a key to a visible update

Not one key = one character
  • Tamil, Hindi: composition, several events
  • Use platform text input, not raw key events
  • A system experience, not a SwiftUI view
  • Keep per-keystroke work cheap; debounce later
SAY

Conceptually; the text’s widget showed only stage 5. Click: the user types on the system keyboard. Click: the platform’s text-input system handles it, including composition, selection and autocorrection. Click: the text field’s edited text changes. Click: SwiftUI writes the new string through the binding. Click: the @State owner receives it. Click: views that depend on it update.

SAY

Click: one key press is not always one character. Tamil and Hindi, among others, compose characters from several input events. That is why ordinary text entry should use the platform’s text-input APIs, not raw key events. Our test entered text through UIKit’s text-input protocol, the same entry point keyboards use.

SAY

Click: the keyboard itself is part of the system input experience; we never build it in SwiftUI. And because every accepted edit can update state, keep per-keystroke work cheap: no network call per keystroke. Debouncing and async validation come later.

Part 4 · Why amounts start as Strings (sections 6, 8)

Keep the text; parse it carefully

Typing 1500: onChange

"" → "1"
"1" → "15"
"15" → "150"
"150" → "1500"

String while editing
  • Holds intermediate text
  • Empty, a lone ".", partial input
Decimal(string:) alone (Mac)

"12abc" → 12
"1,500" → 1
"-500" → -500
"" → nil

Parsing isn’t validation
  • Stops at the first bad character
  • Also check syntax and rules
Money as Double vs Decimal (Mac)

Double 0.1 + 0.2 == 0.3: false
(0.30000000000000004)
Decimal 0.1 + 0.2 == 0.3: true

  • Never Double as the source of truth
  • Decimal, or integer minor units (Unit 01)
SAY

Typing 1500 goes through empty, 1, 15, 150, 1500: our onChange log. A user might also briefly have an empty field or just a decimal point. Keeping amountText as a String while editing preserves those intermediate states; converting every keystroke to a number would fight the user.

SAY

Click: then parse it carefully. Decimal(string:) on its own is lenient: "12abc" became 12, and "1,500" became 1, because it stops at the first character it cannot use. So parsing is not validation: we also check the syntax and the business rules, which is what the form does.

SAY

Click: and never use Double as the authoritative representation of money. In binary floating point, 0.1 plus 0.2 is 0.30000000000000004, not 0.3; Decimal gets it right. Real money uses Decimal or integer minor units, paise, as in Unit 01. Today’s form is a UI-only demo.

Part 6 · Focus management (sections 9, 19)

Which field has the keyboard?

PaymentForm (focus parts)
@FocusState private var focusedField: Field?
enum Field: Hashable { case recipient, amount }

TextField("Recipient ID (e.g. ravi@npay)", text: $recipient)
    .focused($focusedField, equals: .recipient)
    .submitLabel(.next)
    .onSubmit { focusedField = .amount }

.toolbar {                         // on the form
    ToolbarItemGroup(placement: .keyboard) {
        Spacer()
        Button("Done") { focusedField = nil }
    }
}
Return in the recipient field

focused after return:
UITextField, placeholder Amount (₹)

type(of:)

_amountFocused: FocusState<Bool>
$amountFocused: Binding

  • @State: the view’s own data
  • @FocusState: which control is focused
SAY

@FocusState connects a property to the focus of focusable controls. With an optional enum, Field, one property says which of several fields has focus, or nil for none. .focused($focusedField, equals: .recipient) ties the recipient field to that case. .submitLabel(.next) labels the return key, and .onSubmit moves focus to the amount field. Setting focusedField = nil clears focus and hides the keyboard; the Done button in a keyboard toolbar does exactly that, and it is visible above the decimal pad on the previous slide.

SAY

Click: we entered ravi@npay and sent a return: the first responder became the Amount field. onSubmit moved the focus.

SAY

Click: like @State, it is a property wrapper: _amountFocused is a FocusState of Bool, and $amountFocused a binding. Click: but a different concern: @State is the view’s own data; @FocusState is which control is focused.

Part 7 · Validate against the demo balance (sections 10, 17)

Syntax, then rules, then the balance

PaymentForm validation
private var isValidAmount: Bool {
    let pattern = #"^[0-9]+(\.[0-9]{1,2})?$"#
    guard amountText.range(of: pattern,
                           options: .regularExpression) != nil
    else { return false }
    guard let amount = Decimal(string: amountText,
              locale: Locale(identifier: "en_US_POSIX"))
    else { return false }
    return amount > 0
        && amount <= Decimal(availableBalance)
}

SAY

PaymentForm’s validation in three steps. A regular expression checks the syntax: digits, optionally a point and one or two digits. Then Decimal parses it, which after the regex is safe. Then the rules: greater than zero, and not more than the available balance, which the form now receives from ContentView as a let. Continue Demo is disabled unless the recipient is not blank and the amount is valid.

SAY

Click: we ran the text’s whole table: 1500 and 25,000 valid; 25,001, 0, 12.345, abc and -500 invalid, exactly as the text predicts. On the right, the real form with 25001: the red message and a disabled button, with the decimal pad and Done still up.

SAY

Click: and it reacts to the balance too. We typed 25500: invalid at ₹25,000. Then we activated + ₹1,000 in the balance editor: the balance became 26,000, the form received the new value, and Continue Demo enabled itself. isValid is computed from both local input and the input value.

Part 7 · Three responsibilities (sections 11, 16)

Where today’s validation sits

NPay today
  • PaymentForm owns its input and focus state
  • Local validation, then prints a request
  • Does not replace backend validation
  • No financial transaction happens
SAY

Three separate responsibilities. The input experience: keyboard type, placeholder, focus, formatting. Client-side validation, highlighted, which is what we built: required fields, syntax, limits and feedback. And trusted business validation: the authoritative balance, permissions, transaction rules and security, which belongs to the backend.

SAY

In NPay, PaymentForm is added below the quick actions; it owns its own input and focus state and only prints a demo request. Click: a disabled button is a convenience, not security: it never replaces backend validation, and no transaction happens.

Lesson 2.11 · Recap

What to remember

TextField writes a binding
keyboard → binding → @State

Validate the value
keyboard type is only a hint

Focus is state too
@FocusState, onSubmit, Done

SAY

Three things to remember. A TextField reads and writes text through a Binding of String, so the keyboard ends up changing your @State and SwiftUI updates the rest. Validate the value itself, syntax then rules then the balance, because a decimal pad is only a hint and paste bypasses it; and the backend has the final word. And focus is state: @FocusState says which field has the keyboard, onSubmit moves it, and Done clears it.
