Part 2 · What is Text? (section 3)

Text("NPay") makes a value

PartMeaning
TextSwiftUI struct
(...)initializer call
"NPay"string literal
Resulta Text value describing UI content
  • No: a declarative view value
  • SwiftUI lays out and renders it separately
Values.swift
struct Customer {
    let name: String
}

let customer = Customer(name: "Ravi")  // a Customer value
let title = Text("NPay")               // a Text value
Same mechanism, different purpose
  • Customer models domain data
  • Text describes interface content
SAY

Text is not a function, not a class and not a UIKit object. It is a struct defined in SwiftUI, and it conforms to the View protocol. Text is the type, the parentheses call an initializer, "NPay" is a string literal, and the result is a Text value describing UI content.

SAY

Click: does Text("NPay") draw pixels immediately? No. It creates a declarative view value; SwiftUI does layout and rendering separately.

SAY

Click: you have seen this mechanism in Unit 01. Customer(name: "Ravi") creates a Customer value; Text("NPay") creates a Text value. The difference is purpose: Customer models domain data, Text describes interface content.

Part 2 · How Swift finds Text (section 4)

From import SwiftUI to a Text value

At compile time
  • Imported module information resolves Text

SAY

Five steps, all in the compiler. Click: import SwiftUI makes SwiftUI’s declarations available. Click: the compiler resolves the name Text to SwiftUI’s type. Click: it processes the string literal "NPay". Click: overload resolution picks a compatible Text initializer. Click: the result is a Text value, a statically typed view description.

SAY

Part 3 · The View protocol (section 5)

Conformance, not inheritance

View (mental model)
// Teaching approximation, not Apple's exact API

protocol View {
    associatedtype Body: View

    @ViewBuilder
    var body: Body { get }
}
The parts
  • Body: each view’s own body type
  • body: the view’s content
  • @ViewBuilder: composing child views
Real interface, iOS 26.5 SDK

associatedtype Body : View
@ViewBuilder @MainActor var body: Self.Body { get }

  • ContentView doesn’t inherit from Text
  • Its body returns something that is a View
SAY

struct ContentView: View is protocol conformance, not class inheritance; we studied protocols in Unit 01. Here is a simplified model of View: an associated type Body that must itself be a View, a body property of that type, and @ViewBuilder, which lets you compose child views declaratively.

SAY

ContentView satisfies the protocol because its body produces a Text, and Text also conforms to View. Both sit under the same protocol.

SAY

Click: the real interface is close to our model; the two requirement lines say the same thing, and add that body runs on the main actor, as in Lesson 1.9.

SAY

Click: ContentView does not inherit from Text. It only needs to return a view description that satisfies View.

Part 3 · some View (section 6)

some View: one concrete type, hidden

ContentView.swift
var body: some View {
    Text("NPay")
}
Compiler’s view
Declaredsome View
Underlying typeText
RequirementText conforms to View
type(of: body), in the simulator

ContentView.body: Text
with a .frame (Part 5):
ModifiedContent<Text, _FlexFrameLayout>

  • One underlying type per declaration
  • Not a different type on each evaluation
  • Matters for conditional views, later
SAY

Why some View and not just View? some View is an opaque return type, from Lesson 1.6. The implementation returns one specific concrete type that conforms to View, and hides which one from callers. The compiler knows: declared some View, underlying type Text, and Text conforms to View.

SAY

Click: we printed type(of:) on the body in the simulator. ContentView’s body is exactly Text. Add the .frame from Part 5 and the hidden type becomes ModifiedContent of Text and a frame layout: still one type, just a different one. The underscore name is SwiftUI’s private implementation type.

SAY

Click: some View does not let body return a different concrete type each time it runs. The opaque type is fixed for that declaration. We will see why that matters when we write conditional views.

Part 5 · Measuring text (section 9)

Parents propose, text chooses, parents place

Text measurement uses
  • Font metrics
  • Glyph advances
  • Line breaks
… and
  • Language
  • Proposed size
  • So text adapts to device widths
SAY

Text has an intrinsic content size under given constraints: "NPay" in a small font needs less space than "Welcome to NPay" in a large one. SwiftUI’s layout runs in three moves. Click: the parent proposes a size. Click: the child, our Text, chooses its own size within that proposal. Click: the parent positions the child.

SAY

Click: behind the scenes, text measurement considers font metrics, glyph advances, line breaks, the language, and the proposed size. The text system finds a layout; SwiftUI positions the result. That is why text responds naturally to different device widths.

Part 6 · Font styling (section 10)

.largeTitle is inferred from context

ContentView.swift
Text("NPay")
    .font(.largeTitle)        // short form

Text("NPay")
    .font(Font.largeTitle)    // long form
Two words
  • .font(): a SwiftUI modifier
  • .largeTitle: a semantic font style
Contextual type inference (Unit 01)
  • .font expects a Font
  • so .largeTitle means Font.largeTitle
Why semantic fonts
  • .body, .title, .largeTitle follow platform typography
  • and Dynamic Type: the user’s chosen text size (Part 8)
SAY

.font is a SwiftUI modifier. .largeTitle is a semantic font style. The long form is Font.largeTitle; both lines mean the same.

SAY

Click: why can we drop Font? Because the compiler knows .font expects a Font value, so .largeTitle is looked up on Font. That is contextual type inference from Unit 01, the same reason you can write .red where a Color is expected.

SAY

Click: why semantic styles instead of a point size? .body, .title and .largeTitle follow the platform’s typography and Dynamic Type, which lets users choose their preferred text size for accessibility. We will see it working on the final code.

Why
  • Text’s own .font overload returns Text

SAY

A temporary experiment. Take a Text, make a styled copy with .font and a padded copy with .padding, and print each type. It needs a SwiftUI context; we ran it in a view’s task in the simulator. Predict first: what are the three types?

SAY

Click: the real console. original is Text. styled is also Text, because Text has its own .font overload that returns Text. padded is ModifiedContent of Text and a padding layout: a wrapper description around the original.

SAY

Click: not every modifier produces the same kind of type. Text-specific modifiers can keep Text; general View modifiers usually wrap. Part 6 · Modifier order (section 12)

Same modifiers, different order, different result

A: padding, then background
Text("NPay")
    .padding()
    .background(.yellow)
A
  • Background covers the padded area
B: background, then padding
Text("NPay")
    .background(.yellow)
    .padding()
B
  • Background covers the text only

A above, B below (.largeTitle)

  • Both take 109.3 × 80.7 pt: same layout size, different structure
  • Modifiers aren’t decoration; each wraps the one before
SAY

Two versions with the same two modifiers in a different order. We ran both, stacked, at largeTitle so they are easy to see: A on top, B below.

SAY

Click: in A, padding wraps the text first, then the background wraps the padded view, so yellow fills the padded area. Click: in B, the background wraps just the text, then padding adds space outside it, so the yellow is tight around the word.

SAY

Click: we measured both: each takes exactly the same space, 109.3 by 80.7 points. The layout size is the same; the structure, and so the result, differs. Modifiers are applied in sequence, and each one wraps the description before it. This is one of the most important ideas in SwiftUI.
