Part 1 · Reconciliation (section 11) · conceptual

Same screen, one value different

  1. The balance state changes
  2. SwiftUI finds the dependencies on it
  3. Relevant descriptions may be re-evaluated
  4. It decides what managed UI needs updating
  5. Layout, graphics and presentation run as needed
  • No public, fixed tree-diff algorithm
  • Dependency tracking and identity, largely private
SAY

NPay’s dashboard: a heading, the balance and a Send Money button. A transaction completes and the balance becomes ₹30,000. Click: in the new description only the balance differs.

SAY

Click: conceptually, the balance state changes; SwiftUI identifies what depends on it; those descriptions may be re-evaluated; it works out which managed UI needs updating; then layout, graphics and presentation happen as required. Like a restaurant’s order display: when one order goes from Preparing to Ready, nobody rebuilds the kitchen; the display updates that line.

SAY

Click: do not teach this as React’s virtual DOM diff. SwiftUI does not publish a fixed tree-comparison algorithm; its dependency tracking, identity and update mechanisms are more sophisticated and mostly private. Our evidence next comes from logging, not from reading its internals.

struct HeaderView: View {
    var body: some View {

DashboardView body evaluated, balance 25000
HeaderView body evaluated
DashboardView body evaluated, balance 26000
DashboardView body evaluated, balance 27000

OperationMeans
View initializationa Swift value is built
body evaluationa new description is computed
Renderingpixels are prepared and shown
SAY

A dashboard with a print in body, and a HeaderView that depends on nothing. We ran it in the iOS Simulator and changed the balance twice, the way a button would.

SAY

Click: the real console. The dashboard’s body ran three times: once at first, then after each change. The header’s body ran once. SwiftUI only re-evaluated what depended on the balance. The prints are for teaching and debugging; never build app logic on how often body runs.

SAY

Click: keep three operations apart. Initializing a view struct builds a value. Evaluating body computes a new description. Rendering prepares and presents pixels. If body runs ten times, the GPU does not necessarily draw the whole screen ten times.

Part 2 · Views are structs (section 13)

Cheap values, recreated freely

BalanceCard.swift
struct BalanceCard: View {
    let title: String
    let balanceText: String     // from the ViewModel

    var body: some View {
        VStack(alignment: .leading) {
            Text(title)
            Text(balanceText).font(.largeTitle)
        }
    }
}
A struct (1.5)
  • Value semantics: a configuration
  • Not a permanent on-screen object
SwiftUI owns the rest
  • State, identity, rendering
  • No expensive work or side effects in body
SAY

Structs have value semantics, which suits describing a UI configuration. BalanceCard says: a title and a balance, in a vertical stack. It takes balanceText already formatted, as the ViewModel does in NPay.

SAY

A view struct is not a permanent object that represents one element on screen. SwiftUI may recreate view values constantly as part of normal updates; the state, identity and rendering infrastructure live in SwiftUI.

SAY

Click: so keep body pure: no expensive work, no side effects like network calls. Part 6 comes back to this.

Part 3 · Structural identity (section 14)

Switch branches, lose the state

NPayScreen.swift
struct NPayScreen: View {
    @State private var showPremium = false

    var body: some View {
        VStack {
            Toggle("Premium Mode", isOn: $showPremium)
            if showPremium {
                CounterView(name: "Premium")  // own @State
            } else {
                CounterView(name: "Standard")
            }
        }
    }
}
iOS Simulator console

StandardCounterView appeared, count = 0
Standard counted to 3
PremiumCounterView appeared, count = 0
Premium counted to 3
StandardCounterView appeared, count = 0

  • Not object identity: position and structure in the hierarchy
SAY

A Premium Mode toggle chooses between two branches, each a counter with its own @State count. SwiftUI uses view identity to attach state to the right part of the hierarchy, and a branch is a different position in the structure.

SAY

Click through: the standard counter counts to 3. Click: switch to premium; it is a different identity, so it starts at 0. Click: switch back; the standard counter is new again, at 0. Its count of 3 was discarded when its branch was removed.

SAY

Click: the real console from the simulator confirms it: Standard appeared at 0 and counted to 3; Premium appeared at 0; Standard appeared again at 0.

SAY

Click: view identity is not object identity from Lesson 1.5. It is how SwiftUI associates state and updates with a view’s position and structure. Lists and navigation, later in this unit, depend on stable identity.

You can also set identity explicitly.

Part 3 · Explicit identity (section 15)

.id() resets state, on purpose

ExplicitIdentity.swift
BalanceCard(title: "Savings", balanceText: text)
    .id(accountId)      // a new account → a new identity
What it does
  • A changed id = a different view
  • Its @State starts fresh
Good use
  • Switch account A → B
  • Reset account-specific temporary state
  • Not a fix for update bugs
  • Destroys state, adds work (Part 8)
SAY

Besides structural identity, SwiftUI supports explicit identity with .id(). If accountId changes, SwiftUI treats this as a different view, and its state resets.

SAY

Click: that is useful when switching from account A to account B should reset temporary, account-specific state, such as a half-typed note.

SAY

Click: but .id() is not a universal fix for UI update problems. Used carelessly it destroys useful state and adds work. Part 8 shows the classic mistake, measured.

Part 4 · Ownership (sections 16–17)

One owner; children get a binding

Lift shared state
  • Owned at the lowest common level
  • No inconsistent copies
Binding.swift
struct AccountScreen: View {
    @State private var balanceMinor: Int64 = 2_500_000   // the owner

    var body: some View {
        BalanceEditor(balanceMinor: $balanceMinor)         // pass a binding
    }
}

struct BalanceEditor: View {
    @Binding var balanceMinor: Int64                       // reads and writes it

    var body: some View {
        Button("Add Demo ₹1,000") { balanceMinor += 100_000 }
    }
}
@Binding
  • Not a copy: access to state owned elsewhere
  • $balanceMinor creates it
SAY

The dashboard and the transaction history both need the selected account. If each kept its own copy, they could disagree. So shared state is lifted to an appropriate common owner, and both screens read it from there.

SAY

Click: @State marks the owner. AccountScreen owns the balance, in paise as always. BalanceEditor needs to change it, so it receives a binding: dollar balanceMinor. Inside, @Binding reads and writes the parent’s state.

SAY

A binding is not a second, independent copy; it is access to state owned elsewhere. When the editor adds ₹1,000, the parent’s value changes. Lesson 2.5 goes deeper into sources of truth.

Part 5 · Observation (sections 18–19)

An observable model, isolated to the main actor

DashboardViewModel.swift
import Observation

@MainActor @Observable
final class DashboardViewModel {
    var balanceMinor: Int64 = 2_500_000
    var isLoading = false

    var balanceText: String {
        let rupees = Decimal(balanceMinor) / 100
        return rupees.formatted(.currency(code: "INR"))
    }
    func refresh() async {
        isLoading = true
        defer { isLoading = false }
        // await the BalanceService (1.9)
    }
}
DashboardView.swift
struct DashboardView: View {
    @State private var model = DashboardViewModel()

    var body: some View {
        VStack {
            Text(model.balanceText)
            Button("Refresh balance") {
                Task { await model.refresh() }
            }
        }
    }
}
@Observable
  • Updates views that read it
  • Not thread-safe
@MainActor
  • UI state, main actor
  • await frees it
SAY

For more complex state, NPay uses an observable model: the DashboardViewModel from Unit 00 and 1.9. @Observable lets SwiftUI track which properties a view reads, and update that view when they change. The view owns the model with @State, so the model lives as long as the view’s identity.

SAY

The model holds paise and formats balanceText, the canon from Lesson 0.2. The button calls refresh in a task.

SAY

Click: two distinctions. @Observable makes a type observable; it does not make its mutable state thread-safe. That is why it is also @MainActor, which isolates UI-facing state to the main actor. And @MainActor does not mean blocking the main thread: at an await the main actor processes other work, though CPU-heavy synchronous work on it still freezes the UI, as Lesson 1.9 measured.

The pipeline, and what slows it.

Part 6 · Rendering (section 20) · conceptual

Five stages to a visible frame

Three different costs
  • Computing descriptions
  • Layout
  • Rendering and presenting frames
  • “Every SwiftUI view is a CALayer”
  • The rendering representation is an implementation detail
SAY

Click through a conceptual pipeline: SwiftUI view descriptions say what should appear; dependency and identity management decide what may need updating; layout decides where things go; Apple’s graphics and compositing infrastructure prepares and combines the content; and a visible frame reaches the display, the frame from Lesson 0.5.

SAY

It is conceptual: SwiftUI’s private rendering implementation, and the exact role of technologies like Core Animation, can change between OS releases. Each stage can be a separate bottleneck: computing descriptions, layout, and rendering.

SAY

Click: so avoid teaching that every SwiftUI view is a CALayer. SwiftUI manages its own abstractions.

The cost you control most directly is body.

Part 6 · Performance (section 21)

Keep body cheap; do work elsewhere

Risky.swift
var body: some View {
    let result = expensiveCalculation()  // each time
    return Text("\(result)")
}
Risky
  • body may run many times (Part 2)
  • Synchronous work here costs every time
Better.swift
@State private var result = 0

var body: some View {
    Text("\(result)")
        .task {                        // once, owned
            result = await calculator.run()
        }
}
Better
  • Work in a service or .task
  • The result becomes state
  • Networking: never as a side effect of body
SAY

Because SwiftUI may re-evaluate body many times, as Part 2 showed, a substantial synchronous calculation inside body is paid on every evaluation, and it harms responsiveness.

SAY

Click: move the work into a service or an asynchronous operation and expose the result as state. Here .task runs it with the view’s lifetime, as in Lesson 1.9. calculator stands for whatever service does the work.

SAY

Should a network request start as a side effect of evaluating body? No. body describes the interface; use .task, actions and properly owned models for side effects.

Part 8 · _printChanges (section 24)

Ask SwiftUI why body ran

Debug.swift
struct DashboardView: View {
    @State private var count = 0

    var body: some View {
        let _ = Self._printChanges()
        Text("Count: \(count)")
    }
}
iOS Simulator console (count +1 twice)

DashboardView: @self, @identity, _count changed.
DashboardView: _count changed.
DashboardView: _count changed.

Investigate
  1. Which state or observable property changed?
  2. Which views depend on it?
  3. Is the view’s identity stable?
  4. Is expensive work happening in body?
  5. Is a side effect repeatedly changing state?
  • _printChanges() is a diagnostic, not app logic
SAY

body running repeatedly is not proof that SwiftUI is inefficient: re-evaluation is how dependency updates work. The useful question is whether unnecessary expensive work is happening.

SAY

Self._printChanges() is a SwiftUI debugging facility that prints why body was evaluated. Click: the real console. First evaluation: @self, @identity and _count, because everything is new. Then, after each increment: _count changed. Exactly the state we expected.

SAY

Investigate in order: which state changed, which views depend on it, whether identity is stable, whether body does expensive work, and whether a side effect keeps changing state. Measure and find the cause before optimizing.

SAY

Click: _printChanges is a diagnostic. Never build app logic on it.

Part 8 · Identity bugs (section 25)

A random id throws state away every time

Unstable.swift
BalanceCard()
    .id(UUID())     // new every time
Parent updates 3 times

BalanceCard appeared: fresh state #1
BalanceCard appeared: fresh state #2
BalanceCard appeared: fresh state #3
BalanceCard appeared: fresh state #4

Stable.swift
BalanceCard()
    .id(accountId)  // stable
Parent updates 3 times

BalanceCard appeared: fresh state #1

  • No: structural identity is the default
  • Explicit identity only for a reason
SAY

A common mistake: giving a view .id(UUID()). Every evaluation of the parent creates a new UUID, so SwiftUI sees a brand-new view each time.

SAY

Click: we measured it. The parent updated three times; the card appeared four times, each with fresh state, numbers one to four. Any state inside it would reset on every update, and SwiftUI did extra work each time.

SAY

Click: with a stable id, accountId, the same three updates: one appearance, state kept. Use that only when changing accounts should deliberately reset the card.

SAY

Click: should you add .id() to every view? No. SwiftUI already uses structural identity; explicit identity is for specific cases.

Part 8 · Main thread and Instruments (sections 26–27)

Find what blocks the main thread

Calculate.swift
Button("Calculate") {
    result = expensiveCalculation()  // main actor
}
Several seconds on the main actor
  • No event handling, no new frames: the UI freezes (0.5)
  • async alone doesn’t move CPU work off it (1.9)

Time ProfilerCPU-heavy call paths
Animation / hitchesframe timing and rendering

  • Descriptions, layout, rendering (Part 6)
SAY

A Calculate button that runs a several-second calculation directly in its action. Actions run on the main actor, so for those seconds the main thread cannot handle events or produce frames, and the UI freezes, exactly the run loop story from Lesson 0.5. SAY

What to remember

Views describe
body is cheap and may run often

Identity keeps state
change it and state resets

One owner per state
@State, @Binding, @Observable

SAY

Three things to remember. Views are cheap descriptions: body may run often, only for views whose dependencies changed, and evaluation is not rendering. Identity keeps state attached: switch a branch or change an id and the state starts fresh. And every piece of state has one owner: @State for view state, @Binding to share it, an @Observable, @MainActor model for app state.
