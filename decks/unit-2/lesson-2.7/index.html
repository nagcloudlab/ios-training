A title and an escaping action

The simplest button: a title and a trailing closure. A simplified form of the initializer it calls: a localized title key, and an action of type escaping closure taking nothing and returning Void. SwiftUI has several Button initializers; we meet the custom-label one next.

SAY

SAY

Click: closures as values, from Unit 01. You can store a closure in a constant and call it later. A Button does exactly that: it stores the closure and calls it when the button is activated.

Part 3 · Does the closure run when body runs? (section 3)

Evaluation is not activation

PaymentView.swift
struct PaymentView: View {
    let tick: Int
    var body: some View {
        let _ = print("PaymentView.body evaluated (tick \(tick))")
        Button("Send Money") {
            print("Payment requested")
        }
    }
}
Parent changed 3 times, no tap

PaymentView.body evaluated (tick 0)
… (tick 1) … (tick 2) … (tick 3)
"Payment requested": never printed

SAY

A PaymentView with a print in its body and a button. We made its parent change three times, which makes SwiftUI evaluate the body again, and never activated the button. Click: body evaluated. Click: the description contains the action closure, stored, not called. Click: body evaluated again: a new description with a new closure.

SAY

The console: body evaluated four times, tick 0 to 3, and "Payment requested" never printed. Click: the action runs only when the user activates the button, a separate event. Click: and then once per activation.

SAY

So if SwiftUI re-evaluates body ten times, the action runs zero times. View evaluation and user activation are separate events. That is also why it is safe to create closures in body.

When the user taps a point, hit testing determines which interactive view corresponds to that location, using the view hierarchy and each view’s interaction region. The text’s widget showed a tap landing on History.

Part 7 · Interactive quick actions (section 10)

QuickAction stores a closure

QuickAction.swift
struct QuickAction: View {
    let symbol: String
    let title: String
    let action: () -> Void

    var body: some View {
        Button(action: action) {
            VStack(spacing: 8) {
                Image(systemName: symbol)
                    .font(.title2)
                Text(title)
                    .font(.caption)
            }
            .frame(maxWidth: .infinity)
            .padding(.vertical, 14)
            .contentShape(Rectangle())
        }
        .buttonStyle(.plain)
        .foregroundStyle(.blue)
        .background(Color.blue.opacity(0.08),
                    in: RoundedRectangle(cornerRadius: 12))
    }
}
New
  • let action: () -> Void, a closure property
  • Button(action: action) uses it
type(of: quickAction.action)

() -> ()

  • A stored closure can capture objects
  • ARC matters when it captures models (Part 8)
SAY

QuickAction gets a third property: let action: () -> Void, a closure property. Its body wraps the old icon-over-label VStack in Button(action: action): the label is the tile, and contentShape makes the whole tile tappable. .buttonStyle(.plain) keeps our own look instead of the system style.

SAY

Click: we printed the stored property’s type: () -> (), Swift’s spelling of () -> Void. A closure value, not a function name and not an event object.

SAY

Click: because QuickAction stores the closure, the closure can capture other objects and keep them alive. Today the actions only print, so nothing is captured; when they start capturing ViewModels and services, ARC matters. Part 8.

Part 8 · Closure capture and ARC (section 16)

A closure can keep an object alive

Capture.swift (Mac, swiftc)
final class PaymentService {
    func send() { print("Sending payment") }
    deinit { print("PaymentService deinit") }
}

var service: PaymentService? = PaymentService()
var action: (() -> Void)? = { [service] in service?.send() }

service = nil
print("service variable set to nil")
action?()
action = nil
print("closure released")
Output

service variable set to nil
Sending payment
PaymentService deinit
closure released

Every capture a cycle?
  • No: a cycle needs a strong loop
  • e.g. a service storing a closure that captures that service
  • No: decide from ownership (1.8)
  • Today’s actions only print
SAY

The text’s PaymentService example, made observable: a deinit that prints, a closure that captures the service, then we drop our own variable. Click: we compiled and ran it on a Mac. Setting the variable to nil did not free the service: the closure still held it and could still send a payment. The service was freed only when the closure was released. A stored closure can extend the lifetime of what it captures.

SAY

Click: does every button closure cause a retain cycle? No. A cycle needs a strong loop, for example a service that stores a closure which strongly captures that same service, as in Lesson 1.8.

SAY

Click: so should every SwiftUI action say [weak self]? No. Decide from the ownership relationships; weak references everywhere are not a substitute for understanding lifetimes. Our current actions only call print, so there is nothing to worry about yet.

Part 8 · Keep actions responsive (section 18)

A 3-second action freezes the main thread

Deliberately bad
Button("Send") {
    Thread.sleep(forTimeInterval: 3)
    print("Finished")
}
Later: the structure for async work
Button("Send") {
    Task {
        // call an async payment service
    }
}
A main-thread timer, every 0.5 s

fired at 0.5 · 1.0 · 1.5 secs
→ Send activated
Finished
fired at 4.6 · 5.0 · 5.5 secs

  • No timer, no events, no frames (0.5)
  • Task alone doesn’t make CPU work safe (1.9)
SAY

A deliberately bad action: sleep three seconds on the main thread, then print. We ran a repeating timer on the main thread, firing every half second, and activated the button at 1.5 seconds.

SAY

Click: the timer fired at 0.5, 1.0 and 1.5 seconds, then nothing until 4.6. Three seconds of silence: while the action blocked the main thread, no timer, no touch handling and no new frames, the RunLoop story from Lesson 0.5.

SAY

Click: the direction for later: when Send calls a real payment service, the action will start a Task and await an asynchronous service. Only the structure for now. Creating a Task does not by itself make synchronous CPU-heavy work safe on the main actor, as 1.9 measured. Networking and concurrency units come back to this.
