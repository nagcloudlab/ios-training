Part 2 · What exactly is ZStack? (section 2)

Children share the same space

ContentView.swift
ZStack {
    Color.blue

    Text("NPay")
        .foregroundStyle(.white)
}
.frame(width: 240, height: 140)

240 × 140 pt, measured

Interface excerpt, iOS 26.5 SDK (body omitted)
@frozen public struct ZStack<Content> : View
        where Content : View {
    public init(alignment: Alignment = .center,
                @ViewBuilder content: () -> Content)
}
type(of:) in the simulator

ZStack<TupleView<(Color, Text)>>

  • Same @ViewBuilder closure as VStack
  • Children are aligned in overlapping space
SAY

VStack arranges children vertically, HStack horizontally; ZStack overlays them along the depth axis. Here Color.blue fills the frame as a background layer, and the white text sits above it. On the left, the simulator: 240 by 140 points.

SAY

Click: like the other stacks, ZStack is a generic struct conforming to View. Its initializer takes an Alignment, a full two-dimensional alignment, defaulting to .center, and the same @ViewBuilder content closure. Click: the printed type is ZStack of a TupleView of Color and Text: Color is a View too.

SAY

Click: the difference is layout. Instead of placing children one after another, ZStack aligns them within overlapping space.

Later children are drawn on top

Middle: Text, Blue, Green

SAY

Blue, then green, then the text. In a ZStack, later children are normally drawn above earlier ones: green covers blue completely, and the text is on top. That is the top card on the right; it replaces the text’s layer explorer.

SAY

Click: the middle card has the same three children with the text first. It is drawn first, so both colours cover it: the text is still there, but you cannot see it. Changing the source order changes the layering, unless you adjust it explicitly. The bottom card shows how.

Part 3 · What is .zIndex()? (section 4)

.zIndex changes drawing order only

ContentView.swift
ZStack {
    Text("Behind")
        .zIndex(0)

    Text("In Front")
        .zIndex(1)
}
Higher zIndex
  • Drawn above siblings with lower values
Rescue the hidden text
  • Text("NPay").zIndex(1), still written first
  • Visible again: bottom card, previous slide
  • Change size, position or layout priority
  • Create a window or process
Observed
  • Works on the stack’s direct child
  • Wrapped in another modifier, it had no effect
SAY

.zIndex controls relative drawing order: a larger value generally places a view above siblings with lower values in the same stacking context.

SAY

Click: our bottom card on the previous slide: the text still comes first in the source, but with zIndex(1) it is drawn above both colours.

SAY

Click: zIndex only changes visual stacking. It does not change a view’s size, position or layout priority, and it does not create a separate window or process.

SAY

Click: something we hit while measuring: when we put another modifier after .zIndex, so that zIndex was no longer on the outermost layer of the ZStack’s child, it had no effect. Put .zIndex last on the child.

Same children, different sizes

Sizes.swift

        .frame(width: 300, height: 180)

}

VStack {   // same children
    Rectangle().fill(.blue)

Measured (red border)

ZStack: 300.0 × 180.0 pt
VStack: 300.0 × 212.9 pt

  • Here, the size of the largest child
  • Not a rule: proposals and flexibility decide

Top: ZStack. Bottom: VStack

SAY

A blue rectangle requesting 300 by 180 points and a small text, once in a ZStack and once in a VStack, each with a red border. Under ordinary conditions a ZStack considers its children’s sizes and alignment, but it does not add their heights.

SAY

Click: measured. The ZStack is 300 by 180, the rectangle’s size; the text sits inside it. The VStack is 212.9 tall: the rectangle, the default spacing and the text, one after another. That replaces the text’s toggle.

SAY

Click: in this case the ZStack took the size of its largest child, but do not turn that into a rule. ZStack sizing depends on proposals, child flexibility and alignment; a flexible child like Color takes whatever it is offered.

Part 5 · Alignment inside ZStack (section 6)

.topLeading: top and leading

ContentView.swift
ZStack(alignment: .topLeading) {
    Color.blue

    Text("NPay")
        .foregroundStyle(.white)
        .padding()
}
.frame(width: 300, height: 180)
An Alignment value
  • Vertical and horizontal: .topLeading, .center, .bottomTrailing, …
  • alignment: expects Alignment, so the shorthand is inferred

Run at 300 × 150 to fit all three

SAY

ZStack centres by default. With alignment .topLeading the text goes to the top-leading corner; its padding keeps it off the edge. Unlike VStack’s HorizontalAlignment or HStack’s VerticalAlignment, a ZStack has both axes free, so it takes an Alignment: a vertical and a horizontal part together.

SAY

The shorthand works because alignment: expects an Alignment value, contextual type inference again. On the right, .topLeading, .center and .bottomTrailing in the simulator, run at 150 points tall so all three fit; the text’s buttons showed the same idea conceptually.

Part 6 · ZStack vs .background() vs .overlay() (section 7)

Who decides the size?

ZStack.background.overlay
Purposegeneral overlapping layoutcontent behind a viewcontent over a view
Sizeconsiders participating childrenfollows the primary viewfollows the primary view
Typical usecomplex layered compositioncard backgroundsbadges, labels, decoration
Measured (pt)

ZStack 240 × 120 · background 110.3 × 92.3
overlay 240 × 120 · oversized overlay 240 × 120

  • Layers that share a layout: ZStack
  • Visual attached to one view: background / overlay

Bottom: the overlay spills

SAY

Three ways to get layered visuals. A ZStack: its children take part in one layout together. .background: the background is attached to the modified view, behind it, and its size follows that view’s layout region. .overlay: content laid out relative to the primary view, over it, and it generally does not decide the primary view’s size.

SAY

On the right, top to bottom: the ZStack, the padded text with a blue background, the rounded rectangle with a text overlay, and the same rectangle with an overlay that is far too big. Click: the measurements. The background version is exactly the padded text, 110 by 92: the background followed the text. Both overlay versions are 240 by 120: the oversized text spills over the edges, drawn in black so you can see it, and the shape does not grow.

SAY

Click: the decision. Use ZStack when several layers should participate in one layered layout; use background and overlay when the visual naturally belongs to one primary view.

Part 7 · How SwiftUI composes the card (section 9) · conceptual

One description, rendered by SwiftUI

One CALayer per child?
  • Not necessarily
  • SwiftUI manages rendering internally
What the API promises
  • The declarative layout and drawing
  • Not a one-to-one map to layers
SAY

Conceptually the card is a ZStack with two children: the RoundedRectangle as the background layer and the VStack as the text layer, then layout and rendering. The word layer here is about drawing order, not a specific object.

SAY

Click: does SwiftUI create a separate CALayer for each child? Not necessarily. SwiftUI manages its rendering representations internally. The public API guarantees the declarative layout and drawing behaviour, not a fixed one-to-one mapping to Core Animation layers. That is the same caution as Lesson 2.1’s "does every Text create a UILabel?".

Lesson 2.5 · Recap

What to remember

Later is in front
source order; .zIndex when needed

ZStack overlaps
sizes don’t add; proposals decide

Attach or compose
background/overlay vs ZStack

SAY

Three things to remember. In a ZStack later children are drawn in front; .zIndex changes only that drawing order. A ZStack overlaps its children instead of adding their sizes, and its exact size depends on proposals and flexibility. And background and overlay attach a visual to one primary view, whose size wins, while a ZStack composes layers that take part in one layout.
