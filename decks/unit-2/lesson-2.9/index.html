@Binding: How Two
SwiftUI Views Share State

A child view needs to change a value its parent owns. Without a second copy. How?

SAY

In 2.8 NPay’s balance became @State in ContentView. Now a separate view, a balance editor, needs to change that balance. Passing a value is not enough, and giving the child its own state creates a second copy. The answer is @Binding: what it is, how it writes through, how to build one by hand, and where it belongs in NPay. Console output and screenshots came from the iOS Simulator, with buttons activated through accessibility as before.

Part 3 · balance versus $balance (section 4)

The value, or a binding to it

type(of:) in the simulator

parent $balance: Binding<Int>
child balance: Int
child _balance: Binding<Int>

Why the $
// iOS 26.5 SDK (excerpts)
@propertyWrapper public struct State<Value> {
    public var projectedValue: Binding<Value> { get }
}
@propertyWrapper public struct Binding<Value> {
    public var wrappedValue: Value { get nonmutating set }
}
SAY

balance gives the wrapped value, an Int. $balance gives the projected value of @State, a Binding of Int.

SAY

Click: printed in the simulator. In the parent, $balance is Binding of Int. In the child, balance reads as a plain Int, and its hidden storage, _balance, is a Binding of Int: the child stores the binding the parent passed.

SAY

Click: why the dollar sign? A Swift property wrapper can expose a projectedValue, and $name is how you reach it. The SDK shows State’s projectedValue is a Binding. So $ is a Swift language feature, not special SwiftUI syntax. Notice Binding’s wrappedValue: get, nonmutating set. That is the next slide.

Part 4 · How does Binding work? (sections 5, 13)

A getter, a setter, and nonmutating set

SimpleBinding.swift (Mac, swiftc)
// Teaching approximation, not Apple's implementation
struct SimpleBinding<Value> {
    let get: () -> Value
    let set: (Value) -> Void

    var wrappedValue: Value {
        get { get() }
        nonmutating set { set(newValue) }
    }
}

final class Storage { var balance = 25000 }
let storage = Storage()
let binding = SimpleBinding(get: { storage.balance },
                            set: { storage.balance = $0 })
binding.wrappedValue += 1000     // binding is a let!
print(binding.wrappedValue, storage.balance)
Output

through the binding: 26000
the storage itself: 26000

nonmutating set
  • Forwards the write elsewhere
  • Works on a let, inside a view
  • A binding owns nothing
SAY

A teaching model of a binding, not Apple’s implementation: two closures, one that gets a value and one that sets it, and a wrappedValue whose setter is nonmutating. We added a tiny class to stand in for SwiftUI’s state storage, made a SimpleBinding to it, stored the binding in a let, and added 1,000 through it.

SAY

Click: we compiled and ran it on a Mac: 26,000 through the binding, and 26,000 in the storage itself. Click: that worked on a let because the setter is nonmutating: writing does not change the binding’s own fields, it forwards the write to storage elsewhere. That is exactly why a child view, whose self is immutable, can still write through @Binding. The real Binding’s wrappedValue is declared get nonmutating set, as we saw in the SDK.

SAY

Click: so a binding does not own the value. It is a read and write connection to state owned elsewhere. Value is generic; for NPay it is Binding of Int.

Part 6 · Create BalanceEditor (section 8)

Two buttons, one binding

BalanceEditor.swift
struct BalanceEditor: View {
    @Binding var balance: Int

    var body: some View {
        VStack(spacing: 12) {
            Text("Demo Balance Editor")
                .font(.headline)
            HStack(spacing: 12) {
                Button("− ₹1,000") {
                    balance = max(0, balance - 1000)
                }
                .buttonStyle(.bordered)
                Button("+ ₹1,000") {
                    balance += 1000
                }
                .buttonStyle(.borderedProminent)
            }
        }
        .padding()
    }
}
max(0, balance - 1000)
  • The demo balance never goes negative
Started at ₹500: − , −

BalanceEditor body: 0
balance now 0
(second −: still 0, no new update)

  • Validation belongs in trusted domain and backend logic
  • Not only in UI controls
SAY

The real editor: a headline, then an HStack with a bordered minus button and a prominent plus button, both writing through the binding. Minus uses max(0, balance - 1000) so the demo balance never goes below zero.

SAY

Click: we started an editor at ₹500 and activated minus twice. The first press clamped to 0. The second asked for max(0, -1000), which is 0 again: the value did not change, and no further update was printed.

SAY

Click: a production note. A UI clamp is a convenience. In a real payment system, validation belongs in trusted domain and backend logic, never only in a button.

Part 7 · Build a binding manually (sections 11, 14)

Explicit get and set, with validation

Like $balance
BalanceEditor(
    balance: Binding(
        get: {
            balance
        },
        set: { newValue in
            balance = newValue
        }
    )
)
+ through it

manual binding set 26000
BalanceCard body: 26000

Validating binding
private var safeBalance: Binding<Int> {
    Binding(
        get: {
            balance
        },
        set: { newValue in
            balance = max(0, newValue)
        }
    )
}
// BalanceEditor(balance: safeBalance)
A child that doesn’t clamp, from ₹500: − , −

safeBalance set: asked -500, storing 0
safeBalance set: asked -1000, storing 0

  • Prefer plain $balance; UI validation ≠ financial validation
SAY

A binding is a read and a write, so you can build one with Binding(get:set:): get returns the parent’s balance, set stores the new value. That is conceptually the same as passing $balance. Click: we activated plus through it: our set closure ran with 26,000 and the card showed 26,000. It printed Binding of Int, the same type as $balance.

SAY

Custom bindings can also transform or validate. safeBalance clamps every write to zero or above. We gave it to a deliberately naive child that subtracts 1,000 with no check, starting from ₹500. Click: the child asked for -500, the binding stored 0; asked for -1,000, stored 0. The child never knew about the rule; the binding intercepted the write.

SAY

Click: two cautions. Do not add custom bindings where $balance is enough. And this is UI behaviour, not financial security: real payment rules are enforced by trusted domain and backend systems.

Part 8 · Read-only value vs binding (sections 15–16)

Give a child only the access it needs

Two children
struct BalanceCard: View {      // reads
    let balance: Int
    var body: some View {
        Text("₹\(balance)")
    }
}

struct BalanceEditor: View {    // reads and writes
    @Binding var balance: Int
    var body: some View {
        Button("Add ₹1,000") {
            balance += 1000
        }
    }
}
Rule
  • Only displays it: pass a value
  • Must modify parent state: pass a binding
  • Data flow stays understandable
In Xcode
  • Breakpoint on balance += 1000 in the editor
  • Tap + ₹1,000; inspect; continue
  • The card shows the new amount
  • The parent’s state changed
  • No copy in the child
SAY

Two children, intentionally different. BalanceCard only displays, so it gets a let value. BalanceEditor modifies parent-owned state, so it gets a @Binding.

SAY

The rule: give a child only the access it needs. If it only displays information, pass a value; if it must change parent-owned local state, pass a binding. That keeps ownership and data flow easy to follow.

SAY

Click: the debugging check from Section 15: a breakpoint on balance += 1000 in the editor, tap plus, inspect, continue, and the card updates. Click: what you are confirming is what our console showed: the child wrote through the binding, the parent’s state changed, and no separate copy exists in the child.

Lesson 2.9 · Recap

What to remember

$balance is a Binding
the projected value of @State

Bindings forward writes
nonmutating set; no ownership

One owner, right access
value to readers, binding to writers

SAY

Three things to remember. $balance is @State’s projected value, a Binding of Int, and a child declares @Binding to receive it. A binding owns nothing: its nonmutating setter forwards each write to the parent’s storage, which is why it works inside a view struct. And keep one owner for each piece of state, passing a value to children that only read and a binding to children that write.
