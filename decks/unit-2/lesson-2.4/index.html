Part 2 · What exactly is HStack? (section 2)

A generic struct, like VStack

Interface excerpt, iOS 26.5 SDK (body omitted)
@frozen public struct HStack<Content> : View
        where Content : View {
    public init(alignment: VerticalAlignment = .center,
                spacing: CGFloat? = nil,
                @ViewBuilder content: () -> Content)
}
type(of:) in the simulator

HStack { Send; Request; History }:
HStack<TupleView<(Text, Text, Text)>>

VStackHStack
Main axisverticalhorizontal
Cross-axis alignmentHorizontalAlignmentVerticalAlignment
Spacingbetween vertical childrenbetween horizontal children
Content@ViewBuilder closure@ViewBuilder closure
  • Returns the content; the initializer builds the HStack
SAY

Like VStack, HStack is a generic SwiftUI struct conforming to View. Here is its real declaration from the SDK: the same shape as VStack’s, except alignment is a VerticalAlignment.

SAY

The table: the main axis is horizontal instead of vertical; cross-axis alignment is VerticalAlignment instead of HorizontalAlignment; spacing goes between horizontal children; and the content is the same @ViewBuilder closure.

SAY

Click: we printed the type of our three-label row: HStack of a TupleView of three Texts. Exactly the pattern from 2.3.

SAY

Click: does the closure return the HStack? No. The closure produces the child content; the initializer constructs the stack.

Part 3 · HStack’s layout negotiation (section 4)

How an HStack shares out width

The arithmetic
  • Spacing: 2 × 20 = 40 pt
  • Left for children: 350 − 40 = 310 pt
  • Not 310 ÷ 3 = 103.3 pt each
  • Each child has its own sizing
SAY

Layout uses size proposals. For a horizontal stack, the container decides how to distribute width. Click: the parent proposes a size, say 350 points wide. Click: the stack accounts for spacing: two gaps of 20 take 40 points. Click: the children receive proposals, depending on each child’s sizing behaviour and flexibility. Click: they choose sizes and report them. Click: the stack positions them with alignment and spacing.

SAY

Click: the numbers. 350 minus 40 leaves 310 points for the children. But that does not mean each child gets 103.3 points. Each child has its own sizing behaviour. A simplified model; real stacks also weigh ideal sizes and priorities.

SAY

Both rows sit in a stack 350 points wide with spacing 20, so 310 points are left for children. The top row has plain Texts; the bottom row gives every Text a flexible frame with infinite max width. This replaces the text’s browser explorer, which deliberately gave equal flexible widths.

SAY

Click: measured. Plain Texts take what they need: 39.3, 62.7 and 54.7 points, and the stack centres them in the leftover space. With flexible frames, each child gets exactly 103.3 points: 310 divided by 3.

SAY

Click: a plain HStack of Texts does not distribute space equally. When a reusable layout needs equal columns, ask for flexibility explicitly.

Spacer takes the leftover space

Header.swift

Spacer
  • A flexible view along the stack’s main axis
  • No visible content of its own

HStack<TupleView<(Text, Spacer, Image)>>

Row width, measured

without Spacer: 84.3 pt

SAY

The NPay title on the left and an account icon on the right: put a Spacer between them. Spacer is a SwiftUI view that expands along the stack’s main axis when space is available. It draws nothing itself; the stack can give it the remaining space, subject to layout constraints.

SAY

On the right, the text’s checkbox experiment for real: the top row has no Spacer, the bottom row has one. The blue border is the HStack. Click: without the Spacer, the row is just its content, 84.3 points. With it, 370 points: the Spacer absorbed 285.7 points and pushed the icon to the far edge.

SAY

Click: and the Spacer is a real child in the content type: a TupleView of Text, Spacer and Image.

Is a Spacer just padding?

Part 4 · Spacer vs padding (section 6)

Spacer() is not .padding(20)

.padding(20)
  • A fixed amount
  • Around one view
  • Same on every screen
Spacer()
  • Flexible: grows into leftover space
  • Between siblings in a stack
  • Wider screen, wider Spacer
  • Spacer took 285.7 pt here; on another iPhone width, a different amount
SAY

Is Spacer() the same as .padding(20)? No. Padding adds a specified amount of space around a view, the same on every screen. A Spacer is flexible: it sits between siblings in a stack and expands to consume the available space.

SAY

Click: in our run the Spacer took 285.7 points; on a narrower or wider iPhone it would take a different amount, which is exactly why NPay’s header adapts to the device.

Part 5 · Why HStack uses VerticalAlignment (section 8)

Different heights, three alignments

ContentView.swift
HStack(alignment: .top, spacing: 20) {
    Text("Send")
        .font(.largeTitle)

    Text("Request")
        .font(.caption)
}
Each aligns
  • .top: top edges
  • .center: vertical centres
  • .bottom: bottom edges
  • Text baseline alignment: a later experiment

Grey = each Text; blue = the row

SAY

Send in largeTitle and Request in caption: very different heights. HStack’s cross axis is vertical, so its alignment is a VerticalAlignment. .top lines up the top edges, .center the vertical centres, .bottom the bottom edges. On the right, all three in the simulator; the row is as tall as its tallest child.

SAY

When children differ in size, this choice changes how the row looks. Click: for text in different font sizes you often want the text baseline instead; SwiftUI supports that, and we come back to it in a later layout experiment.

Part 6 · Too narrow: layoutPriority (section 9)

Who gets the space when there isn’t enough

BalanceRow.swift
HStack {
    Text("Available Balance")
        .layoutPriority(1)

    Text("₹25,000")
}
no priority

label: 82.3 pt, 2 lines
amount: 75.3 pt, 1 line

label priority 1

label: 152.0 pt, 1 line
amount: 39.3 pt, 2 lines

  • Priority decides who is served first when space is short
  • Here it squeezed the amount

Both rows squeezed into 200 pt (.title3)

SAY

On a smaller iPhone, a row may not fit. SwiftUI has to resolve the layout within the width it has: text may compress, wrap or truncate, depending on the views and their modifiers. We squeezed the text’s balance row into 200 points, at title3 so it clearly does not fit.

SAY

Top row, no priority: the label wrapped onto two lines and the amount kept one line. Bottom row, the label has layoutPriority(1): it is served first and keeps one line, 152 points, and the amount is left with 39 points and wraps: "₹25," above "000".

SAY

Click: so layoutPriority is not an instruction to make a view larger. It decides who gets space first when space is short, and here it produced a worse result for the balance. Use it deliberately, and check the result.

Part 7 · Why .font(.subheadline) reaches the children (section 10)

Modifiers on a container flow down

type(of:) in the simulator

row.font(.subheadline):
ModifiedContent<HStack<…>,
_EnvironmentKeyWritingModifier<Optional<Font>>>

Same as on an Image (2.2)
  • .font on a non-Text view writes the environment
The environment
  • Font is an environment-driven style
  • Every descendant reads it
  • unless it sets its own
  • The modifiers lesson goes deep on this
SAY

Why does .font(.subheadline) on the HStack change the labels inside it, and size the symbols too? We printed the type: the HStack wrapped in an environment-writing modifier for an optional Font, the same thing we saw on an Image in 2.2.

SAY

Click: font is an environment-driven style. A font modifier on a container puts the font into the environment, and every descendant that does not set its own font reads it. The same happens with foregroundStyle, which is why all three actions are blue.

SAY

Click: this is an important concept; the modifiers lesson explores it properly.

Lesson 2.4 · Recap

What to remember

HStack = sideways VStack
VerticalAlignment, horizontal spacing

Width is negotiated
children size themselves; not equal shares

Spacer and priority
flexible space; who is served first

SAY

Three things to remember. HStack is VStack’s horizontal twin: a generic struct, a @ViewBuilder closure, spacing between horizontal children and a VerticalAlignment. Width is negotiated: after spacing, children size themselves, so plain Texts do not get equal shares unless you ask for flexibility. And Spacer is flexible space that takes what is left, while layoutPriority decides who is served first when space runs out.
