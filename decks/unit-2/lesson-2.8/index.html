Part 2 · Experiment 1: a normal Swift variable (section 2)

It doesn’t compile

ContentView.swift
struct ContentView: View {
    var balance = 25000

    var body: some View {
        VStack(spacing: 20) {
            Text("Balance: ₹\(balance)")
            Button("Add ₹1,000") {
                balance += 1000
            }
        }
    }
}
ERROR left side of mutating operator isn’t mutable: ‘self’ is immutable

swiftc, iOS 26.5 SDK, at balance += 1000

Why
  • body is a nonmutating getter
  • The action can’t change the view’s stored property
  • var account = Account(…) works: account is mutable
  • A view struct is a description, not a mutable controller
SAY

Temporarily replace ContentView with this: an ordinary var balance, and a button that adds 1,000. Predict: does it compile? It is declared var, after all.

SAY

Click: the real compiler error: left side of mutating operator isn’t mutable: self is immutable, at balance += 1000.

SAY

Click: why. Structs have value semantics, from Unit 01. var account = Account(balance: 25000); account.balance += 1000 works, because account is a mutable variable. But a view’s body is a nonmutating computed property, and the escaping button action captured an immutable self. It cannot change a stored property of the view value.

SAY

Click: the key insight: a SwiftUI view struct is a description of UI, not a mutable controller object. Mutable state has to live somewhere else.

Part 4 · Property wrapper transformation (section 5)

@NonNegative: a wrapper in plain Swift

NonNegative.swift (Mac, swiftc)
@propertyWrapper
struct NonNegative {
    private var storage: Int
    var wrappedValue: Int {
        get { storage }
        set { storage = max(0, newValue) }
    }
    init(wrappedValue: Int) {
        storage = max(0, wrappedValue)
    }
}

struct Account {
    @NonNegative var balance = 25000
}

var account = Account()
account.balance = -500
print(account.balance)
Output

0

What the compiler generates, roughly
struct Account {   // teaching approximation
    private var _balance =
        NonNegative(wrappedValue: 25000)
    var balance: Int {
        get { _balance.wrappedValue }
        set { _balance.wrappedValue = newValue }
    }
}
  • Same mechanism: _balance + accessors
  • Plus SwiftUI-managed storage and updates
SAY

A custom wrapper in plain Swift: NonNegative stores an Int and clamps anything below zero. Account uses it on balance. We set -500 and print. Click: we compiled and ran it on a Mac: 0. The setter clamped it.

SAY

Click: what the compiler does, as a teaching approximation: it creates hidden backing storage, _balance, holding a NonNegative, and a computed balance property whose get and set go through wrappedValue. That is where the _balance name we printed for @State comes from.

SAY

Click: @State uses the same language mechanism, but its wrapper does something extra: it connects to storage that SwiftUI manages, and to SwiftUI’s dependency updates. NonNegative is not how State is implemented; it shows the syntax.

Part 5 · Where is @State stored? (sections 6, 13)

New view value, same state

Survivor.swift (parent changes tick)
struct Survivor: View {
    let tick: Int
    @State private var balance = 25000
    init(tick: Int) {
        self.tick = tick
        print("Survivor value created (tick \(tick))")
    }
    var body: some View {
        let _ = print("body: tick \(tick), balance = \(balance)")
        Button("Add") { balance += 1000 }
    }
}
  • The initial value for this identity
  • Not re-assigned when body runs
Add ×3, then the parent changed tick twice

Survivor value created (tick 0)
body: tick 0, balance = 25000
… Add ×3 …
body: tick 0, balance = 28000
Survivor value created (tick 1)
body: tick 1, balance = 28000
Survivor value created (tick 2)
body: tick 2, balance = 28000

So
  • The struct was created again, twice
  • The state stayed at 28000: it lives with the view’s identity
SAY

The most important idea today. A view struct is a value that SwiftUI can recreate during normal updates, yet its @State does not reset. To see it, this Survivor view prints when its struct is created and when its body runs. Its parent passes a tick that changes, which forces a new Survivor value.

SAY

Click: the console. Created at tick 0 with 25,000. Three activations of Add: 28,000. Then the parent changed tick twice: two brand-new Survivor values were created, and both bodies saw balance 28,000. The struct is new; the state is not.

SAY

That is because SwiftUI keeps the state in storage associated with the view’s identity, not inside the struct. Click: and it answers Section 13: = 25000 is the initial value SwiftUI uses when it first sets up state for that identity, not an assignment that runs every time body runs. The text’s analogy is a hotel room: the sign on the door can be replaced, and the guest’s belongings stay with the room.

Part 5 · View value vs persistent UI state (section 6) · conceptual

The struct describes; SwiftUI keeps

Like a form
  • SwiftUI may recreate the form template
  • The values entered are kept separately
  • Not saved to disk
  • App terminated: the value is not guaranteed to survive
  • Persistence: a later unit
SAY

The model. The ContentView value may be recreated. SwiftUI’s state machinery keeps storage associated with the view’s identity, and that is where balance lives. The private memory layout is not public; this is a conceptual model. The text’s other analogy: a form template can be reprinted, while the values entered into the form are kept separately.

SAY

Click: one important distinction. @State is not durable persistence. It does not save to disk; if NPay is terminated, the value is not guaranteed to survive. Persistence, SwiftData and the Keychain come later.

Part 7 · State ownership (sections 11, 17)

The parent owns; children read; actions change

One-way data flow
  • State → descriptions → screen
  • Actions change state, never the card
A real payment app (17)
  • The backend owns the real balance
  • A local += 1000 is not a transaction
SAY

Why does ContentView own the state? Because it coordinates both the button that changes the balance and the card that shows it. The parent owns the state and passes values down; the card only reads; the button’s action changes the state, which produces new descriptions. That is one-way data flow. Two-way bindings come next lesson.

SAY

Click: Section 17’s architecture decision. @State is right for this demo of local UI state. In a real payment app the authoritative balance comes from a trusted backend. Click: a production shape: backend, an authenticated networking service, a ViewModel that manages loading, errors and the displayed data, and BalanceCard showing it. The client must never treat a locally incremented number as a real transaction. Later units also store money as paise in Int64, as Unit 01 did; today’s whole-rupee Int is for the demo.

Part 8 · When does @State reset? (section 14)

New identity, fresh state

IdentityExperiment.swift
struct IdentityExperiment: View {
    @State private var identity = UUID()

    var body: some View {
        VStack(spacing: 20) {
            CounterView()          // @State count = 0
                .id(identity)
            Button("Replace Identity") {
                identity = UUID()
            }
        }
    }
}
Increment ×3, then Replace Identity

CounterView body: count = 0 … 1 … 2 … 3
CounterView body: count = 0

After 3 increments

After Replace Identity

  • .id(UUID()) created in body
  • Every evaluation would reset state
SAY

CounterView has its own @State count. The parent gives it an explicit identity with .id, stored as a UUID in the parent’s state, and a button that replaces that UUID.

SAY

We activated Increment three times: count 1, 2, 3, on the left. Click: then Replace Identity: count 0, on the right. Changing .id gave SwiftUI a different identity for CounterView, so the old state was no longer associated with it and a new state started from 0. Same result as 2.1’s identity experiment.

SAY

Click: so never create .id(UUID()) inside body: every evaluation would produce a new identity and reset the state, and SwiftUI would replace the view each time. Here the UUID lives in @State and changes only on purpose.

type(of:) inside the view

balance gives the wrapped value, an Int. $balance gives the projected value, which for @State is a Binding of Int, as we printed. A binding is a reference to state stored elsewhere that you can read and write.

Lesson 2.8 · Recap

What to remember

@State is a wrapper
view-owned state in SwiftUI storage

Identity keeps it
new struct, same state; new id, fresh state

UI = f(State)
change state; SwiftUI updates the screen

SAY

Three things to remember. A view struct cannot change its own stored properties, so @State, a property wrapper, gives it state that SwiftUI stores for it. That state belongs to the view’s identity: the struct can be recreated and the state survives, but a new identity starts fresh. And the screen is a function of state: change the state in an action and SwiftUI re-evaluates what depends on it.
