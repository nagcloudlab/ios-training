SAY

An array of three transaction names, from Unit 01. Can we loop over it inside a VStack with a normal for statement? Click: no. The compiler says a closure containing a control flow statement cannot be used with the result builder ViewBuilder: the builder from 2.3 does not accept this kind of loop as a way to produce child views.

SAY

Instead, SwiftUI provides ForEach: it creates a view description for each element. Click: id: \.self tells SwiftUI what identifies each element: here the string itself. That works for unique strings; with duplicate or changing values it becomes a problem, as Part 5 shows.

What is ForEach?

Part 2 · What exactly is ForEach? (section 3)

A generic view: Data, ID, Content

Interface
// iOS 26.5 SDK (excerpts)
public struct ForEach<Data, ID, Content>
    where Data : RandomAccessCollection, ID : Hashable

extension ForEach : View where Content : View

extension ForEach where ID == Data.Element.ID,
    Content : View, Data.Element : Identifiable {
    public init(_ data: Data,
        @ViewBuilder content: @escaping (Data.Element) -> Content)
}
Three generic types
  • Data: the collection
  • ID: the identity, Hashable
  • Content: the view per element
type(of:) in the simulator

ForEach<Array<String>, String, Text>
ForEach<Array<Transaction>, UUID,
TransactionRow>

  • A view describing child views and their identities
SAY

ForEach is a generic struct with three type parameters: Data, the collection, which must be a RandomAccessCollection; ID, the identity type, which must be Hashable; and Content, the view produced for each element. In the SDK it conforms to View when Content does, and it has an initializer for Identifiable elements that we use in a moment. Generics as in Unit 01’s generic printValue function, applied to UI.

SAY

Click: the printed types make the three parameters concrete: for the strings, ForEach of Array of String, String, Text. For transactions later: ForEach of Array of Transaction, UUID, TransactionRow.

SAY

Click: so ForEach is not just a for loop. It is a view that represents a collection of child views together with their identities.

Part 3 · Transaction and Identifiable (sections 5–6)

Identity belongs to the transaction

Transaction.swift
struct Transaction: Identifiable {
    let id: UUID
    let title: String
    let amount: Int
    let date: String
}

ForEach(transactions) { transaction in   // no id: needed
    Text(transaction.title)
}
Why an id
  • Same title, amount and date can happen twice
  • Identity = the transaction, not its display
Identifiable
  • A Swift protocol: has an id
  • ForEach uses it: no id: \.id
  • No: the model must provide a suitable ID
  • Ours stores one
SAY

A real Transaction struct, from Unit 01’s structs: id, title, amount and date. Why an id? Because two transactions can have the same title, amount and date, say two coffees on the same day. Identity should represent the transaction itself, not what it looks like on screen.

SAY

Click: Swift’s Identifiable protocol says a type exposes an id. Once Transaction conforms, ForEach can use that id directly: no id: \.id argument, as the SDK initializer on the previous slide showed.

SAY

Click: does Identifiable create a UUID for you? No. The model must provide a suitable value; ours stores one. Where it comes from matters a lot, as Part 5 shows.

Part 4 · When a transaction arrives (section 14) · conceptual

Insert one; the rest keep their identity

  • Identity keeps row state attached
  • It doesn’t promise a row’s body never runs
SAY

Conceptual, and only the first stage was in the text’s widget. Click: a transaction with a stable ID arrives. Click: the state array changes. Click: the view that depends on the array is re-evaluated, giving a new ForEach description. Click: by ID, the existing three are the same elements and 104 is new. Click: layout moves the old rows down. Click: Mobile Recharge is rendered at the top.

SAY

Click: two separate concerns. Stable identity keeps the association between a transaction and its view state; it does not guarantee that a row’s body is never evaluated again. Identity preservation and view evaluation are different things.

Part 5 · Stable ID, index, computed UUID (sections 9–10, 15–16)

Flag Coffee Shop, then insert at the top

The experiment
// FlagRow has  @State private var flagged = false
ForEach(items) { FlagRow(title: $0.title) }               // 1
ForEach(items.indices, id: \.self) { i in                 // 2
    FlagRow(title: items[i].title) }
// 3: same as 1, but  var id: UUID { UUID() }

1 Stable id: flag stays on Coffee Shop

2 Index: flag jumps to Mobile Recharge

3 Computed UUID: flag lost

SAY

Each row has its own @State, a flag, the kind of row-local state a real list has: a selection, an expanded row, a text field. Three lists of the same three transactions: one with stable IDs, one using array indices as identity, one with an id that is computed as UUID() on every read. In each, we flagged Coffee Shop and then inserted Mobile Recharge at the top.

SAY

Left, stable ID: the flag stayed on Coffee Shop, which moved down. Click: middle, indices: the flag stayed at index 0, so it now sits on Mobile Recharge, a transaction the user never flagged. A real bug: positions referred to a different logical transaction. Click: right, computed UUID: every read produced a new id, so every row looked new, and the flag vanished.

Part 5 · What the rows reported (sections 9–10, 16)

Who is flagged after the insert?

1 Stable id

row Mobile Recharge: flagged = false
(only the new row’s body ran)

2 Index

row Mobile Recharge: flagged = true
row Coffee Shop: flagged = false
…

3 var id: UUID { UUID() }

row Mobile Recharge: flagged = false
row Coffee Shop: flagged = false
… all rows fresh

Plain Swift (Mac): read the id twice

computed: id == id → false
stored: id == id → true

  • Dynamic domain data: stable domain IDs
  • From the API, not the index or a fresh UUID
  • Indices for presentation only
SAY

Inside, each row printed its state when its body ran. With stable IDs, after the insert only one body ran: the new Mobile Recharge row, unflagged; Coffee Shop kept its flag without even being re-evaluated. Click: with indices, every row was re-evaluated and Mobile Recharge reported flagged = true. Click: with the computed UUID, every row was re-created fresh: all false.

SAY

Click: why the computed id fails, in plain Swift on a Mac: reading a computed id twice gives two different UUIDs; a stored id is equal to itself. Possible consequences, as the text says: lost row state, odd transitions, wasted updates.

SAY

The rule: for dynamic domain collections use stable domain IDs. For NPay, the transaction ID comes from the model and the trusted backend, not from the array index and not from a UUID generated every time data is decoded, which would make the same transaction look new on every refresh. Indices are fine for presentation, such as deciding where to draw a divider, but never as identity.

And which rows actually get built

ForEachList

1,000 transactions: row bodies evaluated

ScrollView { VStack { ForEach } }: 1000
ScrollView { LazyVStack { ForEach } }: 12

  • ForEach doesn’t decide laziness
  • The container does: eager VStack, lazy List / LazyVStack
SAY

ForEach generates child view descriptions; it does not scroll by itself, and its rows are styled by whatever contains them. List is a higher-level container that presents a list: built-in scrolling, list styling, and capabilities like selection, swipe actions and editing. Both depend on identity.

SAY

Click: Section 17 says an ordinary VStack builds its children eagerly and List or lazy containers suit large collections. We measured it: 1,000 transactions, a counter in each row’s body. Inside a plain VStack in a ScrollView: all 1,000 row bodies evaluated at launch. In a LazyVStack: 12, the rows on screen plus a few. In a List: 9.

SAY

Click: so ForEach itself does not guarantee lazy creation; the surrounding container decides. That is why NPay’s short history can live in the existing ScrollView’s VStack, but a full history should use List or a lazy stack. We do not nest a List inside our ScrollView, to avoid two competing scroll containers.

Part 7 · A reusable TransactionRow (section 12)

Everything from 2.1–2.9 in one row

TransactionRow.swift
struct TransactionRow: View {
    let transaction: Transaction

    var body: some View {
        HStack(spacing: 12) {
            Image(systemName: "creditcard")
                .font(.title2).foregroundStyle(.blue)
            VStack(alignment: .leading, spacing: 4) {
                Text(transaction.title).font(.headline)
                Text(transaction.date).font(.caption)
                    .foregroundStyle(.secondary)
            }
            Spacer()
            Text(transaction.amount, format: .currency(code: "INR")
                     .precision(.fractionLength(0)))
                .font(.subheadline.bold())
                .foregroundStyle(transaction.amount >= 0
                                 ? Color.green : Color.primary)
        }
        .padding(.vertical, 8)
    }
}

Lesson 2.10 · Recap

What to remember

ForEach = views + identities
a view, not a for loop

Identity ≠ position
stable IDs; never indices or fresh UUIDs

The container decides
VStack eager; List, LazyVStack lazy

SAY

Three things to remember. ForEach is a view that pairs each element of a collection with an identity and produces a child view for it. Identity is not position: use stable domain IDs, because indices moved our flag to the wrong transaction and a computed UUID lost it. And ForEach does not decide how many rows are built: the container does, all 1,000 in a VStack, about a dozen in a List or LazyVStack.
