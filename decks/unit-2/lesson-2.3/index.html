Part 2 · VStack is not a function (section 2)

VStack(…) calls an initializer

Interface excerpt, iOS 26.5 SDK (body omitted)
@frozen public struct VStack<Content> : View
        where Content : View {
    public init(alignment: HorizontalAlignment = .center,
                spacing: CGFloat? = nil,
                @ViewBuilder content: () -> Content)
}
In the declarationMeans

SAY

It looks like a function call, but VStack is a generic struct and we are calling its initializer. This is the real declaration from the iOS 26.5 SDK, with the body left out; the lesson text shows a simplified version of the same thing.

What is @ViewBuilder?

Part 4 · What is @ViewBuilder? (section 5)

A result builder: many views in, one value out

An array?
  • No [View]
  • A strongly typed composite value
When?
  • At compile time: a language transformation
  • Not a run-time loop or reflection
Interface excerpt
// ViewBuilder (excerpt, iOS 26.5 SDK)
static func buildBlock<each Content>(
    _ content: repeat each Content
) -> TupleView<(repeat each Content)>
    where repeat each Content : View

Exact representation varies by SwiftUI version.

SAY

@ViewBuilder is a Swift result builder used by SwiftUI. You write several view expressions in a block, and it combines them into a single composite view value; that value is the Content of the VStack.

SAY

Click: is it an array of views? No. It does not build [View]; it builds one strongly typed value. Click: and it happens at compile time: a language-supported transformation, not a run-time loop discovering child views by reflection.

SAY

Click: the SDK shows it. ViewBuilder’s buildBlock takes a parameter pack, any number of views each with its own type, and returns a TupleView of exactly those types. That is the tuple-based content the text mentions. The exact representation can change between SwiftUI versions.

CONNECT

The mechanism is plain Swift. Let’s build our own.

Part 4 · Our own result builder (section 6)

Build one: three strings, one message

StringBuilder.swift
@resultBuilder
struct StringBuilder {
    static func buildBlock(_ parts: String...) -> String {
        parts.joined(separator: " ")
    }
}

func makeMessage(@StringBuilder content: () -> String) -> String {
    content()
}

let message = makeMessage {
    "Welcome"
    "to"
    "NPay"
}
print(message)
swiftc, then run

Welcome to NPay

The same mechanism
  • buildBlock gets every expression
  • and returns one result
  • @ViewBuilder: richer rules, for views
SAY

Before going further into SwiftUI, the plain Swift feature. A struct marked @resultBuilder with a static buildBlock that joins strings with spaces. A function whose closure parameter is marked @StringBuilder. And a call with three string expressions on three lines.

SAY

Click: we compiled and ran it: "Welcome to NPay". The compiler passed all three expressions to buildBlock, which returned one String.

SAY

Click: @ViewBuilder is the same mechanism with a much richer set of rules for composing views; its buildBlock returns a TupleView instead of a String.

Part 5 · The generic Content type (sections 7, 13)

The compiler infers Content

Experiment.swift
let stack = VStack(spacing: 20) {
    Text("NPay")
    Text("Payments made simple")
}
print(type(of: stack))
Why it matters
  • Static checking and efficient composition
  • Also why SwiftUI errors can be long
Contenttype(of:) in the simulator
VStack { Text }VStack<Text>
VStack { Text; Image }VStack<TupleView<(Text, Image)>>
Section 13: two TextsVStack<TupleView<(Text, Text)>>
Nested stacks (section 14)VStack<VStack<Text>>
  • Not a collection assembled at run time
  • One concrete generic type, built by @ViewBuilder
SAY

With one child, the compiler infers that the closure produces Text, so the stack is VStack of Text. With two children, the builder combines them, and the stack is still strongly typed. We printed the types in the simulator, as Section 13 suggests: one child gives VStack of Text; Text and Image give VStack of TupleView of Text and Image; Section 13’s two Texts give a TupleView of Text and Text; and a stack in a stack is VStack of VStack of Text.

SAY

Click: SwiftUI uses this compile-time type information extensively, for static checking and efficient composition. It is also why a mistake inside a big SwiftUI expression can produce a long, confusing compiler message: the types are long.

SAY

Click: so a VStack is not a dynamically assembled collection of arbitrary objects. It is one concrete generic type whose content @ViewBuilder built. The printed names can vary between compiler and SwiftUI versions.

Part 6 · How VStack arranges children (section 8)

Five steps, no Y coordinates

  • Space between adjacent children
  • Not padding around the stack
SAY

VStack is a layout container; its job is to arrange children along the vertical axis. A simplified process. Click: it receives a size proposal from its parent. Click: it works out the space its children need. Click: it accounts for spacing and layout priorities. Click: it chooses its own size. Click: it positions the children vertically. You never give a child a Y coordinate.

SAY

Click: spacing: 20 means 20 points between adjacent arranged children. It does not add 20 points around the whole stack. Spacing and padding solve different problems; the next slides show both.

Padding on the stack, or on each child

SAY

Version A: spacing 20 between the two texts, then padding 30 around the resulting stack, then a yellow background so we can see it. Measured 235.7 by 128.7 points.

SAY

Click: version B puts padding 30 on each child instead. Each child’s own layout size grows, so the stack is 60 points taller: 188.7. Same width, because the widest child plus 60 is the same either way. Not equivalent: modifiers affect layout composition.

SAY

Click: and to answer the text’s question: .padding written after the closing brace is not applied to the closure. The closure produces the content; the initializer produces the VStack; .padding is called on that VStack.

SAY

How does SwiftUI decide this stack’s height? A simplified model: the stack’s height is about the first child’s height, plus the second’s, plus the spacing. The text illustrates it with 41, 20 and 20, giving 81 points.

SAY

Click: we measured the real thing. The title chose 48.7 points, the subtitle 21.0, the spacing is 20, and the stack is 89.7 points: exactly the sum. The stack’s width, 158, is its widest child. Real layout also considers proposals, flexibility and priorities, which did not come into play here.

SAY

Click: that is why you never give a child a Y coordinate. The container computes positions from child sizes, spacing and alignment.

Part 7 · Nested stacks (section 14)

Is nesting stacks bad?

Nested.swift
VStack {
    VStack {
        Text("NPay")
    }
}
type(of:)

VStack<VStack<Text>>

Not by itself
  • SwiftUI is built for composition
  • Cost depends on hierarchy, layout, dependencies, rendering
  • Don’t optimise by counting VStacks
  • Profile real bottlenecks
SAY

A stack inside a stack: its type is simply VStack of VStack of Text. Is nesting always bad? No. SwiftUI is designed for compositional layouts, and the real cost depends on the view hierarchy, layout complexity, dependencies and rendering.

SAY

Click: avoid premature optimisation based only on how many VStacks you wrote. For complex layouts, profile and investigate actual bottlenecks; Instruments comes later in the course.

What to remember

VStack is a generic struct
the closure supplies Content

@ViewBuilder builds one value
a typed TupleView, at compile time

Layout from sizes
children + spacing; padding is separate

SAY

Three things to remember. VStack is a generic struct: VStack(spacing:) calls its initializer, and the trailing closure supplies the Content. @ViewBuilder is a result builder that turns several view expressions into one strongly typed value at compile time, such as a TupleView. And the stack lays itself out from its children’s sizes plus spacing; padding, alignment and frames are separate decisions.
