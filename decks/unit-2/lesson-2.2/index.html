Part 3 · How the symbol is resolved (section 4) · conceptual

From symbol name to visible icon

  • The compiler sees only a String
  • The platform resolves the name at run time
SAY

A conceptual pipeline; Apple does not publish exactly how symbol lookup and rendering work inside. Click: our code creates an Image value that stores the name. Click: SwiftUI evaluates body and receives that description. Click: at run time the name is looked up in the system symbol set.

SAY

Click: the symbol is configured from its environment: font size and weight, foreground style. Click: layout, the stage the text shows: SwiftUI determines the symbol’s size and placement. Click: rendering draws the vector symbol at that size.

SAY

Click: the key point. Swift’s compiler never turns "creditcard.fill" into pixels; it sees only a String. The platform resolves the name at run time. So what happens with a name that does not exist?

Part 4 · Where .system(size: 64) comes from (section 6)

.system(size:) is inferred from context

Inference.swift
.font(.system(size: 64))         // short form
.font(Font.system(size: 64))     // long form
Contextual type inference
  • .font() expects a Font
  • so .system(size: 64) is Font.system(size: 64)
  • Same feature as .largeTitle in 2.1
type(of:) in the simulator

Image(…).font(…):
ModifiedContent<Image,
_EnvironmentKeyWritingModifier<Optional<Font>>>

Text(…).font(…):
Text

  • On an Image, .font writes the environment
  • The symbol reads that font
SAY

.font expects a Font value, so the compiler looks .system(size: 64) up on Font: the long form is Font.system(size: 64). Contextual type inference again, the same feature as .largeTitle in Lesson 2.1.

SAY

Click: but the modifier itself is different. We printed the types. On Text, .font returned plain Text, as in 2.1. On Image it returned ModifiedContent of Image and an environment-writing modifier for an optional Font. The underscore name is SwiftUI internal, but the shape is clear.

SAY

Click: on an Image, .font puts a font into the environment, and the symbol reads it from there to choose its size. That is the mechanism behind "symbols follow typography".

Part 5 · Apply a foreground style (section 7)

One symbol, any colour

ContentView.swift
Image(systemName: "creditcard.fill")
    .font(.system(size: 64))
    .foregroundStyle(.blue)    // or Color.blue

.blue, .green, .red

No new resource
  • The same symbol, three styles
Interface excerpt, iOS 26.5 SDK
extension ShapeStyle where Self == Color {
    static var blue: Color { get }
}
How .blue is found
  • foregroundStyle expects some ShapeStyle
  • This extension supplies .blue as a Color
SAY

foregroundStyle applies a foreground style to the symbol. Instead of the text’s colour buttons, the simulator: the same symbol with .blue, .green and .red. The foreground style changes how the symbol is presented without needing a different image resource.

SAY

Click: .blue is shorthand, resolved by Swift’s type system; Color.blue is the long form. Here is how. foregroundStyle is generic: it expects some ShapeStyle. The SDK has an extension on ShapeStyle, only where Self is Color, that declares static var blue.

SAY

Click: so when the compiler needs a ShapeStyle and sees .blue, it finds this member and gets a Color. Protocol extensions with a where clause, from Unit 01.

Part 6 · Image versus Text (section 8)

Both conform to View

So both accept
  • .padding(), .foregroundStyle(), …
Interface, iOS 26.5 SDK

@frozen public struct Image : Equatable, Sendable
extension Image : View

type(of:) in the simulator

Image(…).foregroundStyle(.blue):
ModifiedContent<Image, _ForegroundStyleModifier<Color>>

  • Text has its own overloads that keep Text
  • Image uses the general View modifiers: wrapped
SAY

Two SwiftUI types now: Text and Image. Both conform to View, Text for textual content and Image for graphical content. That is why both support common modifiers like padding and foregroundStyle: those are View modifiers.

SAY

The SDK declares Image exactly like Text: a frozen struct, Equatable and Sendable, with the View conformance in an extension.

SAY

Click: one difference shows in the types. Image’s foregroundStyle returned ModifiedContent of Image and a foreground-style modifier. Click: Text has its own font, bold and foregroundStyle overloads that keep it Text, as we measured in 2.1; Image uses the general View modifiers, which wrap it.

Part 6 · System images and asset images (section 9)

systemName: or an asset name

Two forms
Image(systemName: "creditcard.fill")   // SF Symbol
Image("NPayLogo")                      // Assets.xcassets
FeatureSF SymbolAsset image
Sourcesystem symbol libraryapp-provided resource
Typical usestandard interface iconsbranding, custom artwork
Scalingdesigned for scalable symbolsdepends on resource and configuration
Stylingsymbol-specific modestemplate or original rendering
Availabilitydepends on OS and symbol versionbundled with the app
  • Asset catalog compiled at build time
  • Looked up in the app’s resources at run time
SAY

Two common forms. Image(systemName:) references an SF Symbol. Image("NPayLogo"), with no label, looks for an image resource named NPayLogo, usually in Assets.xcassets.

SAY

The table: symbols come from the system library, assets from your app. Symbols suit standard interface icons, assets suit branding and custom artwork. Symbols are designed to scale; an asset depends on its resource type and configuration. Symbols have symbol-specific styling modes; assets use template or original rendering. And symbol availability depends on the OS and symbol version, while assets ship inside your app.

SAY

Click: an asset named NPayLogo is processed by Xcode’s asset catalog tools during the build, and at run time SwiftUI resolves it through the app’s resources. A different path from resolving an SF Symbol.

What to remember

Names resolve at run time
the compiler sees a String

Symbols follow the font
size and weight from .font

Symbol or asset
systemName: decides where to look

SAY

Three things to remember. A symbol name is just a String to the compiler; the platform resolves it at run time, so a typo builds and shows nothing. Symbols are typographic: .font writes the environment and the symbol takes its size and weight from it, staying sharp at any size. And Image(systemName:) looks in the system symbol set, while Image("name") looks in your app’s assets.
