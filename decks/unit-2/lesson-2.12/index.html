Part 3 · Convert input to paise safely (sections 3–4)

parsePaise: syntax, then exact integers

Money.parsePaise
static func parsePaise(_ text: String) -> Int? {
    let pattern = #"^[0-9]+(\.[0-9]{1,2})?$"#
    guard text.range(of: pattern, options: .regularExpression)
          != nil else { return nil }
    let parts = text.split(separator: ".",
                           omittingEmptySubsequences: false)
    guard let rupees = Int(parts[0]) else { return nil }
    let fraction = parts.count > 1 ? String(parts[1]) : ""
    let padded = fraction.padding(toLength: 2, withPad: "0",
                                  startingAt: 0)
    guard let paise = Int(padded) else { return nil }
    let (rupeePaise, o1) = rupees.multipliedReportingOverflow(by: 100)
    guard !o1 else { return nil }
    let (total, o2) = rupeePaise.addingReportingOverflow(paise)
    guard !o2 else { return nil }
    return total
}

SAY

The amount travels as an Int of paise, the smallest INR unit: ₹1 is 100, ₹10.50 is 1,050, ₹1,500 is 150,000. Integers are exact, so no floating-point rounding, as 2.11 showed, and it matches the paise model from Unit 01.

SAY

parsePaise checks the syntax with the regex first, splits rupees and fraction, pads the fraction to two digits, and combines them with overflow-reporting arithmetic, returning nil instead of crashing. Click: we ran it on a Mac: "1" is 100, "10.50" is 1050, "1500" is 150000, "0.5" is 50; "12.345" and "-500" fail the regex; and "92233720368547759" passes the regex and fits an Int, but times 100 overflows, so the overflow check returns nil.

SAY

Click: compare Double(amountText)!: a crash on bad input, and an inexact number on good input. Still a teaching implementation; production money needs a full domain model.

Part 4 · Implement the demo payment (section 6)

The parent validates again, then updates

ContentView.sendDemoPayment
private func sendDemoPayment(to recipient: String,
                             amountPaise: Int) -> Bool {
    let trimmed = recipient.trimmingCharacters(
        in: .whitespacesAndNewlines)

    guard !trimmed.isEmpty,
          amountPaise > 0,
          amountPaise <= balancePaise else {
        statusMessage = "Invalid payment request."
        return false
    }

    balancePaise -= amountPaise
    transactions.insert(
        Transaction(id: UUID(), title: "Sent to \(trimmed)",
                    amountPaise: -amountPaise, date: .now),
        at: 0)
    statusMessage = "Demo payment recorded."
    return true
}
Two mutations, one action
  • balancePaise and transactions
  • In one synchronous call: consistent on screen
  • No durability across crashes or devices
  • SwiftUI coordinates UI, it isn’t a transaction engine
SAY

sendDemoPayment is the only place money changes. It validates again on the parent’s side: a trimmed, non-empty recipient, an amount above zero and not above the balance. The form checked too, but the owner of the state does not trust the caller blindly, a habit we keep all the way to the backend. If valid, it subtracts from the balance, inserts a "Sent to" transaction with a negative amount and the current date, sets a status message, and returns true; otherwise it sets an error status and returns false.

SAY

Both the balance and the transaction list change in one synchronous call, so the screen never shows one without the other. Click: but this is not a database transaction: nothing is durable across a crash or another device. SwiftUI coordinates UI updates; it is not a financial transaction engine. Authoritative transactions belong on the backend, later in the course.

Nearly every Unit 2 idea, in one flow

NPay after Unit 2

SAY

The whole app: ContentView owns the balance, the transactions and the status. BalanceCard reads a value; BalanceEditor has a binding; QuickActions take closures; PaymentForm owns input, validation and focus and sends requests up; TransactionHistory uses ForEach with stable identity; sendDemoPayment is the single place money changes.

SAY

The flow connects nearly every idea in the unit: TextField, binding, @State, a button action, the onSend closure, validation in the owner, state mutation, and SwiftUI updating the card and the history.

SAY

Click: the honest review. It is a learning prototype. Payment rules live in a view; nothing is persisted; the records are mock data; there is no authentication, networking, server authority or test suite. And the balance editor is a teaching control: a real banking app must never let the user change an authoritative balance. Each of these limits is addressed by a later unit.
