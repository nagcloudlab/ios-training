Part 2 · What is a view modifier? (section 2)

A chain of method calls

ContentView.swift
Text("NPay")
    .font(.largeTitle)
    .foregroundStyle(.blue)
    .padding()
One view, three calls
  • Each returns a new view description
  • The original is not mutated
Method chaining (Unit 01)
let title = Text("NPay")
let styled = title.font(.largeTitle)
let padded = styled.padding()
  • Each result is the next receiver
  • Types can change along the chain: generics
SAY

One initial view value and three modifier calls. A modifier generally returns a new view description; it does not mutate the original value. Text, then font, then foregroundStyle, then padding: a final composed view.

SAY

This is ordinary Swift method-call syntax, from Unit 01. Written out with names: title, then styled from title, then padded from styled. Each call’s result becomes the receiver of the next call.

SAY

Click: and the types can change along the chain. That is where generics come in.

ModifiedContent is a public generic struct that combines a content view and a modifier, and it is still a View, so you can keep chaining. Swift type-checks the whole chain at compile time; SwiftUI interprets the layout and styling at run time.

Click: not every modifier returns ModifiedContent. Click: the text-specific ones on Text, such as font and foregroundStyle, return Text, as we saw in 2.1. And no, a modifier does not create a new UIKit view; there is no one-to-one mapping.

Why can every kind of view use .padding?

Part 2 · Why almost every view has .padding() (section 4)

Modifiers come from the View API

  • Conform to View → get every View modifier
  • Including ContentView and your own views
SAY

.padding is part of SwiftUI’s View API: it is declared in an extension on View. Text, Image, VStack, HStack and ZStack all conform to View, and so does every struct you write with ": View". Conforming gives them all the common modifiers: padding, frame, background, overlay.

SAY

Click: that is one of the reasons SwiftUI is so composable. Your own ContentView and BalanceCard get the same modifiers for free; Part 7 adds our own modifier to that list.

The card’s content with three layout-related modifiers. Layout modifiers change how size proposals and chosen sizes flow through the composition. SAY

.frame adds a layout container that proposes and reports dimensions by its own rules. It does not resize the glyphs. On the right, the text’s three frames with blue borders, run at title size in place of the text’s slider.

SAY

Click: measured. The frame is exactly 200 by 100; the Text inside it is still 64 by 41.7, its own size, centred. So .frame(width: 200) does not make the text 200 points wide; it makes the region 200 wide. With maxWidth .infinity the frame took the full 370 points the parent offered.

SAY

Click: .infinity is an unbounded maximum in the layout API, not physical infinite width; negotiation decides the real size. Click: and a view can occupy a wide frame while its visible content stays small, which is why alignment .leading is useful: it places the content within the larger region, as the third row shows.

Part 5 · Environment-driven modifiers (sections 9, 15)

Set it on the parent; children inherit

Environment.swift
VStack {
    Text("NPay")
    Text("Payments made simple")
}
.font(.title)

VStack {
    Text("Available Balance")
        .foregroundStyle(.yellow)
    Text("₹25,000")
}
.foregroundStyle(.white)
Flows down
  • .font, .foregroundStyle
  • Through the environment
  • A child can override
  • .padding(): only around the view it is on

Middle: .padding() on the stack only. Bottom: on blue to show white

SAY

Top on the right: .font(.title) on the VStack reaches both texts. The parent does not mutate each child; SwiftUI propagates environment values down the hierarchy, and each Text reads the font.

SAY

Bottom: .foregroundStyle(.white) on the stack, with the first Text overriding it with yellow. The first is yellow, the second inherits white. We added a blue background so white is visible. That is how a reusable component sets default styles high up while specific children override them.

SAY

Click: not every modifier propagates. The middle example puts .padding() on the stack: the blue border shows space around the stack only; the grey-bordered children got no padding of their own. Knowing which modifiers flow down matters when you build reusable components.

Part 6 · A reusable balance card (section 10)

BalanceCard: order on purpose

BalanceCard.swift
struct BalanceCard: View {
    var body: some View {
        VStack(alignment: .leading, spacing: 12) {
            Text("Available Balance")
                .font(.subheadline)
            Text("₹25,000")
                .font(.largeTitle.bold())
            Text("NPay Demo Account")
                .font(.caption)
        }
        .foregroundStyle(.white)
        .frame(maxWidth: .infinity, alignment: .leading)
        .padding(24)
        .background(.blue, in: RoundedRectangle(cornerRadius: 20))
    }
}

Part 6 · Evaluating BalanceCard (section 12) · conceptual

Constructing a view ≠ evaluating its body

Trace.swift (excerpt)
struct TracedCard: View {
    init() { print("2. TracedCard value constructed") }
    var body: some View {
        let _ = print("3. TracedCard.body evaluated")
        BalanceCard()
    }
}
// parent body: let _ = print("1. … body evaluated")
Simulator console, at launch

1. TraceView.body evaluated
2. TracedCard value constructed
3. TracedCard.body evaluated

SAY

A conceptual walk; only the final stage, rendering, was in the text’s widget. Click: the parent’s body is evaluated. Click: inside it, BalanceCard() constructs a Swift value, nothing more. Click: SwiftUI evaluates BalanceCard’s body when it needs it. Click: the modifiers wrap the VStack into a nested description. Click: layout. Click: rendering produces the text and the rounded blue card.

SAY

We made steps 1 to 3 visible: a print in the parent’s body, in the card’s init and in the card’s body. At launch the console shows exactly that order: parent body, card constructed, card body.

SAY

The point: constructing a view value and evaluating its body are separate operations. SwiftUI can evaluate bodies selectively; it does not necessarily run every body on every update. Prints like these are for learning, never for app logic.

Part 7 · A custom ViewModifier (sections 16–17)

NPayCardStyle, and a View extension

NPayCardStyle.swift
struct NPayCardStyle: ViewModifier {
    func body(content: Content) -> some View {
        content
            .padding(20)
            .background(
                Color.blue.opacity(0.08),
                in: RoundedRectangle(cornerRadius: 16)
            )
    }
}

extension View {
    func npayCardStyle() -> some View {
        modifier(NPayCardStyle())
    }
}

plain · .modifier · .npayCardStyle()

type(of:), both forms

ModifiedContent<Text,
NPayCardStyle>

Unit 01, again
  • A protocol, no UIKit subclass
  • Extension on View: every view gets it
SAY

SwiftUI defines a ViewModifier protocol. NPayCardStyle conforms to it: its body receives the content being modified and returns a composed view, here padded with a pale blue rounded background. Apply it with .modifier(NPayCardStyle()).

SAY

Then a View extension adds npayCardStyle(), so you can write it like any built-in modifier. On the right: plain, with .modifier, and with .npayCardStyle(). Click: both forms print the same type, ModifiedContent of Text and NPayCardStyle: our own type sits exactly where _PaddingLayout sat earlier.

SAY

Click: no UIKit subclass: a struct conforming to a protocol. And because the extension is on View, every conforming view can call it: protocol extensions from Unit 01, and one consistent NPay design language without repeated styling code.

So when do you write a view, and when a modifier?

Part 7 · Custom modifier or reusable view? (section 18)

Component or styling rule?

Reusable viewCustom ViewModifier
Encapsulatescontent and structurea transformation or styling
ExampleBalanceCardNPayCardStyle
Canown state or receive modelsdecorate or modify content
Representsa meaningful UI componentreusable presentation behaviour
A view when
  • It is a recognisable UI element
  • with its own content and behaviour
A modifier when
  • It is a styling rule
  • for many unrelated views
SAY

An architecture decision. A reusable view encapsulates content and structure, like BalanceCard; it can own state or receive models, and it represents a meaningful UI component. A custom ViewModifier encapsulates a transformation or styling behaviour, like NPayCardStyle; it decorates content and represents reusable presentation behaviour.

SAY

Click: the rule of thumb. If it is a recognisable UI element with its own content and behaviour, make a view. If it is a styling rule you would apply to many unrelated views, make a modifier.

Lesson 2.6 · Recap

What to remember

Modifiers wrap
a new value and often a new type

Order is structure
what wraps what decides the result

Some flow down
font and style via the environment

SAY

Three things to remember. A modifier returns a new view, usually a ModifiedContent wrapping the old one, sometimes the same type, as Text’s own modifiers do. Order is structure: each modifier wraps the result of the one before, so changing the order changes the composition. And some modifiers, like font and foregroundStyle, flow down the environment to children, while others, like padding, stay on the view they are applied to.
