Simplified iOS process memory

Conceptual regions, not their physical order. iOS uses virtual memory, not fixed partitions of RAM.

Part 2 · Swift nuance

Not simply stack versus heap

Common belief

“Structs live on the stack; classes live on the heap.”

In Swift

A struct is not guaranteed to live on the stack: stored in a class, an array or an escaping closure, it lives on the heap. And a class instance that never escapes its function may be placed on the stack by the optimizer.

Value semantics versus reference semantics, not simply stack versus heap.
SAY

Developers from other languages often learn "structs on the stack, classes on the heap". In Swift that is not a guarantee. A struct stored inside a class instance, an array or an escaping closure lives on the heap. And the optimizer may place a class instance on the stack when it can prove the instance never escapes the function. Placement is an implementation detail.

SAY

The reliable language-level distinction is value semantics versus reference semantics.

Part 3 · Value type

A struct: independent values

Account.swift
struct Account {
    var balanceMinor: Int64      // paise
}

var accountA = Account(balanceMinor: 500_000)   // ₹5,000
var accountB = accountA

accountB.balanceMinor = 900_000

print(accountA.balanceMinor)   // 500000
print(accountB.balanceMinor)   // 900000
Assigning accountA to accountB gives independent values.
SAY

NPay stores money as whole paise in an Int64, balanceMinor, so 500,000 paise is ₹5,000. accountB starts as a copy of accountA. Click: we change accountB to ₹9,000; accountA still shows ₹5,000. Each variable changes separately.

Now the same code with a class.

Part 3 · Reference type

A class: one shared instance

Account.swift
final class Account {
    var balanceMinor: Int64      // paise
    init(balanceMinor: Int64) { self.balanceMinor = balanceMinor }
}

let accountA = Account(balanceMinor: 500_000)   // ₹5,000
let accountB = accountA

accountB.balanceMinor = 900_000

print(accountA.balanceMinor)   // 900000
print(accountB.balanceMinor)   // 900000
Both variables reference the same instance.
SAY

With a class, accountA and accountB are two references to one instance. Click: change the balance through accountB and accountA sees ₹9,000 too.

ASK

Why can accountA be a let constant and still change?

EXPECT

let fixes the reference, not the instance it points to. The instance itself is mutable.

Part 4 · ARC · conceptual

Counting strong references

Each strong reference is a cook still using an ingredient from the pantry. When nobody is using it, it can be cleared away.

Conceptual. The compiler and runtime may optimize reference-count operations; they are not necessarily visible one-for-one.

SAY

ARC tracks strong references to a class instance. When no strong references keep it alive, it can be deinitialized. Click through: three references, then two, then one, then none, and the object can be destroyed.

Part 4 · ARC in code

Setting one reference to nil

Customer.swift
final class Customer {
    let name: String
    init(name: String) { self.name = name }
    deinit { print("Customer destroyed") }
}

var customer1: Customer? = Customer(name: "Ravi")
var customer2 = customer1

customer1 = nil   // still alive through customer2
customer2 = nil   // no strong references: deinit runs
1Two strong referencescustomer1 and customer2 point to Ravi
2customer1 = nilthe instance is still alive through customer2
3customer2 = nilno strong references remain; deinit can run
Setting one variable to nil does not necessarily destroy the instance.
SAY

Two variables reference the same Customer. Setting customer1 to nil releases one reference, but the object survives through customer2. Only when customer2 is also nil do no strong references remain, and deinit can execute.

ASK

After customer1 = nil, has "Customer destroyed" printed?

EXPECT

No. customer2 still holds a strong reference.

Part 5 · Reference kinds

Strong, weak and unowned

Strong ownership is normal and necessary. A parent strongly owns its child; a child may hold a weak reference back.
SAY

Click through the three. Strong keeps the instance alive and is the default. Weak does not keep it alive; it is optional and becomes nil automatically when the instance is deallocated. Unowned does not keep it alive either, and assumes the instance is still alive whenever accessed: accessing it after deallocation traps, a deliberate crash.

SAY

There is also unowned(unsafe), which skips even that check: accessing a deallocated instance is then undefined behaviour. Lesson 1.8 goes deeper into unowned and ownership.

SAY

Do not replace every strong reference with weak. A parent usually strongly owns a child; the child may hold a weak back-reference to a parent that can disappear independently.

Part 6

Retain cycles

The classic ARC problem

SAY

Imagine two people holding each other's hands and refusing to let go.

CONNECT

In Swift, two class instances can do the same.

Part 6 · Retain cycle · conceptual

Two objects that never let go

Ownership.swift
class Person { var apartment: Apartment? }
class Apartment { var tenant: Person? }

var person: Person? = Person()
var apartment: Apartment? = Apartment()
person?.apartment = apartment
apartment?.tenant = person

person = nil
apartment = nil   // neither instance is freed
weak var tenant: Person? The apartment no longer owns its tenant, so both instances are freed.
SAY

Person strongly references its apartment and Apartment strongly references its tenant. Both are also reachable from outside variables. Click: set the outside variables to nil. The two instances still retain one another, so neither is released: a leak.

SAY

Click: make Apartment’s reference to its tenant weak, one word: weak var tenant. Now nothing keeps Person alive once the outside reference goes, and the cycle no longer prevents deallocation. With deinit messages in both classes, both would print.

CONNECT

Cycles between two classes are easy to spot. Cycles through closures are not.

SAY

A closure is a block of code that can capture values from its surrounding context, including self.

Part 7 · Closure cycle

A closure that captures self

DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    var onUpdate: (() -> Void)?

    func configure() {
        onUpdate = {
            print(self)       // captures self strongly
        }
    }

    deinit { print("DashboardViewModel destroyed") }
}
SAY

The ViewModel owns its onUpdate closure. The closure captures self strongly, and self is the ViewModel. Both keep each other alive.

SAY

Click: the external owner releases the ViewModel. The cycle remains, so deinit never runs.

CONNECT

The fix is a capture list.

Part 7 · Fix

[weak self]

DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    var onUpdate: (() -> Void)?

    func configure() {
        onUpdate = { [weak self] in
            guard let self else { return }
            print(self)
        }
    }
}
1[weak self]the closure no longer retains the ViewModel
2guard let selfa temporary strong reference while the closure runs, if the object still exists
SAY

[weak self] prevents the closure from retaining the ViewModel through its capture. guard let self temporarily obtains a strong reference while the closure executes, if the object still exists; otherwise it returns.

Part 8 · Capture experiment · conceptual

Strong vs weak capture

[weak self] matters for escaping closures that are retained and create a cycle. A short-lived, non-escaping closure does not need it.
SAY

Strong capture: release the external owner and the ViewModel stays alive in an ownership cycle. Click: with weak capture, the same release lets the ViewModel be deallocated.

Do not teach [weak self] as mandatory for every closure. It matters for escaping closures retained in a way that creates an unwanted cycle or extends a lifetime beyond what is intended. A short-lived non-escaping closure does not automatically need it.

Weak: apartment and tenant

The tenant can move out, so the apartment’s reference to its tenant is weak.

SAY

Strong keeps the object alive; the risk is a retain cycle. Weak does not, and becomes nil on deallocation; the risk is that it may be nil. Unowned does not keep it alive and does not become nil; invalid access may crash.

SAY

The tenant can move out, so the apartment’s reference is weak. A credit card that cannot exist without its customer can hold an unowned reference back to it, provided that lifetime guarantee is enforced: the customer strongly owns the card, and the card is never used after the customer is gone.

SAY

Reach for weak first; use unowned only when the lifetime guarantee is real. Lesson 1.8 goes deeper, including unowned(unsafe), which removes the safety check and makes a bad access undefined behaviour.

Part 10 · Two problems

Leak vs high usage

Memory leak

Memory stays allocated though no longer needed, and cannot be reclaimed through the intended ownership path.

High memory usage

The app uses a lot of memory. That may be legitimate, or a sign of excessive caching or allocation.

NPay keeps recent merchant logos in a cache: not a leak. But a cache that grows without bounds can still cause memory problems, even when everything stays reachable.

SAY

A leak is memory that stays allocated though no longer needed and cannot be reclaimed through the intended ownership path. High memory usage may be legitimate, or may indicate excessive caching or allocation.

SAY

An app can use a lot of memory without leaking; and a small leak repeated thousands of times can eventually cause serious memory pressure. A merchant-logo cache is fine until it grows without bounds.

Three memory tools

ToolShowsGood at findingCan miss
Memory Graph DebuggerLive objects and who references them, at one momentAn instance that should be gone, and the strong chain holding itGrowth over time

A retain cycle hiding in plain sight

Part 12 · Timer cycle

A repeating timer that never lets go

DashboardViewModel.swift
@MainActor @Observable
final class DashboardViewModel {
    var timer: Timer?
    func startAutoRefresh() {
        timer = Timer.scheduledTimer(withTimeInterval: 30,
                                     repeats: true) { _ in
            MainActor.assumeIsolated { self.refreshBalance() }
        }
    }
    func refreshBalance() { print("Refreshing balance") }
    deinit { print("destroyed") }   // never prints
}
The run loop keeps a repeating timer alive until invalidate(). Through the closure, it keeps the ViewModel alive too, so deinit never runs and cleanup there never happens.
SAY

NPay refreshes the balance every 30 seconds. Follow the chain: the run loop keeps a scheduled repeating timer alive until it is invalidated; the timer retains its closure; the closure captures self strongly. So the ViewModel stays alive even after the dashboard is gone, and the timer keeps firing.

SAY

The ViewModel’s own timer property is not what keeps the timer alive; the run loop is. The property only lets the ViewModel invalidate it. That is why putting invalidate() in deinit cannot work: deinit never runs while the chain exists.

SAY

Two Swift 6 details: the timer block is a Sendable closure, so the ViewModel is @MainActor, and because the timer was scheduled on the main run loop, its block runs on the main thread, so MainActor.assumeIsolated is safe there.

CONNECT

So what is the safer design?

Part 12 · Fix

Weak capture and explicit cancellation

DashboardViewModel.swift
func startAutoRefresh() {
    timer = Timer.scheduledTimer(withTimeInterval: 30,
                                 repeats: true) { [weak self] _ in
        MainActor.assumeIsolated { self?.refreshBalance() }
    }
}

func stopAutoRefresh() {   // call when the dashboard goes away
    timer?.invalidate()
    timer = nil
}
Weak capturethe closure no longer keeps the ViewModel alive
Explicit invalidationthe run loop lets go of the timer, and it stops firing
They solve related but distinct problems: ownership versus ongoing activity.
SAY

Weak capture stops the closure owning the ViewModel, so it can be deallocated. But the run loop still holds the timer, and it would keep firing with a nil self. Explicit invalidation in stopAutoRefresh, called when the dashboard goes away, for example from onDisappear, stops that activity. Related but distinct problems; you usually need both.

SAY

A modern alternative is a Task loop that sleeps between refreshes and is cancelled when the screen goes away. Lesson 8.3 covers task lifetimes and cancellation.
