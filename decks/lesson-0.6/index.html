Part 2 · Swift nuance

Not simply stack versus heap

Common belief

“Structs live on the stack; classes live on the heap.”

In Swift

A struct is not guaranteed to live on the stack, and a class reference variable is not necessarily on the heap. Placement depends on implementation and optimization.

Value semantics versus reference semantics, not simply stack versus heap.
SAY

Developers from other languages often learn "structs on the stack, classes on the heap". In Swift that is not a guarantee: storage placement depends on the implementation and optimization.

SAY

The reliable language-level distinction is value semantics versus reference semantics.

Value type versus reference type

Part 3 · Value type

A struct: independent values

Account.swift
struct Account {
    var balance: Int
}

var accountA = Account(balance: 5000)
var accountB = accountA

accountB.balance = 9000

print(accountA.balance) // 5000
print(accountB.balance) // 9000
Assigning accountA to accountB gives independent values.
SAY

accountB starts as a copy of accountA. Click: we change accountB to ₹9,000; accountA still shows ₹5,000. Each variable changes separately.

Now the same code with a class.

Part 3 · Reference type

A class: one shared instance

Account.swift
class Account {
    var balance: Int

    init(balance: Int) {
        self.balance = balance
    }
}

let accountA = Account(balance: 5000)
let accountB = accountA

accountB.balance = 9000

print(accountA.balance) // 9000
print(accountB.balance) // 9000
Both variables reference the same instance.
SAY

With a class, accountA and accountB are two references to one instance. Click: change the balance through accountB and accountA sees ₹9,000 too.

ASK

Why can accountA be a let constant and still change?

EXPECT

let fixes the reference, not the instance it points to. The instance itself is mutable.

Part 4 · ARC · conceptual

Counting strong references

Each strong reference is someone holding a booking for a conference room. When nobody holds it, the room is released.

Conceptual. The compiler and runtime may optimize reference-count operations; they are not necessarily visible one-for-one.

SAY

ARC tracks strong references to a class instance. When no strong references keep it alive, it can be deinitialized. Click through: three references, then two, then one, then none, and the object can be destroyed.

SAY

An object is like a rented conference room; each strong reference is someone holding a valid booking. When nobody holds the room, it can be released.

Part 4 · ARC in code

Setting one reference to nil

Customer.swift
class Customer {
    let name: String

    init(name: String) {
        self.name = name
        print("Customer created")
    }

    deinit {
        print("Customer destroyed")
    }
}

var customer1: Customer? = Customer(name: "Ravi")
var customer2 = customer1

customer1 = nil
// Object is still alive through customer2

customer2 = nil
// No strong references remain
// deinit can execute
1Two strong referencescustomer1 and customer2 point to Ravi
2customer1 = nilthe instance is still alive through customer2
3customer2 = nilno strong references remain; deinit can run
Setting one variable to nil does not necessarily destroy the instance.
SAY

Two variables reference the same Customer. Setting customer1 to nil releases one reference, but the object survives through customer2. Only when customer2 is also nil do no strong references remain, and deinit can execute.

ASK

After customer1 = nil, has "Customer destroyed" printed?

EXPECT

No. customer2 still holds a strong reference.

Strong, weak and unowned

Three ownership relationships

SAY

Swift provides different ownership relationships for different lifetime situations.

CONNECT

Here are the three.

Part 5 · Reference kinds

Strong, weak and unowned

Strong

Keeps the instance alive. Strong ownership is the default.

Weak

Does not keep it alive. Optional, and automatically becomes nil when the instance is deallocated.

Unowned

Does not retain it. Assumes the instance is still alive whenever accessed; violating that can crash.

A parent usually strongly owns a child. A child may hold a weak reference back to a parent that can disappear independently. Use unowned only when the lifetime relationship guarantees safe access.

Do not replace every strong reference with weak. Strong ownership is normal and necessary.
SAY

Strong keeps the instance alive and is the default. Weak does not keep it alive; it is optional and becomes nil automatically when the instance is deallocated. Unowned does not retain it either, but assumes the instance is still alive whenever accessed; violating that assumption can cause a runtime failure.

SAY

A parent usually strongly owns a child; the child may hold a weak back-reference. And do not teach students to replace every strong reference with weak: weak and unowned solve particular lifetime relationships.

What goes wrong when two objects own each other?

Part 6

Retain cycles

The classic ARC problem

SAY

Imagine two people holding each other's hands and refusing to let go.

CONNECT

In Swift, two class instances can do the same.

Part 6 · Retain cycle · conceptual

Two objects that never let go

Ownership.swift
class Person {
    var apartment: Apartment?
}

class Apartment {
    var tenant: Person?
}

var person: Person? = Person()
var apartment: Apartment? = Apartment()

person?.apartment = apartment
apartment?.tenant = person

person = nil
apartment = nil
SAY

Person strongly references its apartment and Apartment strongly references its tenant. Both are also reachable from outside variables. Click: set the outside variables to nil. The two instances still retain one another, so neither is released: a leak.

SAY

Click: make Apartment’s reference to its tenant weak. Now nothing keeps Person alive once the outside reference goes, and the cycle no longer prevents deallocation.

CONNECT

Here is the fix in code.

Part 6 · Fix

Break the cycle with weak

Ownership.swift
class Person {
    var apartment: Apartment?

    deinit {
        print("Person deinitialized")
    }
}

class Apartment {
    weak var tenant: Person?

    deinit {
        print("Apartment deinitialized")
    }
}

The apartment no longer strongly owns its tenant.

When the external strong references are released, the cycle no longer prevents deallocation. Both deinit messages print.
SAY

One word changes: weak var tenant. The apartment no longer strongly owns its tenant, so once the outside references are released, both objects can be deinitialized and both messages print.

CONNECT

SAY

A closure is a block of code that can capture values from its surrounding context, including self.

Part 7 · Closure cycle

A closure that captures self

ProfileViewModel.swift
class ProfileViewModel {

    var onUpdate: (() -> Void)?

    func configure() {
        onUpdate = {
            print(self)
        }
    }

    deinit {
        print("ProfileViewModel destroyed")
    }
}
SAY

The ViewModel owns its onUpdate closure. The closure captures self strongly, and self is the ViewModel. Both keep each other alive.

SAY

Click: the external owner releases the ViewModel. The cycle remains, so deinit never runs.

CONNECT

The fix is a capture list.

Part 7 · Fix

[weak self]

ProfileViewModel.swift
class ProfileViewModel {

    var onUpdate: (() -> Void)?

    func configure() {
        onUpdate = { [weak self] in
            guard let self else { return }
            print(self)
        }
    }

    deinit {
        print("ProfileViewModel destroyed")
    }
}
1[weak self]the closure no longer retains the ViewModel
2guard let selfa temporary strong reference while the closure runs, if the object still exists
SAY

[weak self] prevents the closure from retaining the ViewModel through its capture. guard let self temporarily obtains a strong reference while the closure executes, if the object still exists; otherwise it returns.

Part 8 · Capture experiment · conceptual

Strong vs weak capture

[weak self] matters for escaping closures that are retained and create a cycle. A short-lived, non-escaping closure does not need it.
SAY

Strong capture: release the external owner and the ViewModel stays alive in an ownership cycle. Click: with weak capture, the same release lets the ViewModel be deallocated.

Part 9 · unowned

A card that cannot outlive its customer

CreditCard.swift
class Customer {
    let name: String
    var card: CreditCard?

    init(name: String) {
        self.name = name
    }
}

class CreditCard {
    let number: String
    unowned let customer: Customer

    init(number: String, customer: Customer) {
        self.number = number
        self.customer = customer
    }
}
Safe only if the card is never accessed after its customer has been deallocated.

Teach weak first. Introduce unowned only once students understand lifetime guarantees.

SAY

The customer strongly owns the card; the card holds an unowned reference back. This design is safe only if the card is never accessed after its customer has been deallocated.

SAY

Introduce weak first, and teach unowned only after students understand lifetime guarantees.

Part 10 · Two problems

Leak vs high usage

Memory leak

Memory stays allocated though no longer needed, and cannot be reclaimed through the intended ownership path.

High memory usage

The app uses a lot of memory. That may be legitimate, or a sign of excessive caching or allocation.

A photo app keeps recent images in a cache: not a leak. But a cache that grows without bounds can still cause memory problems, even when everything stays reachable.

SAY

A leak is memory that stays allocated though no longer needed and cannot be reclaimed through the intended ownership path. High memory usage may be legitimate, or may indicate excessive caching or allocation.

SAY

An app can use a lot of memory without leaking; and a small leak repeated thousands of times can eventually cause serious memory pressure. An image cache is fine until it grows without bounds.

Part 12 · Timer cycle

A repeating timer that never lets go

DashboardController.swift
class DashboardController {

    var timer: Timer?

    func startTimer() {
        timer = Timer.scheduledTimer(
            withTimeInterval: 1,
            repeats: true
        ) { _ in
            self.refreshDashboard()
        }
    }

    func refreshDashboard() {
        print("Refreshing...")
    }

    deinit {
        timer?.invalidate()
        print("Dashboard destroyed")
    }
}
deinit cleanup cannot help if the cycle stops deinit from ever running.
SAY

The timer infrastructure retains the timer, the timer retains its closure, and the closure retains self. The controller also holds a reference to the timer. This can prevent the controller from ever being released.

SAY

The invalidate call in deinit looks like cleanup, but it cannot solve the problem if the cycle prevents deinit from running in the first place.

CONNECT

So what is the safer design?

Part 12 · Fix

Weak capture and explicit cancellation

DashboardController.swift
func startTimer() {
    timer = Timer.scheduledTimer(
        withTimeInterval: 1,
        repeats: true
    ) { [weak self] _ in
        self?.refreshDashboard()
    }
}

func stopTimer() {
    timer?.invalidate()
    timer = nil
}
Weak captureaddresses the closure owning self
Explicit invalidationstops the timer when the feature no longer needs it
They solve related but distinct problems: ownership versus ongoing activity.
SAY

Weak capture addresses the closure’s ownership of self. Explicit invalidation, in stopTimer, addresses the timer’s continuing activity when the feature no longer needs it. Related, but distinct problems; you usually need both.
