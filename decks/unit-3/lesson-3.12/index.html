The text’s engineering insight from the first part of Section 4: the router should never deduct money; the review sheet should never own the account balance; the balance card should never process a payment. Part 4 · What the SwiftUI runtime does (section 5) · conceptual

We change state; SwiftUI updates the interface

SwiftUI’s exact reconciliation and rendering are not publicly specified.

No refreshBalanceCard()
  • balancePaise -= amountPaise
  • Home showed ₹23,499.50 on its own
  • Change the state
  • Views describe the UI for that state
  • SwiftUI coordinates the update
SAY

Connecting Unit 0 to everything since. Click through: an application event, a tap, text input, navigation or a data change; a state mutation, in @State, a Binding or an observable model; dependency invalidation, SwiftUI working out which descriptions may need updating; view evaluation of the relevant bodies; reconciliation and layout, identity, structure and geometry; rendering and presentation by the platform. This is conceptual: the exact implementation is not publicly specified.

SAY

Click: the key principle in our trace: the store subtracted the amount, one line, and Home showed ₹23,499.50. Nobody called a method like refreshBalanceCard. Click: we change the state; the view descriptions say how the interface looks for that state; SwiftUI coordinates the updates.

Part 5 · State ownership (section 6)

Where each value belongs

PropertyOwnerReason
balancePaiseNPayStoreShared application data
transactionsNPayStoreShared transaction collection
paymentDraftNPayStoreMust survive tab switches
selectedTabNPayRouterTop-level navigation
paymentsPathNPayRouterPayment navigation hierarchy
reviewDraft*PaymentsScreenTemporary modal presentation
focusedFieldPaymentsScreenLocal keyboard focus
showSuccessAnimation*PaymentSuccessScreenTemporary visual state
appearanceNPayPreferencesShared UI preference

* In our code: review and showContent.

Why not all in NPayStore?
  • Focus needn’t be global
  • A balance mustn’t be copied into four tabs
  • Narrowest owner that supports the value’s lifetime and sharing
SAY

The text’s ownership table. The balance, the transactions and the payment draft belong to NPayStore: shared data, and the draft must survive tab switches, Lesson 3.5. The selected tab and Payments path belong to NPayRouter. The review value and the focused field belong to the Payments screen: temporary presentation and local focus. The success animation flag belongs to the success screen. Appearance belongs to NPayPreferences. Two names differ in our code: the text’s reviewDraft is our review, and showSuccessAnimation is our showContent.

SAY

Click: why not put everything in NPayStore? A focus indicator does not need to be global; and a balance should not be duplicated independently in four tabs, which Lesson 3.1 showed going wrong with a second @State owner. Click: the rule: state is owned at the narrowest level that supports its intended lifetime and sharing. This is a foundational architectural skill.

What still needs improvement

Merged from the text’s two limitation tables; the Unit column is ours, from the curriculum.

SAY

The text lists the limitations twice, in Part 1 and Part 2; this is the merged list. NPayStore combines responsibilities and holds the payment rules: Unit 4 brings use cases and feature ViewModels. Screens reach the shared store directly and the UI coordinates some operations: MVVM and dependency injection. Transactions live in memory: repositories and persistence, Units 5 and 6. The payment is a local simulation with no real authentication: the backend API and security units. Error handling is simple: typed errors and loading states. Testing is manual: Unit 9. And it is one module: modularization comes in the final unit. The Unit column is our mapping to the curriculum.

SAY

Click: the text is clear that this is intentional. Unit 3 taught SwiftUI application composition; these are not reasons to rewrite everything immediately, they are the motivation for Unit 4, architecture and testability.
