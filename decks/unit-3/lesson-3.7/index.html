Part 2 · What exactly is a design system? (section 2)

Tokens define, components apply, screens assemble

A design system
  • Shared design decisions
  • Reusable UI components
Why layers
  • Tokens: the shared visual rules
  • Components apply them; screens assemble components
  • No screen invents its own look
SAY

A design system is a collection of shared design decisions and reusable UI components. For NPay, three layers: design tokens, the colours, spacing, typography and corner radii; reusable components, NPayButton, NPayCard, NPaySectionHeader; and the feature screens, Home, Payments, History, Profile.

SAY

Click: why separate them? The tokens define the shared visual rules; components apply those rules; screens assemble the components. That prevents every screen from independently inventing its own appearance.

Part 2 · Design tokens (section 3)

Enums as namespaces: no instance, just constants

DesignSystem/NPayTheme.swift
enum NPayTheme {
    enum Colors {
        static let primary = Color(red: 0.10, green: 0.34,
                                   blue: 0.65)
        static let success = Color.green
        static let cardBackground = Color.blue.opacity(0.06)
    }
    enum Spacing {
        static let small: CGFloat = 8
        static let medium: CGFloat = 16
        static let large: CGFloat = 24
    }
    enum Radius {
        static let small: CGFloat = 10
        static let card: CGFloat = 18
    }
}

NPayTheme.Colors.primary
NPayTheme.Spacing.medium
NPayTheme.Radius.card
What this Swift is
  • An enum with static properties
  • Nested enums group colours, spacing, radii
  • Never instantiated
Unit 1
  • Ordinary namespacing with enums and static members
  • No SwiftUI mechanism needed to define tokens
Why an enum
  • No cases: it cannot be instantiated by mistake
SAY

NPayTheme.swift: an enum with nested enums, Colors, Spacing and Radius, each with static properties: a primary colour, success and card-background colours; small, medium and large spacing; a small and a card radius. We never create an NPayTheme; we write NPayTheme.Colors.primary, NPayTheme.Spacing.medium, NPayTheme.Radius.card.

SAY

Click: connect to Unit 1: this is ordinary Swift namespace organisation with enums and static members. No special SwiftUI mechanism is involved in defining the tokens. Click: why an enum rather than a struct? An enum with no cases has no values, so nobody can create one by mistake: it can only be a namespace.

Part 3 · Our first reusable component (sections 5–6)

A value describing a branded button

DesignSystem/NPayButton.swift (v1)
struct NPayButton: View {
    let title: String
    let action: () -> Void

    var body: some View {
        Button(action: action) {
            Text(title)
                .font(.headline)
                .frame(maxWidth: .infinity)
                .padding(.vertical, 14)
        }
        .buttonStyle(.plain)
        .foregroundStyle(.white)
        .background(NPayTheme.Colors.primary,
                    in: RoundedRectangle(
                        cornerRadius: NPayTheme.Radius.small))
    }
}

NPayButton(title: "Send Money") {
    print("Send tapped")
}
Reusable
  • Styling stays inside
  • The caller supplies the action: 2.7’s closures

A view description, not necessarily a UIKit object.

SAY

NPayButton: a title and an action. Its body is a native Button whose label is the title, full width, with vertical padding; plain button style, white text, and the primary token as a rounded background with the small radius. The caller writes NPayButton(title:) with a trailing closure. The visual styling stays inside the component; the caller supplies the action, the closure-based architecture of Lesson 2.7.

SAY

Click: behind the scenes: the feature screen creates an NPayButton value; NPayButton is a struct conforming to View; inside, a native Button, the interactive control; then Text and modifiers for label, padding, colours and shape; and the SwiftUI runtime coordinates layout, rendering and interaction, evaluating body as needed.

SAY

Click: creating a reusable view does not necessarily create a separate UIKit view object. SwiftUI composes view descriptions and manages the platform presentation internally.

Part 3 · A more flexible NPayButton (section 17)

Six Unit 1 ideas in one component

NPayButton (v2, condensed)
struct NPayButton: View {
    let title: String
    let symbol: String?
    let action: () -> Void

    init(_ title: String,
         symbol: String? = nil,
         action: @escaping () -> Void) {
        self.title = title
        self.symbol = symbol
        self.action = action
    }

    var body: some View {
        Button(action: action) {
            HStack(spacing: 10) {
                if let symbol { Image(systemName: symbol) }
                Text(title)
            }
            .font(.headline)
            .frame(maxWidth: .infinity)
            .padding(.vertical, 14)
        }
        // .buttonStyle, .foregroundStyle, .background as v1
    }
}
Use

           symbol: "arrow.up.right") {
    print("Send tapped")
}

Version 2 adds an optional SF Symbol. A custom initializer takes an unlabelled title, an optional symbol defaulting to nil, and an escaping action. Part 3 · A finding: .disabled barely shows (integration)

The background is ours, so dimming it is our job

Disabled (empty form)

Enabled (valid form)

What we saw
  • .disabled(!isValid) on NPayButton

A fix (authored, not in our integration)
struct NPayButton: View {
    // title, symbol, action, init as before
    @Environment(\.isEnabled) private var isEnabled

    var body: some View {
        Button(action: action) { /* label as before */ }
            .buttonStyle(.plain)
            .foregroundStyle(.white)
            .background(NPayTheme.Colors.primary
                            .opacity(isEnabled ? 1 : 0.4),
                        in: RoundedRectangle(
                            cornerRadius: NPayTheme.Radius.small))
    }
}
SAY

Integrating the button into the Payments form showed something the text does not cover. Review Payment is disabled until the form is valid. On the left, disabled; in the middle, enabled. Look closely: only the text dims; the blue background stays at full strength, so a disabled payment button looks almost tappable. With .plain style, the system dims the content it styles; our background is our own drawing.

SAY

Click: a design-system fix, which we wrote and typechecked but did not put into the integration, to keep the text’s component as written: read isEnabled from the environment, which .disabled sets, and dim the background. Another reason a design system is more than looking identical: states matter.

  • Content: a generic type parameter

@ViewBuilder on the property
  • The memberwise init takes a builder closure
  • Callers write declarative view syntax

Two NPayCards: a VStack, an HStack

SAY

We want a card that can contain any SwiftUI content: a Text, or a VStack of several texts. One component, different view types: generics and @ViewBuilder. Part 4 · Why not AnyView everywhere? (section 16)

Erasure hides the structure

Generic vs type-erased

    let content: Content
    var body: some View { content }
}

// type-erased: one type for any content
struct ErasedCard: View {

}

ErasedCard(content: AnyView(Text("NPay")))
type(of:), simulator

AnyView(Text("NPay")): AnyView
NPayCard { Text }:   NPayCard<Text>

AnyView is for
  • Storing different view types behind one type
  • Prefer generics: unnecessary erasure obscures structure
SAY

SwiftUI provides AnyView, which erases the concrete view type. Compare a generic card, whose content type is part of the card’s type, with a type-erased one that stores AnyView. We renamed the erased one ErasedCard so both compile together.

SAY

Click: printed: an AnyView is just AnyView; what was inside is no longer in the type. The generic card keeps it: NPayCard of Text. Click: AnyView is useful when different view types must be stored behind one common type. Click: but unnecessary type erasure obscures structural information and adds complexity, so for NPay’s reusable components the generic approach is preferable.

The recap.

Lesson 3.7 · Recap

What to remember

Tokens → components → screens
one change in a token reaches everything that uses it

Generic, not erased
Content: View + @ViewBuilder; real types like TupleView

Adapt, don’t just match
semantic fonts and colours; disabled states; no business logic

SAY

Three things to remember. A design system is layers: tokens are plain Swift constants, components apply them, screens assemble components, so one token change reaches everything that uses it, and nothing that hardcodes around it. Components that take arbitrary content are generic over Content: View with @ViewBuilder, keeping the full structure in the type instead of AnyView. And a good system adapts: semantic fonts scale with Dynamic Type, semantic colours follow dark mode, components show their states, and none of them contains business logic.
