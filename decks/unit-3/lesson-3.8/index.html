Part 2 · SwiftUI’s layout system (section 2)

A conversation between parent and child

UIKit
  • Frames and Auto Layout constraints
SwiftUI
  • Proposal-based: children decide their own size
  • Text("NPay") takes what its content needs
SAY

In UIKit we think in frames and constraints. SwiftUI uses a proposal-based layout system, a conversation. Click: the parent proposes a size: here is how much space is available. Click: the child chooses its size: here is how much my content needs. Click: the parent places the child: where it should appear. This is a conceptual description of SwiftUI’s layout protocol, and the next slide shows it really happening.

SAY

Click: the important insight: a child does not always take all the space it is offered. Text("NPay") picks a size from its content and the proposal.

A VStack of 320 points asks; each child answers

A logging Layout (simplified: ours formats the sizes)
struct ProposalLog: Layout {   // passes through, prints
    let name: String
    func sizeThatFits(proposal: ProposedViewSize,
                      subviews: Subviews, cache: inout ()) -> CGSize {
        let size = subviews[0].sizeThatFits(proposal)
        print("\(name): proposed \(proposal) → chose \(size)")
        return size
    }
    func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize,
                       subviews: Subviews, cache: inout ()) {
        subviews[0].place(at: bounds.origin, proposal: proposal)
    }
}

Part 3 · How .frame() works; modifier order (section 3)

Background first, or frame first?

Two orders (red border: the 200×80 frame)
// Example A
Text("NPay")
    .background(.blue)
    .frame(width: 200, height: 80)

// Example B
Text("NPay")
    .frame(width: 200, height: 80)
    .background(.blue)
.frame() is a view
  • A new view description that takes part in layout
  • Not a mutable UIView.frame
  • Layout, hit testing, animation, rendering

A: background wraps the text · B: background fills the frame

SAY

Text("NPay").frame(width: 200, height: 80) is not assigning a UIView’s frame property. It creates a modified view description, a frame view around the text, that takes part in the negotiation we just watched.

SAY

Click: so order matters. Example A puts the background on the text, then frames it: the background wraps the text’s own size. Example B frames first, then adds the background: it covers the whole 200 by 80 region. Click: our screenshot: in A the blue hugs "NPay" inside the red frame; in B it fills the frame.

SAY

Click: the text’s question: does order matter only for colours? No. It affects layout, hit testing, animation and rendering: a tap area or an animation attaches to whatever layer you put it on.

Part 5 · Build adaptive quick actions with GeometryReader (section 6)

Measure the width; switch below 350

NPayQuickActions (section 6, condensed)
struct NPayQuickActions: View {
    let onSend: () -> Void
    let onRequest: () -> Void
    let onHistory: () -> Void

    var body: some View {
        GeometryReader { geometry in
            let isCompact = geometry.size.width < 350
            Group {
                if isCompact {
                    VStack(spacing: 12) { actions }
                } else {
                    HStack(spacing: 12) { actions }
                }
            }
        }
        .frame(height: 180)
    }

    @ViewBuilder
    private var actions: some View {
        QuickAction(symbol: "arrow.up.right", title: "Send",
                    action: onSend)
        // Request and History the same way
    }
}
What it introduces
  • GeometryReader measures the width
  • A conditional picks HStack or VStack
  • @ViewBuilder shares the actions; closures supply behaviour
  • .frame(height: 180): a teaching shortcut
  • May waste space, or clip with larger text
SAY

The text’s first version: a GeometryReader measures the available width; below 350 points the three actions stack vertically, otherwise they sit in a row. @ViewBuilder lets one property supply the three QuickAction views to either stack, and the parent supplies behaviour through closures. QuickAction is Lesson 2.7’s component, back in our code.

SAY

Click: the text itself flags the limitation: the fixed 180-point height is a teaching shortcut; it may waste space in the row and clip content with larger text. The next slide shows both happening.

            HStack(spacing: 12) { actionViews }

        }
    }

    @ViewBuilder
    private var actionViews: some View {
        // the same three QuickActions
    }
}
Why better
  • Decides by whether the content fits
  • No fixed height; no device breakpoint

SAY

SwiftUI’s ViewThatFits takes candidate views in order and uses the first one that fits the available space along the given axes, horizontal here. The text’s improved NPayQuickActions offers an HStack first, then a VStack, with the same three actions. No GeometryReader, no fixed height.

SAY

Click: why better: the decision is whether the content fits, not an assumption about device width, which matters most with Dynamic Type. Both of the breakpoint’s mistakes are gone.

It is not magic, though.

Part 5 · ViewThatFits: an important nuance (sections 7, 17)

It judges ideal sizes, not truncation

How it decides
  • Each candidate’s ideal size along the axis
  • Not a comparison with a hardcoded screen width
  • Flexible content can “fit” while compressing or truncating
  • QuickAction uses maxWidth: .infinity: its ideal width is its label
So
  • It worked here because the labels’ ideal widths grew with the text
  • Still test: large text, other languages
Other tools (section 12)
  • AnyLayout, grids, custom Layout, size classes
SAY

The text’s nuance. ViewThatFits evaluates candidates by their ideal sizing behaviour along the axes you give it. It is not a universal overflow detector: some flexible content reports that it fits while it compresses or truncates.

SAY

Click: our QuickAction is flexible, it uses frame maxWidth infinity, but its ideal width still comes from its icon and label, which grow with Dynamic Type, so the row stopped fitting at the largest size and ViewThatFits chose the column. Click: with different content that might not happen, so test the actual UI: large text sizes and localised labels.

SAY

Click: the text’s trainer question: is ViewThatFits always the best adaptive solution? No: for complex responsive designs, custom Layout implementations, AnyLayout, grid containers and size-class-aware structures may be more appropriate.

Part 6 · AnyLayout: switch the algorithm, keep the structure (section 8)

One child list, two layouts

AdaptiveActions.swift
struct AdaptiveActions: View {
    let compact: Bool

    var body: some View {
        let layout = compact
            ? AnyLayout(VStackLayout(spacing: 12))
            : AnyLayout(HStackLayout(spacing: 12))

        layout {
            Text("Send")
            Text("Request")
            Text("History")
        }
    }
}
AnyLayout
  • Type-erases a Layout: HStackLayout, VStackLayout…
  • Callable like a container: layout { … }
Why it matters
  • Not two branches with two structures
  • The same children; only the algorithm changes
SAY

AnyLayout lets us choose between HStackLayout and VStackLayout at run time: both are Layout types, and AnyLayout erases which one, so a single variable can hold either. You call it like a container with the children in a closure.

SAY

Click: why it is interesting: instead of two separate branches that create two different layout structures, we switch the layout container while keeping the same child descriptions. That can preserve view identity across layout changes. Let’s measure that.

Part 6 · AnyLayout and state identity (sections 9, 18)

Count to 3, switch the layout

Two ways to switch (condensed)
struct CounterView: View {
    @State private var count = 0
    var body: some View {
        Button("Count: \(count)") { count += 1 }
    }
}

// AnyLayout (section 18)
let layout = vertical ? AnyLayout(VStackLayout())
                      : AnyLayout(HStackLayout())
layout { CounterView() }

// Branches (section 9)
if vertical {
    VStack { CounterView() }
} else {
    HStack { CounterView() }
}
Simulator: tap Count three times, then Switch Layout

AnyLayout: Count: 3 → Count: 3
if / else: Count: 3 → Count: 0

  • Branches: different structural positions, new identity
  • AnyLayout: same position, same identity, state kept
Adaptive design
  • Consider identity, not only the arrangement
SAY

The text’s experiment. CounterView keeps a count in @State. In LayoutIdentityExperiment, from Section 18, a Switch Layout button toggles between a VStackLayout and an HStackLayout through AnyLayout. Section 9’s alternative uses if and else with a VStack in one branch and an HStack in the other.

SAY

Click: we tapped Count three times and switched. With AnyLayout: still Count: 3. With the branches: Count: 0.

SAY

Click: Lesson 3.5 explains it: the two branches give CounterView different structural positions, so SwiftUI treats the switch as removing one counter and inserting another, and its state resets. AnyLayout keeps the child in the same position and only changes the algorithm, so the identity and the state survive. Click: adaptive layout design must consider identity, not only visual arrangement: a user’s half-filled form should not reset because they rotated the phone.

The recap.

Lesson 3.8 · Recap

What to remember

Propose, choose, place
children size themselves; maxWidth means the proposed width

Fit, don’t guess
ViewThatFits over a 350-pt breakpoint; test anyway

Adapt without resetting
AnyLayout keeps identity; respect safe areas and text size

SAY

Three things to remember. SwiftUI layout is a negotiation: the parent proposes, the child chooses, the parent places; that is why Text takes 39 points and maxWidth infinity means the proposed width. Adapt to content rather than guessed breakpoints: GeometryReader is for real geometry needs and misbehaves in a ScrollView, while ViewThatFits picks what fits, though you still test large text and other languages. And adapt without breaking things: AnyLayout switches arrangement while keeping identity and state, backgrounds may extend into the safe area but controls should not, and text must stay whole at every size.
