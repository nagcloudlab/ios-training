Part 2 · Where does the value come from? (section 3)

From the hierarchy, not the initializer

Propagation
  • A parent or ancestor can override a value
  • Descendants read the effective value
  • The value depends on where a view sits
  • Two instances of one view can read different values
SAY

The most important question. Unlike an initializer parameter, an environment value is supplied through the view hierarchy. The root supplies configuration; containers like the TabView and NavigationStack pass it on; each screen reads what it needs, such as colorScheme. A parent or ancestor can override a value for its descendants.

SAY

Click: the nuance: environment values are not simply global variables. Their value depends on where a view appears in the hierarchy, so two instances of the same view can receive different values if they have different ancestors. The next part proves it.

Part 5 · Build NPay appearance preferences (sections 6, 17)

System means “don’t force it”: nil

NPayAppearance
enum NPayAppearance: String, CaseIterable, Identifiable {
    case system
    case light
    case dark

    var id: String { rawValue }

    var title: String { rawValue.capitalized }

    var colorScheme: ColorScheme? {
        switch self {
        case .system: return nil
        case .light:  return .light
        case .dark:   return .dark
        }
    }
}
Swift features
  • String raw values; CaseIterable for the picker
  • Identifiable via id; title from the raw value
Why ColorScheme?
  • .system → nil
  • nil = follow the surrounding appearance
SAY

A model for the preference: NPayAppearance, an enum with System, Light and Dark. String raw values give a title through capitalized; CaseIterable lets a picker list all cases; Identifiable lets ForEach use them, with the raw value as the id.

SAY

Click: why is colorScheme optional? Because System means we do not want to force a specific scheme. Returning nil lets the app follow the surrounding appearance. Sections 6 and 17 show the same enum; 17 uses explicit returns.

Part 6 · Create our own environment value (section 11)

A key and an accessor

NPayDemoModeKey
private struct NPayDemoModeKey: EnvironmentKey {
    static let defaultValue = true
}

extension EnvironmentValues {
    var npayDemoMode: Bool {
        get { self[NPayDemoModeKey.self] }
        set { self[NPayDemoModeKey.self] = newValue }
    }
}

// a parent supplies
.environment(\.npayDemoMode, true)

// a child reads
@Environment(\.npayDemoMode) private var demoMode
The parts
  • EnvironmentKey: the type and the default
  • EnvironmentValues extension: typed key-path access
Two readers (simulator)

no ancestor sets it: true (the default)
ancestor sets false: false

  • extension EnvironmentValues { @Entry var npayDemoMode = true }
  • Typechecks for our iOS 17 target
SAY

Suppose NPay wants a configuration value controlling whether demo-mode indicators appear. A custom environment value needs two things: an EnvironmentKey, which defines the value’s type through its default, true here; and an extension on EnvironmentValues with a computed property that reads and writes through the key. Then any parent can supply .environment(\.npayDemoMode, …) and any child can read it with @Environment.

SAY

Click: our run: a reader with no ancestor setting the value gets the default, true; a reader under .environment(\.npayDemoMode, false) gets false. Unit 1 at work: protocols, static properties, extensions, generics and key paths supporting a framework-level configuration system.

SAY

Click: a note from the SDK: SwiftUI also has the @Entry macro, which writes the key and accessor for you in one line. We typechecked it for NPay’s iOS 17 target. The long form shows what @Entry generates.

Lesson 3.9 · Recap

What to remember

Contextual, not global
the nearest override wins; values depend on position

Own it, apply it
preferences in an observable model; preferredColorScheme at the root

Inject deliberately
required environment models crash if missing; data stays explicit

SAY

Three things to remember. The environment carries contextual values down the hierarchy: what a view reads depends on where it sits, and the nearest override wins; overriding colorScheme changes how a subtree resolves colours, not the surface or the sheets it presents. User preferences are owned in a model, NPayPreferences, injected with .environment and applied with preferredColorScheme; @Environment retrieves it and @Bindable binds it. And inject deliberately: a missing required model is a run-time crash, nothing is persisted automatically, and domain data stays in explicit parameters.
