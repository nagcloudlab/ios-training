Part 4 · Implicit versus explicit animations (section 6)

On the change, or on the value

Explicit: withAnimation

    expanded.toggle()
}

The animation is attached to the state update.

Value-driven: .animation(_:value:)

    .frame(width: expanded ? 180 : 80,
           height: expanded ? 180 : 80)
    .animation(.easeInOut(duration: 0.3),
               value: expanded)

Animates when expanded changes.

  • .animation(_:value:) affects animatable changes in the modified subtree
  • Not just one property, unless you scope it
SAY

Explicit animation: withAnimation around the state change. The animation is associated with that update, wherever the change shows up.

SAY

Click: value-driven animation: the .animation modifier with a value. Whenever expanded changes, animatable changes in this part of the tree animate with that curve, no matter who changed the value.

SAY

Click: the important distinction: .animation(_:value:) affects animatable changes in the modified subtree when the value changes. It is not limited to one property unless you scope the modifier appropriately, by placing it close to what should animate.

Part 7 · How SwiftUI knows what can animate (sections 16–17)

v(t) = v₀ + (v₁ − v₀)t

Animatable
  • Values SwiftUI can interpolate: size, offset, opacity, shape parameters
  • Exposed through animatableData

v(0.5) = 80 + (180 − 80) × 0.5 = 130

Not everything animates
  • Some properties change discretely
  • Others need an Animatable implementation
linear(0.5), measured diameters

…
205 ms 116.7
255 ms 126.7
305 ms 136.7
…
+3.3 per frame: 100 points over 30 frames

Times from the withAnimation call; the first frame lands about 16 ms later, so 130 falls between the 255 and 305 ms frames.

SAY

SwiftUI uses the Animatable protocol and related mechanisms: many modifiers expose animatable values such as size, offset, opacity and shape parameters. Animatable data is data that can be interpolated between two values. The linear case is this formula: v of t equals the start, plus the difference times t, with t the normalised progress from 0 to 1. At t = 0.5, 80 plus 100 times a half: 130 points.

SAY

Click: not every property animates: some change discretely, others need an Animatable implementation or a suitable modifier.

SAY

Click: our linear measurement matches the formula: a steady 3.3 points per frame, 116.7, 126.7, 136.7. Our clock starts at the withAnimation call and the first frame comes about 16 ms later, so the 130-point midpoint falls between our 255 and 305 ms samples. The text’s note applies: the screen itself renders in physical pixels.

Part 7 · Build our own Animatable modifier (section 18)

SwiftUI feeds the in-between values

AnimatedNumber (text)
struct AnimatedNumber: AnimatableModifier {
    var value: Double

    var animatableData: Double {
        get { value }
        set { value = newValue }
    }

    func body(content: Content) -> some View {
        Text(value,
             format: .number.precision(.fractionLength(0)))
            .font(.largeTitle.bold())
    }
}

SAY

Connect animations to Swift protocols: a custom modifier that animates a number. animatableData exposes the value SwiftUI can interpolate; as the animation progresses, SwiftUI supplies intermediate values through it, and body draws the current one.

SAY

Click: we ran it with one extra line that records each value body receives: 30 values in half a second as the balance went from ₹25,000 to ₹23,500, following the ease-in-out curve: 24997, 24947, 24832, and so on to 23500. The state changed once; the modifier saw 30 values.

Click: as the text says, for NPay’s balance numericText is simpler; the SDK also marks AnimatableModifier as superseded: conform to Animatable directly.

Part 8 · Performance: animations are not free (sections 13, 21)

Tendencies, not guarantees

AnimationTypical work
Opacityoften compositing
Scaletransform / compositing in many cases
Offsetposition- or transform-related presentation
Frame changescan involve layout
Complex list changesreconciliation and layout
Custom drawingrepeated drawing work
Instruments (Product → Profile)
  • Animation hitches, Core Animation, Time Profiler
  • Look for hitches, layout, CPU, main-thread blocking, repeated bodies
  • Measure on a device like your users’
  • We didn’t profile here: the simulator isn’t that device
SAY

Animations can involve layout, rendering, compositing, or a mix. Opacity is often compositing-friendly. Scale is a transform, efficient in many cases. Offset is position- or transform-related. Frame changes, like our circle, can mean layout on every frame. Complex list changes need reconciliation and layout; custom drawing repeats drawing work. These are tendencies, not guarantees: the cost depends on the hierarchy and the rendering environment.

SAY

Click: measure with Instruments via Product, Profile: depending on the Xcode version, animation hitch analysis, Core Animation and the Time Profiler. Look for frame hitches, excessive layout, CPU use during the animation, main-thread blocking, repeated expensive view evaluation.

SAY

Click: the principle: do not optimise based on assumptions; measure on a device representative of your users. We deliberately did not profile on the simulator, which runs on a Mac and says little about a phone’s rendering cost. Unit 8 covers performance.

What to remember

State once, frames many
withAnimation attaches a curve; SwiftUI interpolates

SAY

Three things to remember. And motion is presentation: respect Reduce Motion, measure before optimising, and never make the money wait for an animation.
