Why does success carry only an ID?

Part 2 · Why carry an ID? (section 3)

Identify the destination; don’t carry it

A route says
  • Which destination
  • The data needed to resolve it
A stable ID, not the Transaction
  • No coupling to a whole mutable object
  • The owner keeps the data; the route points at it
Route equality (Mac run)

.success(transactionID: id) == .success(transactionID: id) → true
.success(transactionID: id) == .success(transactionID: UUID()) → false

Hashable routes compare by case and associated value.

SAY

Why does the success route carry a transaction ID instead of the whole Transaction? Because navigation should usually identify the destination and the data needed to resolve it, nothing more.

SAY

Click: passing a stable ID avoids coupling the route to an entire transaction object, which may change. The state owner, ContentView, keeps the data; the route just points at it.

SAY

Click: our Mac run: two success routes with the same ID are equal; with different IDs they are not. A synthesized Hashable route compares the case and its associated value: that is how SwiftUI can tell routes apart in a path.

Part 4 · Register destinations with navigationDestination (section 6)

One switch, every screen

The routing structure
.navigationDestination(for: NPayRoute.self) { route in
    switch route {
    case .payment:
        PaymentScreen()

    case .history:
        HistoryScreen()

    case .success(let transactionID):
        PaymentSuccessScreen(
            transactionID: transactionID
        )
    }
}

Structure only: the real initializers still take 3.1’s dependencies.

What happens
  • SwiftUI associates the route type with a destination builder
  • When a route becomes active, it builds the view
  • The route: a typed description of intent
SDK (simplified)

func navigationDestination<D, C>(for data: D.Type,
  @ViewBuilder destination: @escaping (D) -> C) -> some View
  where D : Hashable, C : View

SAY

SwiftUI needs to know which view corresponds to each route, so we register a mapping: navigationDestination for NPayRoute.self, with a closure that receives a route and switches over it. The switch is exhaustive: add a route case and the compiler makes you handle it. This shows the routing structure; the real screens still need the balance, transactions and closures from 3.1, which we add in Part 6.

SAY

Click: conceptually, SwiftUI associates the route type with a destination builder; when a route becomes active, it builds the matching view. The route is a typed description of navigation intent.

SAY

Click: the SDK declaration: generic over the data type D, which must be Hashable, and the destination view C, built by an escaping closure. Escaping because SwiftUI calls it later, whenever a route needs a view.

Two ways to declare the path

Typed arrayNavigationPath

SAY

So far: an array of NPayRoute. SwiftUI also provides NavigationPath, a type-erased path that can hold Hashable values of different types: for example, routes from several features, or plain identifiers.

SAY

SAY

Where does the transaction ID come from?

Part 6 · Connect payment success to navigation (section 10)

From Bool to UUID?

ContentView.sendDemoPayment
private func sendDemoPayment(
    to recipient: String,
    amountPaise: Int
) -> UUID? {
    let trimmed = recipient.trimmingCharacters(
        in: .whitespacesAndNewlines)
    guard !trimmed.isEmpty,
          amountPaise > 0,
          amountPaise <= balancePaise else {
        return nil
    }
    let transactionID = UUID()
    balancePaise -= amountPaise
    transactions.insert(
        Transaction(id: transactionID,
                    title: "Sent to \(trimmed)",
                    amountPaise: -amountPaise, date: .now),
        at: 0)
    return transactionID
}
The new contract
  • nil: rejected
  • A UUID: recorded, and which transaction
Navigation responds to the result
if let id = sendDemoPayment(
    to: recipient, amountPaise: amountPaise) {
    path.append(.success(transactionID: id))
}
  • Payment returns a meaningful result
  • Navigation responds to it
  • Payment logic knows no screens
SAY

In 3.1 sendDemoPayment returned a Bool. Now we need the transaction ID, so the contract improves: it returns an optional UUID. nil means rejected. On success it creates the ID first, uses it for the inserted transaction, and returns it.

SAY

Click: the navigation flow uses it: if let id = sendDemoPayment, append the success route with that ID.

SAY

Click: why this is better. Payment processing returns a meaningful result. Navigation responds to that result. And the payment logic does not need to know about SwiftUI screens; it could move into a service in Unit 4 unchanged.

A question from the lesson discussion: don’t we have a routing module, like Angular Router or React Router? Angular ships its router; React uses an external library; Flutter has Navigator and Router. In SwiftUI, navigation is part of the framework: NavigationStack and navigationDestination. In UIKit, UINavigationController.

SAY

Click: so there is no separate router package and no built-in application-level Router class. SwiftUI provides the navigation primitives, and we can build our own router on top to centralise navigation.

Part 8 · A router of our own (Q&A 2–3)

The path, moved into an object

NPayRouter.swift
@MainActor
@Observable
final class NPayRouter {
    var path: [NPayRoute] = []

    func push(_ route: NPayRoute) {
        path.append(route)
    }

    func pop() {
        guard !path.isEmpty else { return }
        path.removeLast()
    }

    func popToRoot() {
        path.removeAll()
    }
}

Observation framework: iOS 17+.

ContentView
@State private var router = NPayRouter()

var body: some View {
    @Bindable var router = router

    NavigationStack(path: $router.path) {
        VStack(spacing: 20) {
            Button("Send Money") { router.push(.payment) }
            Button("History") { router.push(.history) }
        }
        .navigationDestination(for: NPayRoute.self) { route in
            switch route {
            case .payment: Text("Payment Screen")
            case .history: Text("History Screen")
            case .success(let id):
                Text("Payment Success: \(id.uuidString)")
            }
        }
    }
}

Lesson 3.2 · Recap

What to remember

Routes are values
a Hashable enum names every destination

The path is the stack
append, removeLast, removeAll; the stack writes back

Results drive navigation
payment returns an ID; the parent appends .success

SAY

Three things to remember. A typed route is a Hashable enum that names each destination, carrying only the data needed to resolve it, like a transaction ID. The path array is the stack above the root: append pushes, removeLast pops, removeAll goes home, and the stack updates the array when the user goes back; navigationDestination maps each route to a view. And application logic drives navigation: the payment returns an ID, the parent appends the success route, and the payment code never knows about screens.
