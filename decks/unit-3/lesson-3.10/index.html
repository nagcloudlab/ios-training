How does a key become a translation?

Part 1 · How localization is resolved (section 16)

A literal is a key; a String is just text

String versus LocalizedStringKey
Text("payment.send")                    // literal: a LocalizedStringKey

let title: String = "payment.send"
Text(title)                             // a String: shown as is

Text(LocalizedStringKey(title))         // explicitly a key
Lineenta
literalSend Moneyபணம் அனுப்பு
Text(title)payment.sendpayment.send
explicit keySend Moneyபணம் அனுப்பு

Accessibility labels read from the simulator.

SAY

The resolution pipeline: Text("payment.send") is interpreted as a LocalizedStringKey; the key identifies a translatable resource; the locale and the app’s language decide which localization applies; the catalog supplies the value, with the development-language value as fallback; and the resolved string is rendered.

SAY

The important distinction. A string literal passed straight to Text uses SwiftUI’s LocalizedStringKey initializer. A String variable uses the verbatim initializer: it is shown as is. To localize a key held in a variable, wrap it: Text(LocalizedStringKey(title)).

SAY

Click: our run: the literal and the explicit key resolved, Send Money and பணம் அனுப்பு; the String variable showed "payment.send" in every language. That raw key would also be what VoiceOver reads. It compiles without a warning, so it is easy to ship.

SAY

A financial app must keep three things apart: the monetary value, the currency, and the formatting locale. The text’s example formats ₹1,500.50 as INR in the en_IN and en_US locales. Click: our run printed ₹1,500.50 twice: at this amount the two look identical.

SAY

Click: so we added a larger amount and more locales. At twelve million, en_IN groups in lakhs and crores, ₹1,23,45,678.50, while en_US groups in thousands, ₹12,345,678.50, as Lesson 2.12 showed. German uses a dot for grouping, a comma for decimals and puts the symbol after; French uses a narrow space; Arabic in Saudi Arabia uses Arabic-Indic digits. Every one is the same INR value.

SAY

Click: the text’s insight: changing the user’s language must not change the currency or the monetary value. Localization is presentation; calculations follow the domain model, integer paise.

SAY

The text says to avoid Text("₹\(amount)") for production money, and to prefer Text with a currency format. SAY

Why leading and trailing.

Part 3 · Leading and trailing; test RTL (sections 19–20)

Semantic alignment adapts; left and right don’t

Semantic alignment and an RTL preview
.frame(maxWidth: .infinity, alignment: .leading)   // adapts

#Preview("RTL") {
    ContentView()
        .environment(\.layoutDirection, .rightToLeft)
}
Leading / trailing
  • Start and end of the reading direction
  • Prefer them to hardcoded left/right
RTL preview
  • Finds layout assumptions fast
  • Test the app in a supported RTL language
SAY

.frame(maxWidth: .infinity, alignment: .leading) uses semantic alignment: leading means the start of the reading direction, which is the right edge in Arabic. Avoid assuming leading means left; prefer leading and trailing over hardcoded left and right where appropriate. Every NPay alignment so far was semantic, which is why the mirror on the last slide just worked.

SAY

Click: the text’s RTL preview: the content with the layoutDirection environment set to rightToLeft. Useful for finding layout assumptions. Click: but not a substitute for running the actual app in a supported RTL language, with real translations, fonts and symbol behaviour.

Part 5 · A reusable accessible NPay action (section 22)

Translated title; identifier never spoken

NPayActionButton
struct NPayActionButton: View {
    let title: LocalizedStringKey
    let symbol: String
    let accessibilityID: String
    let action: () -> Void

    var body: some View {
        Button(action: action) {
            Label(title, systemImage: symbol)
                .font(.headline)
                .frame(maxWidth: .infinity)
                .padding()
        }
        .buttonStyle(.borderedProminent)
        .accessibilityIdentifier(accessibilityID)
    }
}

NPayActionButton(title: "payment.send",
                 symbol: "arrow.up.right",
                 accessibilityID: "npay.sendPayment") {
    print("Send Money tapped")
}
Simulator, Tamil

"பணம் அனுப்பு" [button] id npay.sendPayment

LocalizedStringKey
  • “payment.send” is looked up, not shown
  • A String parameter would show the key (Part 1)
accessibilityIdentifier
  • Stable, for UI automation
  • Not spoken by VoiceOver
SAY

The text adds an accessible action to the design system: NPayActionButton takes its title as a LocalizedStringKey, a symbol, an accessibility identifier and an action, and renders a bordered-prominent Button with a Label.

SAY

Click: run in Tamil, the element is "பணம் அனுப்பு", a button, with the identifier npay.sendPayment. Why LocalizedStringKey? So the literal "payment.send" at the call site is looked up; had the parameter been a String, we would see the key, as Part 1 showed.

SAY

Click: why accessibilityIdentifier? It gives UI automation a stable identifier that does not change with the language. It is not a spoken label: VoiceOver reads the localized title; tests find the identifier. Two audiences, two properties.

literals and LocalizedStringKey are looked up

Locale formats, never changes, money
