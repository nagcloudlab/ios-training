Part 2 · Sheet versus NavigationStack (section 4)

Deeper, or temporary?

NavigationStackSheet
Pushes a navigation destinationPresents modal content
Hierarchical navigationFocused temporary tasks
Back navigationDismissal
Managed by the navigation pathManaged by presentation state
History → Transaction DetailPayment → Review
  • Moving deeper: a navigation destination
  • A temporary, focused task: a sheet
SAY

Two ways to show another screen. A NavigationStack pushes a destination; a sheet presents modal content. Navigation is for hierarchies, sheets for focused temporary tasks. You leave a pushed screen with Back, a sheet by dismissal. Navigation is managed by the path, a sheet by presentation state. History to Transaction Detail is navigation; Payment to Review is a sheet.

SAY

Click: so should every new screen be a sheet? No. Use a navigation destination when the user is moving deeper into a hierarchy; use a sheet when they are doing a temporary, focused interaction and will come back to where they were.

Part 5 · Connect the sheet to PaymentsScreen (section 12)

First version: dismiss and navigate together

PaymentsScreen (section 12)
// PaymentsScreen
@State private var reviewDraft: PaymentDraft?

// Review Payment, when the form is valid
reviewDraft = PaymentDraft(recipient: recipient,
                           amountPaise: amountPaise)

.sheet(item: $reviewDraft) { draft in
    PaymentReviewSheet(draft: draft) {
        if let transactionID = store.recordDemoPayment(
            recipient: draft.recipient,
            amountPaise: draft.amountPaise) {
            reviewDraft = nil
            router.showPaymentSuccess(transactionID)
        }
    }
}
The flow
  • Valid form → reviewDraft set → sheet
  • Confirm → store records → ID
  • reviewDraft = nil and push success
  • Dismissing a sheet and pushing in the same update
  • Not guaranteed to transition as you want
SAY

PaymentsScreen gets the reviewDraft state. When the form is valid and the user taps Review Payment, it creates a draft from the recipient and the parsed amount. The sheet modifier passes that draft to PaymentReviewSheet, with a trailing closure for onConfirm: record the payment in the store; with the returned ID, set reviewDraft to nil to dismiss, and ask the router to show success.

SAY

Click: the nuance the text raises. That closure dismisses a sheet and pushes a navigation destination in the same synchronous update. We should not assume that always produces the transition we want. The fix uses the sheet’s onDismiss callback, which is Part 6, where we also measure what this version does.

Part 6 · Better: navigate in onDismiss (section 15)

Remember the ID; push when the sheet is gone

PaymentsScreen (section 15)
@State private var reviewDraft: PaymentDraft?
@State private var pendingSuccessID: UUID?

.sheet(item: $reviewDraft, onDismiss: {
    guard let id = pendingSuccessID else { return }
    pendingSuccessID = nil
    router.showPaymentSuccess(id)
}) { draft in
    PaymentReviewSheet(draft: draft) {
        if let id = store.recordDemoPayment(
            recipient: draft.recipient,
            amountPaise: draft.amountPaise) {
            pendingSuccessID = id
            reviewDraft = nil
        }
    }
}
Section 12: dismiss + push together

t=  9 ms sheet shown, paymentsPath 1
t=567 ms sheet gone, paymentsPath 1

Section 15: onDismiss

t=  8 ms sheet shown, paymentsPath 0
t=588 ms sheet gone, paymentsPath 1

  • Same update: the push happened behind the sheet
  • onDismiss: the path changed only once the sheet was gone
  • Both reached Success here; only one is ordered by design
SAY

The better approach: a pending transaction ID. Confirm records the payment, stores the ID in pendingSuccessID, and sets reviewDraft to nil. The navigation happens in the sheet’s onDismiss callback: if there is a pending ID, clear it and ask the router to show success. We no longer request navigation in the same update as the dismissal.

SAY

We measured both, polling every 10 milliseconds after Confirm. Click: the Section 12 version: at 9 ms the sheet is still on screen and the payments path already holds the success route: the push happened behind the sheet. At 567 ms the sheet is gone. Click: the onDismiss version: at 8 ms the sheet is up and the path is still empty; when the sheet is gone, the path holds the success route.

SAY

Click: honestly read: on iOS 26.5 both versions ended on the success screen. The difference is that onDismiss orders the two transitions by design, instead of depending on how this release happens to handle a push behind a sheet.

Part 7 · Why confirmation must be idempotent (section 16)

Two taps, two payments

Confirm activated twice, back to back (simulator)

UI protection (section 16)
@State private var isProcessing = false

Button("Confirm Demo Payment") {
    guard !isProcessing else { return }
    isProcessing = true
    onConfirm()
}
.disabled(isProcessing)
IdeaMeans
UI protectionstop repeated taps while processing
Business idempotencyone logical request applied once
  • A disabled button protects this view instance
  • It is not durable idempotency
  • Server-enforced: a stable request ID, authoritative handling
SAY

What if the user taps Confirm twice? We tested it: two activations back to back, before SwiftUI could dismiss the sheet. Without a guard, a confirm button that records the payment ran twice: two transactions, and the balance dropped by ₹3,001, to ₹21,999.00. With the guard, one transaction, ₹23,499.50.

SAY

Click: the guard from the text: an isProcessing state; the action returns early if it is set, sets it, then confirms; and the button is disabled while processing. Our complete code uses it.

SAY

Click: two different ideas. UI protection prevents repeated taps while processing. Business idempotency ensures the same logical payment request cannot be applied more than once, anywhere. Click: a disabled button helps within this view instance, but it is not durable idempotency: a new sheet, a retry after a crash, or a second device are not covered. Click: a real payment API enforces idempotency on the server, with a stable request identifier and authoritative transaction handling. Our demo only models the idea locally.

Part 8 · How presentation relates to the view hierarchy (section 19)

A modifier describes a conditional presentation

The modifier
  • Declared on a view: .sheet(item: $reviewDraft)
  • Non-nil → SwiftUI presents; nil → it dismisses
A new UIWindow per sheet?
  • No such guarantee in the public API
  • Implementation is private and may change
SAY

A sheet is declared as a modifier on a view. The modifier describes a conditional presentation relationship: when the bound item becomes non-nil, SwiftUI coordinates presentation; when it becomes nil, SwiftUI coordinates dismissal. In NPay, PaymentsScreen owns its input and the reviewDraft; the review sheet is a temporary presentation of it.

Lesson 3.4 · Recap

What to remember

Presentation is state
a Bool or an optional item; dismissal writes it back

Dismiss, then navigate
pending ID + onDismiss; never a fixed delay

Confirm once, validate again
guard the button; the store re-checks; servers enforce

SAY

Three things to remember. A sheet, cover, alert or dialog is driven by state: a Bool or an optional item, which SwiftUI writes back when the presentation is dismissed; choose sheets for temporary tasks and navigation for going deeper. Coordinate transitions with the presentation lifecycle: keep the result pending and navigate in onDismiss, never after a guessed delay. And protect the money: guard Confirm against double taps, validate again in the store at confirm time, and remember that real idempotency is enforced by the server.
