Part 4 · TabView and NPayRouter together (section 12)

One router: a selection and four paths

App/NPayRouter.swift (condensed)
enum NPayRoute: Hashable {
    case accountDetails, settings
    case paymentSuccess(UUID), transactionDetails(UUID)
}

@MainActor @Observable
final class NPayRouter {
    var selectedTab: NPayTab = .home
    var homePath: [NPayRoute] = []
    var paymentsPath: [NPayRoute] = []
    var historyPath: [NPayRoute] = []
    var profilePath: [NPayRoute] = []

    func select(_ tab: NPayTab) { selectedTab = tab }

    func showPaymentSuccess(_ id: UUID) {
        selectedTab = .payments
        paymentsPath.append(.paymentSuccess(id))
    }

    func returnHome() {
        paymentsPath.removeAll()
        selectedTab = .home
    }
}
Why separate paths
  • Home → Account Details; History → a transaction
  • Back on Home: still on Account Details
  • One shared path makes that hard
@MainActor
  • Navigation state drives UI: mutate it on the main actor
@Observable
  • SwiftUI tracks the properties it reads
  • In depth: Unit 4
SAY

The 3.2 router had one path. Now NPay has four tabs. Picture the journey: Home to Account Details; switch to History and open a transaction; switch back to Home. Ideally Home is still on Account Details, independently of History. One shared path for every tab makes that hard to manage.

SAY

The better design: the router holds the selected tab and one path per tab. The route enum changes too: account details, payment success and transaction details carrying a UUID, and settings. Two coordinating methods: showPaymentSuccess selects the Payments tab and pushes the success route; returnHome clears the payments path and selects Home.

SAY

Click: why @MainActor? Navigation state affects the user interface, so main-actor isolation keeps its mutations in the UI execution context, as in Lesson 1.9. Click: why @Observable? The Observation framework lets SwiftUI track which properties a view reads and respond when they change. The text studies it in depth in Unit 4; for now, this router is a reference-type object that owns navigation state.

Part 6 · Where should balance and transactions live? (section 14)

Not in a tab: in a shared store

Store/NPayStore.swift
@MainActor
@Observable
final class NPayStore {
    var balancePaise = 2_500_000
    var transactions: [Transaction] = []

    func recordDemoPayment(recipient: String,
                           amountPaise: Int) -> UUID? {
        let trimmed = recipient.trimmingCharacters(
            in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty, amountPaise > 0,
              amountPaise <= balancePaise else { return nil }
        let id = UUID()
        balancePaise -= amountPaise
        transactions.insert(
            Transaction(id: id, title: "Sent to \(trimmed)",
                        amountPaise: -amountPaise, date: .now),
            at: 0)
        return id
    }
}
What changed
  • Before: ContentView owned the data
  • Now: NPayStore owns it; the root owns one store
  • 3.2’s sendDemoPayment, moved in
Never
  • A separate balance per tab (3.1’s two owners)
  • In memory: not persisted, authenticated or server-backed
SAY

The crucial design question. ContentView owned the balance and the transactions; now Home, Payments and History all need them. We must not create a separate balance per tab: Lesson 3.1 showed what two owners do. So Unit 3 introduces a shared application state object, NPayStore: main-actor, observable, holding the balance and transactions, with recordDemoPayment, which is 3.2’s sendDemoPayment moved into the store: validate, subtract, insert, return the ID.

SAY

The root view owns one instance and passes it to the tabs. This prepares us for MVVM and dependency injection in Unit 4. Click: never one balance per tab. Click: and an honest note: this is still local, in-memory demo state. Not persisted, not authenticated, not backed by a payment server.

Part 7 · Resolving routes (complete code, authored)

Every stack, one destination function

App/NPayRootView.swift
// NPayRootView: each tab's root registers the same mapping
HomeScreen(store: store, router: router)
    .navigationDestination(for: NPayRoute.self,
                           destination: destination)

@ViewBuilder
private func destination(_ route: NPayRoute) -> some View {
    switch route {
    case .accountDetails:
        AccountDetailsScreen(balancePaise: store.balancePaise)
    case .paymentSuccess(let id):
        PaymentSuccessScreen(transactionID: id,
                             onDone: { router.returnHome() })
    case .transactionDetails(let id):
        if let transaction = store.transactions.first(where: { $0.id == id }) {
            TransactionDetailScreen(transaction: transaction)
        } else {
            ContentUnavailableView("Transaction not found",
                                   systemImage: "questionmark.circle")
        }
    case .settings:
        SettingsScreen()
    }
}
Why one function
  • Any tab can show any route
  • Registered on each stack’s root
IDs resolved by the owner
  • .transactionDetails(id) → the store finds it
  • Missing ID: a ContentUnavailableView
SAY

With four stacks, each one needs navigationDestination for NPayRoute. Rather than four copies of the switch, our complete code has one destination function in the root view, passed to each stack’s root. Account details shows the balance; payment success gets its ID and an onDone that calls router.returnHome(); settings shows SettingsScreen.

SAY

Click: transaction details is 3.2’s "carry an ID" idea paying off: the route holds only the UUID, and the store, the owner of the data, looks the transaction up. If the ID is not found, ContentUnavailableView shows a standard empty state instead of crashing.

Lesson 3.3 · Recap

What to remember

Tabs switch, stacks deepen
TabView: which section; NavigationStack: how deep

One path per tab
a router: selection + four paths

One store, observed
readers update; router and store stay separate

SAY

Three things to remember. TabView answers which major section is active and NavigationStack answers how deep we are within it; selection is state, written by taps or by code. Each tab gets its own navigation path in one router, so every section keeps its place. And shared data lives in one observable store that the root owns: Observation updates the views that read what changed, and the router decides where while the store decides what.
