  • Preservation: kept while the owner lives
  • Persistence: recovered after owner or process is gone

SAY

Two ideas that are frequently confused. The lifetimes: @State lives while its view identity survives. The shared store lives while its instance survives. @SceneStorage can restore simple scene state through supported restoration. @AppStorage persists simple values through UserDefaults. SAY

Click: experiment 8, run: type a draft, terminate NPay, launch it again: both fields empty. The store is an in-memory object; when the process ended, so did the draft. Click: preservation means keeping a value while its owner is alive; persistence means storing it so it can be recovered after the owner or the process is gone.

SAY

Click: for Unit 3 we deliberately preserve the draft in memory. Persistence comes in Unit 6, and a payment draft holds a recipient and an amount: privacy and security must be considered before storing it, which is Unit 7’s territory.

Should every state property go into NPayStore? No. Moving everything into one global object creates unnecessary coupling. Decide ownership by intended lifetime and sharing. Lesson 3.5 · Recap

What to remember

Identity owns state
new values keep it; a new identity resets it

Give drafts an owner
store + @Bindable; clear when paid or discarded

Preserved is not persisted
in memory dies with the process

SAY

Three things to remember. A view value is just a struct; state belongs to the view’s identity, so recreating structs keeps it and a new identity, from replacement or .id, resets it. When input must survive navigation, move it to an owner whose lifetime spans the journey, like NPayStore, edit it through @Bindable, and clear it only on a recorded payment or an explicit discard. And preservation is not persistence: anything held in memory is gone when the process ends.
