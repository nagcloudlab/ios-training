It is called a stack. Is it like VStack?

Part 2 · Not a layout stack (section 2)

NavigationStack is not a VStack

Two different jobs
  • VStack: arranges children vertically
  • NavigationStack: manages a hierarchy of destinations
iOS 26.5 SDK, SwiftUI interface (simplified)

public struct NavigationStack<Data, Root> : View where Root : View {
  public init(@ViewBuilder root: () -> Root) where Data == NavigationPath
  public init(path: Binding<NavigationPath>, @ViewBuilder root: () -> Root)
  …
}

SAY

The name says stack, but this is not a layout stack. A VStack arranges several children vertically, and all of them are on screen together. A NavigationStack manages a hierarchy of navigation destinations: the root, then whatever has been pushed on top. One destination is visible at a time; the earlier ones sit behind it in the hierarchy.

SAY

Click: the declaration from the SDK, what Command-click shows, simplified. It is generic over Data and Root. The plain init takes only the root content; then Data is NavigationPath, a list of destinations SwiftUI keeps for you. The second init takes a path binding: navigation driven by your own state. That is Lesson 3.2.

Part 2 · NavigationLink versus Button (section 5)

An action, or a destination?

An action
Button("Send Money") {
    print("Send tapped")
}

A button runs code when tapped.

A destination
NavigationLink("Send Money") {
    PaymentScreen()
}

A navigation link declares where to go.

You want to…Use
Confirm a paymentButton
Move from Dashboard to PaymentScreenNavigationLink
SAY

Both are interactive, and both can show the words Send Money, but they express different intentions. A Button represents an action: run this closure. A NavigationLink declares a destination: this is where tapping takes you.

SAY

Click. Why it matters: with the navigation API, SwiftUI can provide the navigation behaviour for you: the push, the back button, the swipe back, the transition, and the navigation semantics. A Button that tried to fake that would have to rebuild it.

SAY

Click: the rule of thumb. Confirming a payment is an operation: a Button. Moving from the dashboard to the payment screen is navigation: a NavigationLink.

Part 7 · NavigationStack versus UINavigationController (section 15)

Same idea, declarative API

UIKitSwiftUI
UINavigationControllerNavigationStack
pushViewControllerNavigationLink or a path update
popViewControllerBack navigation or a path update
UIViewController objectsView descriptions and navigation state
Imperative navigation APIDeclarative navigation API
  • SwiftUI may use UIKit internally on iOS
  • No fixed one-to-one mapping to view controllers
  • Use the public navigation APIs
SAY

In UIKit, navigation is commonly built with UINavigationController: you create view controller objects and call pushViewController and popViewController, an imperative API. SwiftUI’s NavigationStack is a declarative abstraction: you describe destinations with links, or with a path, which is Lesson 3.2, and SwiftUI performs the pushes and pops. View controllers become view descriptions plus navigation state.

SAY

Click: the insight. On iOS, SwiftUI may integrate with UIKit internally, but do not assume a fixed one-to-one mapping between SwiftUI destinations and UIKit view controllers. Use the public navigation APIs unless you have a specific interoperability need; Unit 10 covers UIKit integration.

Simulator

-- tap Send Money
DemoPaymentService init
-- tap Back

Two systems
  • SwiftUI: view lifetime and state, by hierarchy
  • ARC: class instances, by ownership (1.8)
So
  • Here: freed right after Back
  • Off screen ≠ guaranteed immediate deallocation
  • A capturing closure can keep it alive
SAY

Connect Unit 0 and Unit 1. When a destination appears it may create state, load resources or reference services; when it disappears, some of that may become eligible for release. Two systems are involved: SwiftUI manages view lifetime and state according to the hierarchy, and ARC manages the lifetime of class instances, as in Lesson 1.8.

SAY

Our experiment, authored: the destination creates a reference-type service in onAppear and keeps it in @State. Click: the run: the service is created on the push; after Back, onDisappear, then deinit: the destination’s state was discarded and the last strong reference went with it.

SAY

Click: but read that as "here", not "always". Disappearing from the screen is not a guarantee of immediate deallocation. If a closure retained that service, for example a stored callback or a task, its lifetime would follow those ownership relationships. What to remember

A hierarchy, not a layout
NavigationStack manages destinations; one is visible

Links declare, buttons act
NavigationLink for screens; Button for operations

One owner; local state is temporary

SAY
